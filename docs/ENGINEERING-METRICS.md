# 工程质量量化标准（ENGINEERING-METRICS）

本文档把四条研发宗旨——**做事不要怕繁琐、目标导向、用户使用便利导向、安全导向**——翻译成可测量、可判定、可执行的工程标准。每条标准写清五件事：指标定义、当前实测基线、目标阈值、测量方法（可执行命令）、判定与失败动作。

**文档边界**：CODING-STANDARDS.md 回答「代码怎么写」（91 条规则），SECURITY.md 回答「防什么威胁」（核查清单），本文档只回答「做到什么程度算达标、怎么量、不达标怎么办」。三份文档不互相重复，本文档的判定结果挂接到 CODING-STANDARDS §7 提交前自检清单逐条执行。

**基线测量时点**：2026-11-03，v0.17.42，Windows 本机 `.venv`。所有基线值均为当日实跑结果，未估算。

**2026-11-03 裁决回填**：第七节 5 个取舍点经用户裁决全部落地——U2 时延脚本已建并实测定档（P95 ≤ 500ms）、S5 已引入 pip-audit 并完成首次真实扫描（119 条命中 / 10 个包）、S2 覆盖率目标统一 90%、S4 的 `{e}` 口径收窄为「对外三通道零容忍、本机日志放行」、CI 门禁裁决维持人工。回填只改本文档与 requirements-dev.txt、tests/perf_baseline.py，CODING-STANDARDS.md 的同步修订点另列清单转交。

## 二、目标导向：没有可判定的验收条目，不得进入开发

**G1 · spec 前置率**
指标：进入开发的每项任务在 `docs/specs/` 有对应 spec，且含编号验收条目（AC）。
基线：19 份 spec；现行 spec 均带 AC1..N 编号条目（近三版 v0.17.39/40/41 均按此交付）。
阈值：**100%**，无 spec 不开工。
测法：`ls docs/specs/`，任务启动时人工核对文件名与 AC 存在性。
失败动作：**阻断**——任务不进入开发，先补 spec 并经确认。

**G2 · 验收条目可判定率**
指标：每条 AC 的通过条件可以客观判定（具体数字、具体状态码、具体文件存在性），不接受「体验良好」「性能较优」式描述。
基线：现行 spec 的 AC 均可判定（如「全量 686 个用例通过」）；人工抽查口径，无自动化。
阈值：**100%**。
测法：spec 自检（spec-first 流程既有环节），逐条问「这条拿什么命令或操作验」。
失败动作：**阻断**——spec 退回改写，不写无法判定的 AC。

**G3 · 交付对照率**
指标：交付时逐条对照 AC 给结论，版本记录写明「新增 N 个用例，全量 M 个通过」。
基线：README 版本记录近十版均含用例数与全量结果（如 v0.17.42「新增 6 个用例，全量 694 个用例通过」）。
阈值：**100%**，每条 AC 有「通过/不通过及原因」结论。
测法：代码评审环节逐条核对 spec 的 AC 与测试/实现。
失败动作：**阻断**——对照表不全不得进入评审。

## 三、用户便利导向：时延、步骤、错误提示都要有数

**U1 · E2E 人工链路回归**
指标：5 条真实浏览器链路（登录/登出/会话恢复、HttpOnly 凭据、恶意 docx 不执行、审批 UI 链路、部署待验项）构成用户体验的验收底线。
基线：5 条链路 2026-11-03 本机真实浏览器执行通过（E2E-ACCEPTANCE.md 第四节有执行记录）。
阈值：**变更触及认证、审批、知识库渲染、聊天页面任一链路覆盖面时，必须重跑对应链路**；全量 5 链每季度至少执行 1 次。
测法：按 docs/E2E-ACCEPTANCE.md 步骤表逐链人工执行并留证（截图/记录写回该文档第四节）。
失败动作：链路失败**阻断提交**；季度全量缺失记 PLAN 待办。

**U2 · API 时延**
指标：本地 mock 模式下基础端点响应时延（登录、会话列表、文件列表等），不含模型推理时间。
基线：2026-11-03 实测（tests/perf_baseline.py，TestClient 进程内，每端点热身 1 轮 + 计 50 轮，独立临时库）：login min 224.2 / median 235.1 / **P95 241.9** / max 244.4；health P95 11.6；sessions P95 12.0；uploads P95 7.4；usage P95 23.7（单位 ms）。login 显著高于其余端点的主因是 pbkdf2 口令哈希的刻意时延成本，属安全设计，不压缩。
阈值：**每端点 P95 ≤ 500ms**（依据：最差端点实测 241.9ms，留约 2 倍余量；2026-11-03 用户裁决定档）。模型首 token 时延依赖 vLLM 部署质量，不设阻断线，列入长期跟踪。
测法：`.venv\Scripts\python.exe tests\perf_baseline.py`，脚本输出各端点 min/median/p95/max，任一 P95 超 500ms 退出码非零。
失败动作：单次超标记 PLAN 待办排查；连续两个提交点超标**阻断提交**。

**U3 · 错误提示可操作性**
指标：面向用户的错误提示必须含「下一步能做什么」（如「租约已被接管」类文案），不得只报内部状态。
基线：无统计口径，靠评审把关；既有反例已在历史版本修复（如 SessionDeletedError 误报「模型调用失败」已归一）。
阈值：新增用户可见错误文案 100% 含可操作指引。
测法：代码评审逐条检查新增错误文案；无法自动化。
失败动作：评审发现问题**阻断提交**，修复后重审。

**U4 · 核心交互步骤数**
指标：核心路径「打开页面 → 登录 → 发出第一条消息 → 看到回复开始流出」的操作步骤数。
基线：未量化统计；E2E-1 链路实际覆盖了该路径。
阈值：**≤ 4 步**（打开、输入凭据、输入消息、看到流式输出）。
测法：随 E2E-1 链路人工执行时数步骤并记录。
失败动作：步骤数增加需在 spec 中说明理由并经确认；无理由增步**阻断**。

## 四、安全导向：拒绝路径与 fail-closed 要逐个数

**S1 · 全量回归不破**
指标：安全防线的最小保障是全量测试全绿。
基线：784 passed / 18 skipped / 0 failed（18 个 skipped 为真实模型/Docker 门控与本机符号链接权限降级，语义固定；较上版 694 增 90 = S4(b) 5 + S3 缺口 32 + 三模块拒绝/边界分支 53）。
阈值：**failed = 0；passed 单调不减**（用例被替代时须在 spec 说明）；skipped 集合语义不变。
测法：`.venv\Scripts\python.exe -m pytest -q`。
失败动作：**阻断提交**。

**S2 · 安全关键模块覆盖率**
指标：12 个安全敏感文件的行覆盖率（auth、approval、session_lock、sessions、packsign、packs、skills、custom_tools、tools_builtin、html_sanitize、usage、sandbox/server）与整体覆盖率。
基线（2026-11-03 一期补齐后实测）：approval 100%、session_lock 100%、sandbox/server **100%**、custom_tools **100%**、auth 99%、skills **99%**、packsign 96%、usage 96%、sessions 95%、packs 92%、html_sanitize 91%、tools_builtin 91%；12 个文件全部 ≥90%，整体（server/+sandbox/）**92%**（4691 语句 / 362 未覆盖）。skills 余 1 行（zip 落点 resolve 兜底，属不可构造分支）。
阈值（2026-11-03 用户裁决，统一 90% 不设折中档）：单文件 **≥ 90%**；整体（server/+sandbox/）**≥ 90%**——三个不达标模块补齐后整体自然过线，两档同目标。
测法：`.venv\Scripts\python.exe -m pytest -q --cov=server --cov=sandbox`，再 `coverage report --include=<清单>`。pytest-cov 已在环境中，零新增依赖。
失败动作：整体或任一已达标文件跌破 90% **阻断提交**；一期补齐（2026-11-03 已完成）：skills 补错误哨兵与快照缺失分支、custom_tools 补守卫拦截与执行异常分支、sandbox/server 补超时与清理失败分支，共新增 53 条拒绝/边界用例，不堆正向用例。

**S3 · 拒绝路径逐入口覆盖**
指标：每个外部入口（35 个 HTTP 端点、文件上传、包导入、工具执行、登录、审批）至少 1 条拒绝/越权用例。
基线：`docs/reviews/endpoint-deny-mapping.md` 已建（2026-11-03），35 个端点逐行登记：4 个公开端点（不计缺口）、31 个有真实拒绝用例覆盖（其中 #12、#20 仍为部分场景覆盖）、**0 个纯缺口**；原 9 缺口 + 2 半覆盖由 `tests/test_endpoint_deny_gaps.py` 32 条用例补齐。test_deny_paths.py 33 个用例 + 各模块内 40x 断言继续作为补充。
阈值：映射表内每个涉权限端点 ≥ 1 条拒绝用例，覆盖率 100%；免鉴权端点（如 health）在表中标注「无权限维度」占位，不算缺口。
测法：建立 `docs/reviews/endpoint-deny-mapping.md`（一次性人工核对 35 端点逐行登记，约半天），之后新增端点同步登记；抽查用 grep 验证。
失败动作：映射表建立前，新增端点无拒绝用例即**阻断**（现有规则已有此要求）；存量映射补建列为**一期补齐**。通过判定：映射表 35 行齐全（每行标「用例文件::用例名」或「无权限维度」）+ 表内引用用例在测试中真实存在 + 全量回归绿。

**S4 · 敏感信息泄露自检**
指标：(a) server/+sandbox/ 的 `print(` 违规数；(b) **对外三通道**的 `{e}` 拼接数；(c) TODO/FIXME 残留。
通道口径（2026-11-03 用户裁决定义）：**用户通道**=HTTP 响应体/SSE 流/页面可见文本；**模型通道**=工具执行后返回给 LLM 的文本；**审计通道**=写入审计日志的记录。这三条通道的受众可能离开部署机（浏览器、模型上下文、日志外发），零容忍。**本机日志通道**（uvicorn/应用日志，只落在部署机磁盘）允许保留原始异常文本——理由：日志不出内网、排障需要完整堆栈，外泄面已被 (a) print 禁令与 CODING-STANDARDS §2.6 密钥条款覆盖。
基线：(a) **0 违规**（2 处豁免均有注释与理由）；(b) **5 处对外通道命中**：server/custom_tools.py:195（语法错误回显）、server/packs.py:112 与 :385（包错误信息）、server/skills.py:506（错误哨兵）、server/weather.py:133（错误聚合）；本机日志通道约 18 处按裁决放行；(c) **0**。
阈值：(a) 0，(b) 0，(c) 0；本机日志通道不设限。
测法：(a) `grep -n "^\s*print(" server/ sandbox/`（豁免逐条核对注释）；(b) `grep -n "{e}" server/`，逐处判定落点通道（函数返回值去向：HTTP 响应/工具返回/审计 → 对外；logger 调用 → 放行）；(c) `grep -rn "TODO|FIXME|XXX|HACK" --include=*.py .`。
失败动作：(a)(b)(c) 新增即**阻断提交**；存量 5 处对外通道 `{e}` 已于一期补齐（改为固定/归类文案，参照 tools_builtin.py:248 先例）。通过判定：对外三通道 grep 命中清零 + 每处改造配「错误文本不含绝对路径/异常原文」的断言用例 + 全量回归绿。

**S5 · 依赖供应链**
指标：直接依赖数量受控、已知漏洞扫描（pip-audit）。
基线：21 个直接依赖；pip-audit 2.10.1 已入 requirements-dev.txt，固定 OSV 后端。2026-11-03 首次扫描命中 **119 条 / 10 个包**（直接依赖 3 个：pypdf 11 条、fastmcp 1 条、langgraph-checkpoint-postgres 1 条）；同日升级后复扫 **107 条 / 8 个包**，直接依赖命中 **3 → 1**：pypdf（6.21.4）与 langgraph-checkpoint-postgres（3.2.0）清零，**fastmcp 1 条（GHSA-7xgj-8392-5q4r）仍存在**——4.x 需先验证与 mcp 1.x 锁定行兼容，本轮不动，不隐藏（requirements.txt 已留注记）。
环境说明：本机访问 pip-audit 默认的 PyPI JSON 服务超时，固定改用 OSV 批量接口；OSV 输出无 CVSS 分级，故不按「高危=0」判定而按「直接依赖命中=0」判定。
阈值：**直接依赖命中 = 0**（阻断线）；传递依赖命中数只减不增；直接依赖数量（21）只减不增（新增需 spec 说明理由）。
测法：`.venv\Scripts\pip-audit.exe --vulnerability-service osv --timeout 60`（依赖变更必跑 + 每月定期 1 次）。离线替代路径：在有网环境定期跑扫描、把升级清单带回内网执行；不可用扫描结果造假充数。
失败动作：直接依赖命中 > 0 时**阻断依赖变更类提交**，并登记升级清单（当前剩：fastmcp→≥4.1.2——需先验证与 mcp 1.x 锁定行的兼容性，见 requirements.txt 注释；该条为已知例外，不隐藏）；非依赖类提交不受存量阻断，但升级清单列入**一期补齐**。

**S6 · fail-closed 与鉴权一致性（流程判定）**
指标：新增安全防线默认拒绝、权限判定三处（提示层/执行层/端点层）同口径。
基线：SECURITY.md 附录已有 fail-closed 原则总表；v0.17.39 起 Identity 快照统一两层口径。
阈值：100%——每条新防线 fail-closed + 配拒绝用例。
测法：代码评审逐条核对（自检清单已有对应勾选项）；无自动化。
失败动作：**阻断提交**。

## 五、不怕繁琐：固定次数、固定留痕、不许跳

**P1 · 全量回归，每次提交前 1 次**
指标：提交前必须实跑一次全量回归，不许用「上次跑过」替代。
基线：143s（含覆盖率 208s）——成本可承受。
阈值：每次提交 1 次，结果全绿（S1 口径）；墙钟预算 **≤ 300s**，超时记待办做拆分/加速，不阻断。
测法：pytest 输出尾部计数与耗时；提交汇报中引用本次结果数字。
失败动作：未跑或不绿**阻断提交**。

**P2 · 代码评审，每次提交前 1 次**
指标：每次提交前执行 TRAE-code-review，候选问题逐条处置（修复/证伪/有意保留三选一），处置理由留痕。
基线：docs/reviews/ 11 份留痕；近版本评审候选均逐条裁决（如 v0.17.42「4 候选：修复 2、有意保留 2」）。
阈值：**100% 提交有评审；候选处置率 100%**。
测法：docs/reviews/ 或 spec 第五节的留痕存在性；提交汇报中引用评审结论。
失败动作：**阻断提交**。

**P3 · spec 与红测试先行**
指标：测试先于实现跑红，再实现转绿（red-test-first）。
基线：现行流程已固化（CODING-STANDARDS §4.1）；无法从事后代码自动验证顺序。
阈值：100% 新功能与缺陷修复。
测法：开发过程留痕（spec 中记录红测试输出）；评审时抽查。
失败动作：评审发现先实现后补测，该功能**打回重做测试**。

**P4 · 带页面功能两道人工关**
指标：页面原型人工审核通过才开发；页面实现后人工实测通过才评审。
基线：流程已固化（CODING-STANDARDS §5.5）；v0.17.28 等有「经浏览器实测与人工确认」记录。
阈值：100% 带页面功能。
测法：spec 与提交汇报中的关卡记录。
失败动作：**阻断**——原型未审不开发，页面未实测不评审。

**P5 · 文档同步，每次提交 1 套**
指标：README 版本记录（只写功能）、docs/ 相关文档、PLAN.md 待办标记随提交同步。
基线：13 条自检清单末位即是；近版本均同步。
阈值：100% 提交。
测法：提交前自检清单勾选。
