# PAP 4.2 定时/事件触发 Spec 草案评估

日期：2026-11-06

评估对象：`docs/specs/4.2-scheduled-triggers.md`（工作区草案，尚未提交）

对照基线：最新提交 `dd44a5644c41a7decabd39ba91492e9f79e16bde`（v0.17.48）、4.1 spec 与当前编排/身份/上传实现。

范围：仅评估需求、架构契约和验收标准，不修改业务代码；工作区其他改动及 `.screenshots/` 未纳入评估。

## 1. 结论

**方向可行，但当前不建议确认进入编码。** 复用 4.1 的定义校验、编排引擎和实例历史，采用 interval、单调度循环和纯工具管理等取舍适合 POC；但自动执行的身份时效、事件授权、防重入原子性和崩溃恢复尚未形成可实现契约，且草案对现有栅栏行为的描述与代码相反。

建议先关闭本文 P1，再补齐对应 AC。否则实现 agent 很可能在“按 spec 实现”的情况下引入持续越权执行、重复触发、永久停摆或上传接口异常。

## 2. Findings

### P1-1：后台执行与栅栏契约存在事实错误

草案称后台“无会话代际，`fence_ok` 必失败”，并预期审批路径以 `aborted` 结束；当前实现并非如此：

- `server/orchestration.py:511`：`generation is None` 或 `session_id` 为空时，`check_fence()` 直接返回，不做栅栏检查。
- `server/usage.py:41`：非对话路径的 generation 默认为 `None`，注释明确“不做栅栏”。
- `server/orchestration.py:60`：审批、管理和危险工具已通过 `FORBIDDEN_TOOL_NAMES` 与编排安全清单隔离，不能把这类工具笼统描述成后台审批场景。

必须修订为明确契约：

1. 自动实例使用 `session_id=""`、`generation=None`，不绑定任何会话删除生命周期。
2. 自动执行仍只能装配现有安全工具清单；危险/审批/管理工具直接拒绝，不承诺产生“审批后 aborted”的伪语义。
3. 明确删除调度只停止未来触发，还是同时取消在途实例。若需后者，应另设调度/实例取消代际，不能复用会话 fence；若本轮不取消，也须写入 AC。

### P1-2：永久 Identity 快照会在撤权后继续自动执行

D6 将创建者完整 Identity 永久保存在调度行，并以“零新增权限判定”为理由。请求内不可变快照适用于 5.1，但不能直接推广为长期后台任务的永久授权：

- `server/auth.py:489` 支持吊销用户，`server/auth.py:238` 支持角色降级，`server/auth.py:222` 支持部门调整；旧快照不会随这些操作失效。
- SSO 场景下部门是权威身份属性，登记时快照尤其不能代表未来调岗后的权限。
- 自动任务可反复读取文件/知识库并写产出，且持续消耗创建者额度，风险显著高于单次请求内沿用快照。

建议调度行只保存创建者主体和必要审计字段，每次触发时重新解析当前有效身份、角色、部门、账号有效期及目标定义/资源权限。主体不存在、吊销、过期或降权后不满足条件时拒绝执行并留下可查的 `skipped/failed` 记录。若坚持冻结快照，必须单独完成风险裁决并提供到期、续期和撤权联动机制；不建议 POC 采用。

### P1-3：文件上传事件缺少匹配规则、载荷和权限绑定

当前 AC3 仅要求“上传成功后触发登记了该事件的定义”，不足以避免跨域触发和成本放大：

- 未定义调度按上传者域、目录、文件名/扩展名过滤，任何用户上传是否都会触发 admin/approver 登记的高权限流程不清楚。
- 未定义流程如何获得事件上下文；若没有白名单载荷，上传事件虽然触发成功，流程也无法可靠处理目标文件。
- 同名覆盖、连续重复上传、docx 转换后名称、无权限上传及失败上传是否触发均未明确。

建议 POC 最小契约：登记时强制指定精确 `scope`，可选安全的文件名/扩展名过滤；只在上传及转换均已成功后触发；事件载荷仅包含 `event_id`、规范化相对路径、上传者主体、scope、文件大小/字符数和触发时间等白名单字段，不传 preview/全文；上传者域不在允许范围时不执行。还要明确同一次上传对同一调度的幂等键及覆盖上传语义。

挂钩位置应对应 `server/routes/files.py:175` 的落盘成功之后。当前外层 `except Exception` 位于 `server/routes/files.py:184`，若同步挂钩异常未被内部完全隔离，会把已成功的上传变成 500，因此“旁路不阻塞”必须由挂钩边界和测试共同保证，不能只靠描述。

### P1-4：防重入和调度推进没有原子性及崩溃恢复契约

AC5 的“查询上一实例 running 则跳过”不足以作为互斥机制：

- running 查询、创建实例和推进 `next_run` 若不在同一原子协议中，并发到点扫描或事件派发可重复执行。
- `server/orchestration.py:1030` 明确实例创建是 best-effort，写库失败仍继续执行，因此不能把实例行当作可靠锁。
- 进程崩溃会留下永久 running，按现草案会导致该定义之后永远跳过。
- “跳过并记日志”没有可查询历史，不满足自动任务的可观测性。

需定义独立、持久的调度 claim/租约及唯一触发键，在同一事务中完成到点判断、抢占和 `next_run` 推进；实例历史仍用于业务结果，不承担锁职责。还需定义启动时 stale running/claim 的处理、重复扫描幂等、执行期间再次到点的规则，以及事件与 interval 并发时的防重入口径。

部署边界也要写成强制前提：仅一个进程、每进程仅一个调度循环；否则启动时必须拒绝多 worker 或使用真正跨进程锁。仅写“不做多进程抢占”不能防止误部署重复执行。

### P2-1：异步边界不清，容易阻塞事件循环或产生孤儿任务

D4 把 `process_due(now)` 定义为同步函数，但实际 `run_orchestration` 是 async（`server/orchestration.py:1087`）。需明确核心函数是仅做同步 claim 并返回待执行作业，还是会同步等待异步编排；不得在事件循环线程中直接阻塞执行完整流程。

D5 的“异步派发”也需规定任务引用管理、完成回调、异常回收和 shutdown 行为。裸 `create_task` 可能造成异常无人观察、重启时任务静默丢失或退出悬挂。若接受重启丢失，应与“不补跑”一起明确，不得暗示持久事件队列语义。

### P2-2：实例和调度审计字段不足

仅给 `workflow_instances` 增加 `trigger_source` 不足以定位自动任务。建议至少设计：

- `schedule_id`、`trigger_id/event_id` 或幂等键、计划触发时间与实际触发时间。
- skip/error 原因及可查询的触发尝试记录；跳过、失效、撤权、claim 冲突不能只存在日志。
- 自动实例唯一 `run_id` 的生成和归属，避免空 run_id 难以串联用量与审计。
- 调度创建、删除、失效、触发和拒绝的审计事件；删除权限需区分创建者、approver、admin。

interval 还需明确首次到点基准、执行耗时跨过多个周期时的推进方式、系统时钟回拨/跳变处理。调度参数及持久化 JSON 应限制大小、类型和长度，并定义旧行/损坏行的兼容与拒绝行为。

## 3. 可保留的设计

- 复用定义加载、参数校验、编排执行与实例列表，避免另建执行引擎。
- POC 仅支持 interval，不引入 cron 和第三方调度依赖。
- 将调度管理工具纳入编排禁用清单，防止流程递归创建调度。
- 调度持久化、无人在场计量归属、上传旁路隔离和可注入时钟的测试方向合理。
- 不做 Web 页面和错过补跑可作为本轮明确边界，但必须以可查询的跳过/失效记录弥补可观测性。

## 4. 必须补充的验收标准

建议在现有 AC1–AC10 之外补充或改写以下用例：

1. **身份时效**：创建后吊销、删除、过期、角色降级、部门调岗，下一次触发均被拒绝并留痕；恢复有效身份后的行为明确。
2. **后台边界**：自动实例不绑定会话 fence；危险/审批/调度管理工具被拒绝；删除调度对未来和在途实例分别符合约定。
3. **原子防重**：同一到点并发扫描两次只 claim/执行一次；事件与 interval 同时到达不重复；实例历史写失败也不能破坏互斥。
4. **崩溃恢复**：执行中进程退出留下 running/claim，重启后按明确 stale 策略恢复，不永久跳过、不无条件重复执行。
5. **推进与幂等**：长任务跨多个周期、重复 event_id、同名覆盖上传、停机恢复均按约定推进，不发生追赶风暴。
6. **事件授权**：匹配/不匹配 scope、不同上传者、docx 转换后路径、失败上传、无登记及过滤条件均有明确结果；事件载荷不含全文和绝对路径。
7. **旁路与生命周期**：挂钩同步异常、异步执行异常均不影响上传响应；服务退出能取消/等待任务并记录结果，无未观察异常。
8. **调度拓扑**：多 worker/第二调度器的拒绝或互斥行为有测试/启动守护，而非仅文档声明。
9. **历史与审计**：scheduled/event 实例可关联 schedule 和 trigger，skipped/failed 原因可查，创建/删除/撤权拒绝有审计。

## 5. 建议的 Q1–Q5 裁决

- **Q1：A，仅 interval。** 补充首次执行、周期推进、时钟跳变和最小间隔契约；测试注入时钟，不降低生产下限。
- **Q2：仅对话式管理工具。** 本轮不加管理端点，但需完整定义工具级 RBAC、资源归属和审计。
- **Q3：A，仅 approver/admin 登记。** 这只是创建入口收口，不能替代每次触发时重新鉴权；删除权限另需明确。
- **Q4：仅文件上传成功事件。** 先增加精确 scope 绑定和白名单事件载荷，不挂 KB 入库、不造通用事件总线。
- **Q5：纯后端+工具。** 可接受；调度状态和跳过/失败原因必须能通过工具查询，避免无页面导致不可运维。

## 6. 复审准入条件

满足以下条件后再进入编码较稳妥：P1 四项均有明确设计与对应 AC；D4/D5 的 async 生命周期无歧义；数据模型能表达调度、触发尝试、实例和审计的关联；单调度器部署前提可执行。本文未运行测试，因为评估对象仅为 spec 草案。
