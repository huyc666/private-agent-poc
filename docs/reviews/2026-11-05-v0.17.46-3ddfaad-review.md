## 1. 审核结论

**PLAN 4.1 主体功能通过：参数化定义、重复触发、实例实体与分身份可见性、
真实 Runnable 进度事件、SSE 白名单、周报示例、计量回归和全量测试均成立。**

本轮未发现高危越权或远程代码执行问题。主审与交叉审查共确认 **6 项边界问题**：

- **N1【中低·验收语义】**：执行中途栅栏中止时，`aborted` 实例仍保存此前步骤的
  部分产出；现有测试只覆盖“首步前中止”，没有覆盖规格 AC7 的中途中止场景。
- **N2【中低】**：声明中的字符串 `default` 可超过 2000 字符，省略该参数时绕过运行期
  长度上限，并进入实例记录和模型任务。
- **N3【中低】**：`list_orchestrations` 不做定义校验；可解析但不可执行的定义会混入
  列表，`params: 1` 更可使整个发现工具抛 `TypeError`。
- **N4【低·内部健壮性】**：`params=[]`、`params=""`、`params=0` 等 falsy 非字典值

  校验通常会在外层拦截，因此当前不按外部越权处理。
- **N5【低·前端交互】**：进度事件提前创建回答气泡，后续工具芯片会显示在回答之后，
  破坏既有“工具调用标签显示在回答之前”的顺序。
- **N6【低·示例一致性】**：周报 `highlights` 实现默认值为 `"无"`，与 spec §2.5
  明确的“默认空”不一致，测试还固化了这一偏差。

**建议至少修复 N1–N3、N5–N6，并将 N4 一并作低成本收口后再标记 PLAN 4.1
完整验收通过。当前实现可继续作为后续评审与修复基线，但严格按 spec，AC2、AC5、

## 3. 新发现与修复建议

### N1【中低】中途栅栏中止仍留存部分产出，AC7 覆盖不完整

位置：

- `server/orchestration.py:796-799`：`_FenceAbort` 返回的 `_failure` 携带 `outputs`。
- `server/orchestration.py:1108-1115`：aborted 与 failed 共用终态回写，均传
  `result.get("outputs")`。
- `tests/test_workflow_instances.py:287-300`：栅栏从第一次检查起即 false，只验证
  首步前中止，因此无法发现中途场景。

独立复现：两步定义，第一次 fence 检查通过、第二次失败。结果：

```text
status = aborted
failed_step = second
outputs_json = {"first": "第一步敏感产出"}
```

规格 AC7 写明“代际栅栏中止 → `aborted`、无新产出”。当前没有第二步新产出，但
实例仍保存第一步部分产出；这与现有测试所采用的 `outputs_json == {}` 口径不一致。
如果产品真实意图是允许保留中止前部分产出，则应修改 spec 与测试文案，明确“无
中止后新增产出”而非“无产出”；否则实现应按当前 AC 收口。

建议：aborted 分支回写 `outputs={}`、`summary=""`；增加“首步已完成、第二步前
fence 失效”的用例，断言 `status=aborted`、`failed_step=second`、`outputs_json={}`。
若裁决保留部分产出，则反向修改 AC7，并补测不得在 fence 失败后追加第二步产出。

### N2【中低】默认值绕过运行期参数长度上限

位置：`server/orchestration.py:939-949`。长度检查只在 `name in provided` 分支，
默认分支直接 `values[name] = p.get("default", "")`；声明校验 `:166-167` 只检查
default 类型，不检查字符串长度。

独立复现：

```text
params = [{name: week, type: string, default: "x" * 2001}]
validate_definition(...) = []
_resolve_trigger_params(..., None) error = ""
len(values["week"]) = 2001
```

这违反 2.1“单个参数值运行期长度上限 2000 字符”。超长默认值会完整写入
`params_json`、渲染进任务并送往模型，绕过防成本放大措施。风险需要流程作者控制
默认定义，不等同外部提权，但验收上限明确失效。

建议：在 `_resolve_trigger_params` 返回前统一校验所有最终值（显式值与默认值），
并可在声明校验期提前拒绝超长字符串 default；增加“省略参数时使用超长默认值
拒绝且无实例行”的用例。

### N3【中低】无效定义混入发现列表，特定输入可使整个工具崩溃

位置：`server/orchestration.py:1130-1136`、`:1169-1204`。列举使用
`_load_yaml_lenient`，只判断 YAML 可解析且为 dict，不调用 `validate_definition` /
`load_definition`。

独立复现：写入 `roles: []`、`steps: []` 的 `semantic-bad.yaml`：

```text
validate_definition(...) -> 非空错误列表
list_orchestrations() -> "- semantic-bad（v1，全局）"
run_orchestration(...) -> 定义校验失败
```

进一步复现：加入一个可解析的 `aaa-crash.yaml`（内容为 `name: aaa-crash`、
`params: 1`）后，`list_orchestrations()` 在 `_format_params_line(1)` 抛出：

```text
TypeError: 'int' object is not iterable
```

一个损坏文件即可使其他有效全局/个人定义也无法被发现。执行仍 fail-closed，因此
不是权限绕过；问题包括“可用流程”展示不一致和单文件拖垮整个发现工具。

建议：列举时复用 `load_definition(path)`，只展示 `status == "ok"` 的定义；语法错误
与语义错误均跳过，参数格式化同时防御非 list 输入。新增“YAML 合法但 roles/steps
为空”和“一个 `params: 1` 文件不影响其他有效定义列举”的用例。

### N4【低】falsy 非字典 params 被当作缺省

位置：`server/orchestration.py:929-932`：

```python
provided = params or {}
if not isinstance(provided, dict):
    ...
```

空列表、空字符串和整数 0 都在类型检查前被变成 `{}`。在参数均非必填时，独立直调
`_resolve_trigger_params` 对这三种值均返回成功。正确顺序应是仅在 `params is None`
时补 `{}`，其余值原样做 dict 类型检查。

外部 StructuredTool 通常会先按 schema 拒绝这些类型，故本项主要是公共函数防御性与
测试替身路径一致性，不升级为安全漏洞。建议增加直接函数边界用例。

### N5【低】进度事件提前创建回答气泡，破坏工具/回答显示顺序

位置：`web/index.html:671-675`、`:720-735`。原有注释明确“延迟到首个 token 再创建，
保证工具调用标签显示在回答之前”，但 progress 分支调用 `getBubble()`，在首个 token
之前就插入空气泡。

真实事件顺序可为：工具开始 → progress → 子工具事件/工具结束 → 最终 token。此时
后续工具芯片追加在空气泡之后，而最终 token 又写回较早的气泡，用户看到的回答位于
后续进度与工具结果之前。进度元素也是气泡的兄弟节点，不是 spec §2.4 所述“当前
气泡内”。

建议：progress 分支不要创建回答气泡，改用独立执行进度容器，保持首个 token 才创建
回答气泡的原有顺序；补 `progress → tool → token` 的 DOM 顺序测试。该发现由交叉
审查提出并经主审对照事件分派代码确认，本轮未运行真实浏览器。

### N6【低】周报默认值与已确认 spec 不一致

位置：`orchestrations/weekly-report.yaml:13-16` 使用 `default: "无"`；
`tests/test_workflow_instances.py:184-185` 进一步断言省略参数后存成 `"无"`。
但 spec §2.5 明确 `highlights`“可选，默认空”。因此省略参数时的渲染任务与持久化
参数均偏离契约。

建议：改为 `default: ""`，同步修正实例字段断言和预期渲染文本；若产品确实偏好
“无”，应先修订 spec，而不是让测试反向固化未裁决行为。
