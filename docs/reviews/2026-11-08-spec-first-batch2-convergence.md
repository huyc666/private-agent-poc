# spec-first 第二批重构：收敛性复核记录

执行者：未参与本批改动的独立会话，只读规则文本与既有 spec/tests，不改文件
整理落盘：改动作者按复核结论整理，未参与结论形成；本文不含复核之外的新判断

被复核对象：第一批改动落地后的 `.trae/skills/spec-first/SKILL.md`、

## 1. 复核方法

1. 逐条读三个文件的规则文本，重点看跨文件引用是否自洽（矩阵 ↔ 红线 ↔
   CODING-STANDARDS ↔ TRAE-code-review）。
2. 取已交付的 4.2 定时触发器 spec 做 dry run：用新账本规则尝试为其中一条
   AC 填账本行，并核对 spec §5 清单与 `tests/` 实际用例名是否能一一对上。
3. 对每个疑点先回到文件核实，再定性；核不实的写入第 4 节「不成立的疑虑」，
   不与确认问题混排。

### 1.1 dry run 的具体过程与发现

dry run 选 4.2 的理由是它有完整的 §5 红测试清单与 §6 红运行记录，且已交付、
用例名稳定。实际跑出三个结果：

- **4.2 不能当账本样本**：它只有 §5、§6，没有账本，也没有 §7 收敛结论；
  CODING-STANDARDS 却把它举成账本实例，引用证明不了「账本怎么写」。
- **AC13 填不出合法的红态值**：4.2 §5 标注「AC13 无独立用例」，但账本规则
  当时没有允许值枚举，填「无单测」「待填」「手工」都像合法，无法判定。
- **前缀匹配会把语义错配判成对上**：4.2 §5 声称 AC13 无独立用例，
  `tests/` 下却有 12 个 `test_ac13_*`。若红态一致性/兑现关按「AC 编号前缀」
  匹配验证项，这 12 个用例会被自动认作 AC13 的验证项，与 §5 的声明直接
  矛盾，而流程不会报错。这是本次复核发现的真问题，不是纸面推演。

## 2. 十条接缝：位置、问题、裁决与改法

### 2.1 缺陷修复档没有账本载体

- **位置**：SKILL.md 档位矩阵（spec 文件=免、AC 账本=免）；红线允许无 spec 提交。
- **问题**：账本必须落在评审能看见的地方，但该档既无 spec 也无账本，复现
  用例与验证方式只存在于对话，评审与兑现关无法对照。
- **裁决**：保留一份极简 spec，只写复现用例与验证方式，并入 §4 账本行；
  不要求四部分全文、不强制 §5–§7；必须落 `docs/specs/`。
- **改法**：矩阵两格改为「极简（复现用例 + 验证方式）」与「必（AC=复现
  用例 + 验证方式）」；模板段补例外；红线新增「未落极简 spec 不得提交」。
  连带修正：红线例外由「免 spec 的档位」改为「『用户确认』为免的档位」，
  CODING-STANDARDS §5.1 的四部分要求同步放宽，否则缺陷修复档无法开工。

### 2.2 账本另起 §4.1 与 §4 重复

- **位置**：SKILL.md spec 骨架，§4 验收标准 + 独立 §4.1 账本。
- **问题**：同一个 AC 在 §4 写一遍、在 §4.1 再列一遍，两处漂移无人负责；
  S 级任务还要背六列，轻档负担与收益不匹配。
- **裁决**：不另起 §4.1，直接把 §4 验收标准表扩成账本；S 级允许压缩到
  「验证方式 / 用例 / 收敛」三列。
- **改法**：模板改为七列表（AC / 验收标准 / 验证方式 / 用例·留证 / 红态 /
  实现证据 / 收敛）；步骤 4、7、10 的「§4.1」引用全部改为「§4 账本」；
  CODING-STANDARDS §5.1 同步。

### 2.3 复审计数口径会把收敛误判成停滞

- **位置**：SKILL.md 步骤 11；CODING-STANDARDS §5.2；第二批设计记录 §3.4/Q6。
- **问题**：「每轮 P0/P1 严格递减」把「存量关闭」与「本轮新增」混在一个数里。
  上轮 2 项全部关闭、本轮新增 2 项时数量持平，会被判停滞；但收敛质量并未
  退化。复核认为该口径会制造假阴性。
- **裁决**：「上轮问题全部关闭，且本轮新增 P0/P1 不高于上轮新增」；两轮
  封顶不变；不满足即停止并交用户裁决。
- **改法**：SKILL.md 步骤 11 与 CODING-STANDARDS §5.2 同步改写；新增 P2
  仍记 PLAN 后续待办，不延长本轮。

### 2.4 页面关卡与三分口径的接缝

- **位置**：SKILL.md 矩阵「重构」行页面列=免；红线「原型未经审核不进入开发」。
- **问题**：三分口径已按改动性质判定，矩阵却对重构一律写「免」，规则自相
  矛盾；红线没有三分口径例外，纯样式调整也会被拦住。
- **裁决**：矩阵该格改「按三分口径」；红线补「按三分口径判定为免的除外」。
- **改法**：矩阵单元格与红线各一处；CODING-STANDARDS §5.5 补「按三分口径
  判定为免的页面调整跳过两关」。

### 2.5 复核整改档存在零评审路径

- **位置**：SKILL.md 矩阵「代码评审=免（由复审承担）」+「修复后复审=条件」。
- **问题**：两条组合后，条件不触发时该档既无首轮评审也无复审，可以零评审
  提交，与「未经代码评审不得提交」的红线冲突。
- **裁决**：该档复审改为必做，不再写「条件」。
- **改法**：矩阵「修复后复审」该格改「必」；代码评审仍由复审承担。

### 2.6 编码规范把 4.2 举成账本实例指错了对象

- **位置**：CODING-STANDARDS §5.1 账本行。
- **问题**：4.2 只有 §5、§6，没有账本与 §7；dry run 已确认。引用既不能
  证明账本格式，也会误导后来者照抄一个不存在的小节。
- **裁决**：只把 4.2 的 §5/§6 引成红清单与红运行实例；另引 4.1 §6.1–6.3
  的多轮红运行记录；账本规则本身指向 spec-first 模板，不举不存在的样本。
- **改法**：§5.1 该行重写，引用与结论一一对应。

### 2.7 description 尾词与正文不一致

- **位置**：SKILL.md frontmatter description 结尾。
- **问题**：正文已统一为「兑现关」，description 仍写「收敛判定」；同一份
  skill 出现两个关卡名，检索与外部引用都会失真。
- **裁决**：统一为「兑现关」。
- **改法**：description 一处替换。

### 2.8 双子代理与复审的边界不清

- **位置**：TRAE-code-review SKILL.md 开头；spec-first 步骤 11。
- **问题**：「结论必须经双子代理独立交叉验证」读起来像所有评审（含复审）
  都必须双代理，与复审「单代理、只查上轮关闭、不重审未触碰代码」冲突；
  也容易被理解为做过双代理即免复审。
- **裁决**：双子代理是首轮评审的执行形式；复审是另一道关卡，按 spec-first
  步骤 11 单独触发，不因做过双代理而免。
- **改法**：TRAE-code-review 开头补两句划界。

### 2.9 红态无允许值、守护用例无命名空间（dry run 真问题）

- **位置**：SKILL.md 账本模板；4.2 §5 与 `tests/` 实际用例名。
- **问题**：红态列没有允许值，自由文本无法判定填写是否合法；评审补充的
  守护用例没有独立位置，实际被塞进最后一个 AC 编号。dry run 发现
  4.2 §5 写「AC13 无独立用例」，`tests/` 却有 12 个 `test_ac13_*`；按前缀
  匹配会把语义错配判成对上，形成「账本看起来填了、实际没验证」的失效。
- **裁决**：红态允许值固定为 `红态` / `结构性红` / `无红态·特征测试` /
  `无红态·回归` / `手工留证`；评审补充的守护用例用独立命名空间
  `test_guard_*`，不得塞进最后一个 AC 编号；AC 无独立用例时不得使用其
  编号前缀；§5 清单须与实际用例名一致。
- **改法**：账本模板与步骤 7 同步；4.3 草案按该枚举回写（不在本次提交内）。

### 2.10 两处可判定性缺口

- **位置**：SKILL.md 档位说明；CODING-STANDARDS §5.1。
- **问题**：「事实核对」在轻档声明里反复出现但没有定义，无法判定是否完成；
  全关卡任务省略「裁剪」时，无法区分「无裁剪」与「漏写声明」。
- **裁决**：事实核对 = spec 名词与代码现状核对 + 相关既有用例跑绿；全关卡
  任务写「裁剪：无」，不得省略。
- **改法**：档位说明与 §5.1 各补一句；红线既有「裁剪声明缺失或与实际不符
  不得提交」保持不变。

## 3. 核对后不成立的疑虑

以下疑点经回文件核对后不成立，记录理由，避免后续重复提出：

1. **「账本并入 §4 会让轻档负担变重」**：不成立。§4 本来就是验收标准表，
   扩列不新增填写点；S 级还可压到三列。
2. **「缺陷修复档极简 spec 与『没有确认的 spec 不得编码』冲突」**：冲突
   来自旧红线例外写成「免 spec 的档位」；改为「『用户确认』为免的档位」后
   闭合。缺陷修复仍需落文件，只是不单独请求确认。
3. **「复审新口径会放行同等数量的新问题」**：不成立。硬条件仍是上轮全部
   关闭，新增只允许不高于上轮，且两轮封顶、不满足交用户裁决。
4. **「矩阵重构行改三分口径会强制重构出原型」**：不成立。三分口径第③类
   （纯文案/颜色/间距/图标）免；只有动结构、交互或用户可见业务信息才触发。
5. **「双子代理划界等于给复审豁免」**：不成立。划界只说明两者是不同关卡，
   复审仍按步骤 11 单独触发。
6. **「4.2 只是引错行号，改行号即可」**：不成立。4.2 没有账本与 §7，改
   行号仍证明不了规则，必须换引用对象。
7. **「红态枚举保留『手工留证』会让手工 AC 逃避自动测试」**：不成立。
   规则仍要求手工 AC 有可复核留证；枚举只是把既有做法命名为允许值，不新增
   豁免。

## 4. 复核结论

- 十条接缝全部有明确裁决与落点，无需新增关卡；改动集中在规则文本与两处
  引用修正。
- 最高风险是 2.9：编号前缀匹配会把语义错配判成对上，属于账本静默失效；
  已用独立命名空间与清单一致性要求封住。
- 残留：本次只改规则文本，不回改历史 spec；4.3 草案的账本结构在 Q1–Q5
  裁决后单独回写，不属于本次提交。
