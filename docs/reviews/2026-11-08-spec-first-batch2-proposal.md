## 3. 四块方案

### 3.1 三关合并为两关 + AC 账本

不压成一道关卡：自检必须在用户确认前，红态一致性必须在确认后，时点不可合并。合并的是**判定对象与载体**：

| 关卡 | 时点 | 判定内容 | 产物 |
|---|---|---|---|
| 契约关·第一动作 | spec 确认前 | AC 可检验、名词真实存在 | §4.1 账本「验证方式」列 |
| 契约关·第二动作 | 确认后、写实现前 | AC↔验证项双向无孤儿、红态与预期一致 | 账本「用例/红态」列 + §5 + §6 |
| 兑现关 | 全量回归后、评审前 | AC↔代码证据、§2 触点 grep | 账本「实现证据/收敛」列 + §7 |

账本固定为 spec §4.1 的六列表格（AC / 验证方式 / 用例留证 / 红态 / 实现证据 / 收敛）；§5 红测试清单、§6 红运行记录沿用 4.2 已跑通结构，§7 收敛结论为本批新增。历史 spec 不回改。

### 3.2 任务档位矩阵

五类加一类并存形态（缺陷修复）各自裁剪；「免」必须显式声明 `流程档位：<类型>；裁剪：<关卡清单>（原因）`，声明与实际不符按 P1 处理，安全加固档不可裁剪。重构以特征测试替代红态（改实现前先钉住当前对外行为，覆盖率不得低于重构前基线）。页面关卡按三分口径：①页面结构、交互流程、信息架构变化 → 全关卡；②新增或调整用户可见的业务信息（信息本身变化，不只是改措辞）→ 同样走全关卡；③纯文案、颜色、间距、图标等不动语义的调整 → 免原型与人工测试。

### 3.3 编码前 spec 独立评审

- 执行者：新会话独立代理，只读 spec 与必要代码，不做产品决策。
- 顺序：自检 → 独立评审 → 作者整改 → 用户确认（一次）。
- 产物：`docs/reviews/YYYY-MM-DD-plan-<任务号>-spec-review.md`，含 P0/P1/P2 问题表（行号证据）、「不成立/误报」区、结论（通过/有条件通过/退回）。
- 约束：P0/P1 修复或书面拒绝后才可请求确认；需用户拍板的并入确认包。

### 3.4 修复后复审

- 触发（任一）：首轮 P0；≥2 项 P1；修复触及安全边界；净改动 >100 行或 3 文件；改法与评审建议不一致。
- 形式：新会话独立代理，产物 `YYYY-MM-DD-v0.17.xx-<修复后短hash>-rereview.md`，只查上轮关闭与本轮新改动。
- 回归：每次代码修复跑一次全量；复审不改代码不重复跑。
- 防循环：最多 2 轮；P0/P1 严格递减，出现新 P0 或数量不降即停止交用户裁决；新增 P2 记入 PLAN 后续待办。

## 6. 成本与形式主义风险

- 成本：L/XL 与安全任务多一次独立评审、一次复审、账本三个填表点；S/M 仅多账本；纯文档与缺陷修复档减少 2-4 个关卡。
- 风险与对冲：账本勾选化 → 证据必须是测试名或 `文件:行号`；独立评审自说自话 → 强制新会话 + 「不成立/误报」区；复审重复首轮 → 限定关闭验证；矩阵成为豁免通道 → 声明前置且安全档不可裁剪。
