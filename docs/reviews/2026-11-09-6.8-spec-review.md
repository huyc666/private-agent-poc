## 不成立/误报

- **安全边界没有实际漏洞。** 没有新增写入面：`run_id` 由服务端生成（`chat.py:73`），`ChatRequest` 无 `run_id` 入参（`webdeps.py:75-78`）；`user_id` 在认证模式下来自 `request.state.user`（`chat.py:76-77`），`run_records` 不参与任何授权判定。取消状态不能绕过计量：`usage_records` 由回调独立落账（`usage.py:238-263`），run 状态不参与计量。全仓库无同名 `run_records` 表，不与既有表冲突。
- 「`stream_reply` 没有任何 run 级时间戳落点」成立：538-709 行内没有时间调用，唯一时钟是 `usage.record` 落账时的 `ts`。
- 「`duration_ms` 只覆盖单次模型调用」成立（`usage.py:224-253`）。
- 「`workflow_instances` 起止不覆盖普通 run」成立（1104-1105/1164/1195），只是行号需改。
- 「`run_id` 生成到进 `stream_reply` 之间有排队」成立（`chat.py:73` 对 114-153）。
- 「前端自然忽略多出的字段」成立：`web/index.html:454-465` 只读 `total_tokens`/`prompt_tokens`/`completion_tokens`。
- `agent.py:492-493` 指摘要缓存略偏（`_compact_cache` 实际写入在 495），但语义成立，不另计问题。
- 既有测试用子集断言（`test_usage_pricing.py:47-50`），`by_run` 新增键不会破坏现有断言。

## 零模型调用 run 的口径缺口

`total` 与 `by_run` 都取自 `usage_records`，两者不会互相对不上；加 LEFT JOIN 也不改变 by_run 的行集。真正的缺口在别处：

1. `run_records` 的行集大于 by_run。零调用 run（首 token 前取消、首调用前报错、会话删除中止）只存在于 `run_records`，本轮没有任何端点或 CLI 能查到它们。§2.2 说「需要时按 run_id 查 `run_usage`」，但 `run_usage` 是内部函数，只在 done 事件里被调用（`agent.py:706-708`），零调用 run 根本走不到 done，等于没有查询入口。
2. 反过来，`run_triggered` 的 run（`orchestration.py:1326-1374`）有 usage 行、会出现在 by_run，但按 Q3 永远 `wall_ms=NULL`。它和「历史未观测」「写失败」混在一起，运维会误判成 6.8 没生效。

建议在 §2.2 和 §9 加一段「口径边界」：明确 by_run 的统计单位是「有模型调用的 run」；`COUNT(run_records) >= len(by_run)`，差异为预期；NULL wall_ms 有三类来源（历史、写失败、run_triggered）；禁止拿 run_records 的条数做成功率/平均墙钟的分母。若需要看零调用行，本轮只能直查 `usage.db`，或加一个只读 `run_record(run_id)` 函数（不加端点）。
