## 2. Findings

### P0：删除后在途执行仍可写回，问题原样存在

- `server/main.py:567-570` 仍只在流开始前检查一次 tombstone。
- `server/main.py:711-722` 仍是顺序清理 messages/checkpoint/cache/pending/lease，没有取消在途执行或写代际校验。
- `server/agent.py:467-529` 仍可继续推进图、创建审批并在批准后 resume 危险操作。
- `server/main.py:594-605` 仍会在 `finally` 中把 assistant 内容追加到已删除会话。

因此 DELETE 返回成功后，仍可能出现新 checkpoint、新 pending 审批和新 assistant 消息。tombstone 只拒绝新请求，不能终止旧请求。清租约依赖下一拍心跳与下一个 SSE 事件，等待审批时不构成及时、可靠的执行边界。

必须补确定性并发测试：模型流中途删除、pending 后删除、删除与批准/工具执行竞争；验证 DELETE 后存储不再增长、审批不新建、危险工具不执行。

### P1：存量混合归属扩大访问权的问题未修复

`server/sessions.py:233-258` 仍按最早 user 消息确定 owner，`server/main.py:668-671` 还把该规则用于锁外快查。`tests/test_session_acl.py` 新增的混合作者用例将“最早作者获得整个会话”固化成预期，但没有验证混合/匿名历史 checkpoint 是否可安全授予该作者。

这不是单纯的快查/终判一致性修复：它会把原先因多作者而被拒绝的会话永久授予最早作者。无法证明单一 owner 的历史会话应隔离或只读，不应直接续用原 thread_id。

### P1：旧架构问题保持未闭环

- SSO 部门仍由 `server/auth.py:393-404` 从本地表重建，未与 HTTP 请求身份统一。
- 共享技能仍经 `server/tools_admin.py:44-50` 直接写入，未统一审批；高风险审批仍缺少发起/批准职责分离。

这些属于本轮显式范围外，但应继续保持开放状态，不能计入 v0.17.37 已修复项。

## 3. 本提交的有效改进
