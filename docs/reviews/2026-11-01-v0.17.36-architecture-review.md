# PAP v0.17.36 系统架构审核与整改建议

日期：2026-11-01

审核基线：master `2ec462f51b6fae6118fba3cd6fa3125c37d7b399`

审核范围：FastAPI 接入层、LangGraph 会话与审批链、身份与部门授权、知识库原文视图、插件与共享能力治理、持久化与部署配置。

本文供后续编程 Agent 制定整改方案和验收用例。除新增本报告外，本次审核未修改项目代码；工作区原有的 `README.md`、`docs/PLAN.md`、`tests/test_packsign.py` 修改不属于本次审核。

## 1. 总体结论

PAP 已具备较完整的私有化 Agent POC 骨架：Domain Pack 分层、执行侧鉴权、人工审批、代码沙箱、混合检索、用量计量和离线回归测试均已落地。

当前主要风险不在单个安全函数，而在跨层一致性：会话展示记录与模型上下文生命周期不一致、SSO 请求身份与工具执行身份不一致、文档原文渲染缺少统一输出安全边界、共享能力变更未统一经过管控与审计。

建议当前定位为“受控环境试点”。以下 P0/P1 问题关闭，并完成真实模型及目标部署环境验收前，不建议直接承载高敏数据或多租户生产流量。

## 3. P0：删除会话后复用 session_id 可接续旧模型上下文

### 证据

1. `server/main.py:620-626` 的会话删除端点只调用 `sessions.delete_session()`。
2. `server/sessions.py:139-149` 仅删除 `messages` 表中的展示记录，未处理 LangGraph checkpointer、`agent._compact_cache` 或会话租约。
3. `server/main.py:585-597` 使用 `messages` 中的用户记录推断会话归属；全部删除后，owners 为空，会被视为可创建的新会话。
4. `server/agent.py:453-460` 始终以客户端提供的 `session_id` 作为 LangGraph `thread_id`。因此同一 ID 被另一用户复用时，可能接续未删除的历史模型上下文。

### 影响

- 被删除会话的模型上下文可能被另一用户接续、推断或引出。
- 用户执行“删除”后，展示记录与模型记忆产生隐私语义不一致。
- 原用户删除后立即复用同一 ID，也可能得到并非全新会话的上下文。

### 修复建议

1. 新建独立的会话元数据/所有权表，至少包含 `session_id`、`owner_id`、创建时间、删除状态；归属判定不得仅依赖消息记录。
2. 新建会话使用服务端生成的不可预测 ID；已有客户端 ID 仅在所有权明确且未删除时允许复用。
3. 删除采用明确的 tombstone 或状态机，禁止已删除 ID 再次注册；删除策略需覆盖消息、checkpoint、压缩摘要缓存、未完成审批和租约。
4. 明确“逻辑删除”与“物理删除”的合规口径。若 checkpoint 无法可靠物理删除，至少永久封禁该 ID 并禁止恢复。
5. 管理员跨用户接入会话时，也应明确是否允许接管写操作，避免 admin 写入后改变普通用户的归属推断。

### 必补验收

- 用户 A 产生真实 LangGraph 历史并删除，用户 B 使用同一 ID 发消息：必须拒绝，且模型无法获得 A 的上下文。
- 用户 A 删除后复用自己的 ID：按产品语义拒绝或创建全新上下文，不得接续旧历史。
- 删除分别覆盖 MemorySaver 和 PostgresSaver、进程内摘要缓存、存在租约/待审批的场景。
- 重启后已删除 ID 仍不可复用；两个用户并发争抢同一新 ID 时只能有一个明确所有者。

## 4. P0：知识库 Word 原文视图存在存储型 XSS 路径

### 证据

1. `server/main.py:1122-1125` 将 `kb_parsers.parse_document()` 返回的文本直接拼接进 `<p>` 和 `data-a` 属性，未调用 `_esc()`。
2. `server/main.py:1126-1159` 将 `doc`、逻辑路径和正文组合进 HTML；`server/main.py:1153` 将 Mammoth 转换结果直接写入 `innerHTML`，未使用统一白名单消毒。
3. `web/index.html:246-247` 与 `web/console.html:443-444` 将 Bearer 凭据存入 localStorage。若同源脚本执行，凭据及同源 API 数据面会扩大影响。
4. `docs/SECURITY.md:107` 中“无 innerHTML 注入点”的表述与服务端知识库原文视图不符，应同步修正。

### 影响

- 恶意或被污染的 Word 文档可在有权限用户打开出处原文时形成存储型 XSS。
- 同源脚本可能读取浏览器凭据、调用管理接口或读取用户可访问的知识内容。

### 修复建议

1. 所有服务端拼接的标题、正文和属性值统一做上下文对应的 HTML 转义，优先改为 DOM/模板的安全文本绑定。
2. Mammoth 输出必须经过成熟的 HTML sanitizer 白名单处理；只允许排版所需标签和安全属性，禁止脚本、事件属性、危险 URL、iframe/object 等主动内容。
3. 对原文查看页设置严格 CSP，至少禁用内联脚本并限制脚本、连接、frame 和 object 来源；同步评估 `X-Frame-Options`/`frame-ancestors`。
4. 短期禁止 Bearer 令牌长期落 localStorage；浏览器登录优先迁移到 `HttpOnly + Secure + SameSite` Cookie，并配套 CSRF 防护。
5. 不依赖“文档来自可信员工”作为 XSS 防线，文档内容和转换器输出均按不可信输入处理。

### 必补验收

- Word 正文包含 HTML 标签、事件属性、引号和实体时，响应中的 fallback 只能显示文本，不能形成可执行节点。
- 构造 Mammoth 富文本输出，验证消毒后的白名单标签保留，脚本、事件属性、危险链接和嵌入内容全部移除。
- 恶意文件名不能突破 title、正文或 URL 属性上下文。
- 浏览器端验证恶意文档打开后无脚本执行，且无法读取登录凭据。

## 5. P1：SSO 部门身份在 HTTP 与 Agent 工具执行层不一致

### 证据

1. `server/auth.py:440-444` 的 `resolve_identity()` 会让受信 SSO 部门头覆盖本地部门。
2. `server/main.py:1080-1089` 的知识库原文端点使用请求身份中的部门，能采用 SSO 新值。
3. `server/agent.py:438-440` 只把 `user_id/session_id/run_id` 写入 contextvars，没有传递本次请求的完整身份声明。
4. `server/auth.py:393-404` 的 `current_department()` 重新从本地用户表读取部门；`server/custom_tools.py:440-467` 据此执行包级部门授权。

### 影响

- 调岗后，原文端点可能已经按新部门拒绝，而检索工具仍按本地旧部门放行。
- 同一用户对同一知识库可能得到不同授权结果，破坏最小权限及撤权及时性。

### 修复建议

1. 在认证中间件生成不可变的请求级 `Identity(username, role, department, auth_source)`，传递至 Agent、orchestrator、worker 和工具执行层。
2. 执行层禁止通过用户名重新查询并重建本次请求身份；角色和部门均以同一份认证结果为准。
3. 保留独立的管理员用户管理接口，但不得让本地缓存覆盖已认证的 SSO 请求声明。
4. 多 Agent 使用 contextvars 时验证异步任务复制语义，禁止跨请求共享可变身份对象。

### 必补验收

- 本地部门为 HR、SSO 部门为 Finance 时，提示词、工具执行、原文定位和用量口径全部只采用 Finance。
- 用户从 HR 调至 Finance 后，HR 工具与原文立即不可访问，无需等待本地表同步。
- SSO 部门为空时按明确的 fail-closed 规则处理；对比 SSO、Bearer、开放模式三类身份路径。
- 并发请求不同部门身份时不得串用角色或部门。

## 6. P1：共享能力治理、职责分离与执行审计未统一收口

### 证据

1. `server/tools_admin.py:326-332` 将 `create_skill` 暴露给主 Agent；`server/skills.py:266-309` 允许 approver/admin 直接写通用技能，未经过 `approval.require_approval()`。
2. 通用技能会进入共享提示词与后续用户会话，影响面并不限于创建者，不能简单按普通个人文件处理。
3. `server/tools_admin.py:244-273` 的包签名、创建和删除经审批门，但执行结果没有统一写入 `audit_log`；当前统一审计主要覆盖决议本身。
4. `server/approval.py:160-179` 只限制 approver/admin 角色，未阻止其批准本人创建的审批单。
5. `server/audit.py:62-84` 审计写失败仅告警继续；作为 POC 可用性选择可以接受，但高保证审计场景需要显式风险和补偿机制。

### 影响

- 部分共享提示词/能力变更绕过统一审批治理。
- 审批单能回答“谁批准”，但不一定能完整回答“实际执行了什么、是否成功、结果是什么”。
- 高风险操作可能由同一 approver 发起并批准，职责分离不充分。

### 修复建议

1. 建立统一 Command/Policy 应用服务层，在唯一入口完成身份校验、参数校验、审批、执行和审计，避免 HTTP 与 Agent 工具分别实现治理。
2. 对共享技能、通用工具、包、签名和系统提示词变更定义明确的风险等级与审批策略。
3. 高风险操作禁止发起人批准本人单据；管理员紧急通道单独授权并加强审计。
4. 审计记录至少包含 request/run/approval ID、操作者、发起人、批准人、动作、目标、前后摘要、开始/结束时间、结果和失败类别。
5. 明确审计不可用时的策略：普通查询可降级，高危写操作建议 fail-closed 或进入可靠外发队列并告警。

### 必补验收

- 普通用户不能发布共享技能；approver/admin 的共享技能变更按风险策略审批。
- approver 批准本人创建的高风险单据必须拒绝。
- 包创建/签名/启停/删除均留下决议与执行结果，失败也留痕且不含密钥。
- HTTP 管理端点与对话工具执行同一动作时，授权与审计语义一致。

## 7. P1：当前不具备真正的跨机水平扩展能力

### 证据

1. `server/sessions.py:11-13` 明确 SQLite 只适合同机多进程；用户、审批、审计和会话锁也采用相同存储模式。
2. `server/session_lock.py:1-13` 的跨进程互斥以共享 STATE_DB 为前提，不能直接跨机使用 SQLite 网络共享。
3. `server/agent.py:296-297` 的上下文摘要缓存是进程内字典，多副本间摘要状态不一致。
4. 当前只有 LangGraph checkpointer 提供 Postgres 后端；`docs/PLAN.md` 的 STATE_DB Postgres 化仍未完成。

### 影响

- 现有生产部署应限定为单 Agent 副本，不能把单机压测直接解释为近线性扩容能力。
- 多副本时可能出现会话锁失效、摘要反复计算或上下文表现不一致。

### 修复建议

1. 先明确发布拓扑：Linux + 单 Agent + Postgres checkpointer + 独立沙箱；多副本暂不作为已交付能力。
2. 用 Repository 接口统一 sessions/auth/approvals/audit/usage/locks 的持久化访问，提供 PostgreSQL 实现与版本化迁移。
3. 锁采用数据库原子租约或成熟协调组件，使用单调时间语义、 fencing token，验证停摆与接管。
4. 将压缩摘要按会话版本持久化或保证可确定性重建；删除时遵循同一生命周期。
5. 完成统一状态存储后再增加副本，不以增加 uvicorn worker 代替架构迁移。

### 必补验收

- 两个 Agent 副本共享 Postgres 时，同会话严格串行，审批可跨副本决议并准确恢复。
- 杀死持锁副本、暂停心跳、时钟偏移和数据库短暂不可用时，不发生双写或错误接管。
- 重启、故障转移后模型上下文、展示记录、摘要和删除状态一致。
- 形成有数据量与 SLO 的真实模型压测报告，区分应用吞吐、模型吞吐和单会话排队。

## 8. P2：依赖、镜像与默认数据出口需生产化

### 证据

1. `requirements.txt` 使用宽松下界/范围约束，没有锁定完整传递依赖；`sandbox/Dockerfile` 也未锁定 FastAPI/uvicorn 版本。
2. `docker/docker-compose.yml` 使用 `vllm/vllm-openai:latest`，`docker/docker-compose.gateway.yml` 使用 `ghcr.io/berriai/litellm:main-stable`。
3. `gateway/litellm_config.yaml:33-43` 默认保留 DeepSeek fallback；生产需要依赖文档要求人工删除，而非配置层默认拒绝外发。
4. `server/agent.py:175-193` 依赖 langchain-openai 私有转换方法，版本漂移可能破坏 reasoning 透传。

### 修复建议

- 生成完整依赖 lock/constraints，镜像按不可变版本或 digest 固定；CI 执行依赖与镜像漏洞扫描、构建及升级回归。
- 私有部署默认仅允许内部模型端点，云 fallback 必须显式启用、单独审批并记录数据出口。
- 将真实 Qwen/vLLM + LiteLLM + hermes 工具解析作为发布门禁，覆盖普通回答、工具调用、长上下文、reasoning 和主备切换。
- 跟进 `create_react_agent` 弃用迁移，避免等待 LangGraph V2 破坏性升级。

## 9. 推荐整改顺序

1. **安全阻断项**：P0 会话生命周期与知识库 XSS；先补攻击回归，再修改实现。
2. **统一信任上下文**：修复 SSO 部门口径，收敛请求身份传递与执行侧授权。
3. **统一管控面**：共享能力审批、发起/批准职责分离、执行结果审计。
4. **生产数据面**：STATE_DB/USAGE_DB Repository 与 PostgreSQL 化、删除/锁/摘要一致性、双副本故障演练。
5. **交付基线**：依赖和镜像锁定、真实模型与 Docker 验收、数据出口默认关闭。

建议将上述每项拆成独立 spec，继续沿用项目现有“攻击/失败场景先行、放行与拒绝成对覆盖、修复后独立复验”的方式。整改优先级应先于通用工作流、定时触发和更多企业连接器。
