# PAP v0.17.37 系统架构复验报告

日期：2026-11-01

审核对象：提交基线 `2ec462f51b6fae6118fba3cd6fa3125c37d7b399` 之上的当前工作区修改。审核期间 Git 历史未产生新提交，因此本报告中的 v0.17.37 指工作区版本，而非已落盘的 Git commit。

参考：`docs/reviews/2026-11-01-v0.17.36-architecture-review.md`、`docs/specs/security-hardening-v0.17.37.md`。

## 1. 复验结论

本轮对知识库原文 XSS 的输出转义、CSP、Mammoth 消毒及浏览器 Cookie 迁移做了较完整的静态修复；tombstone 也阻断了删除后的新请求复用。但“删除是不可逆终局”尚未覆盖在途请求，删除完成后仍可能新增审批、重建 checkpoint 并写回 assistant 消息。因此 P0-1 不能判定通过，本轮整体结论为 **有条件退回整改**。

旧 P0-2 的主要注入路径基本闭环，仍须补真实浏览器 E2E 和消毒器对抗测试。上一轮 SSO 身份一致性、共享能力审批与职责分离问题保持原状，不属于本轮改动范围，继续作为 P1 遗留项。

## 2. Findings（按严重程度）

### P0：删除与在途 chat 并发时，终局语义仍可被打破

证据链：

1. `server/main.py:567-570` 只在取得租约后、首次写 user 消息前检查一次 tombstone；后续模型执行、审批创建和 assistant 落库前均无终局校验。
2. `server/main.py:708-719` 的删除编排依次清 messages、checkpoint、pending 审批和租约，没有与在途请求建立取消/完成协议，也没有删除代际（generation）或 fencing token。
3. `server/agent.py:467-525` 在删除后仍可继续图执行、写 checkpoint，并于 `server/agent.py:522` 新建 pending 审批。删除在 `:718` 扫描 pending 之前已经完成，无法清除这种“删除后新建”的记录。
4. `server/main.py:579-584` 仅在流产生下一个事件时观察 `lease.lost`；默认心跳 15 秒才更新该标志。等待审批期间没有事件驱动该检查，批准后又可在 `server/agent.py:527-529` 执行危险操作。
5. `server/main.py:594-605` 的 `finally` 会无条件把已收集的 assistant 内容追加回 messages；即使未来仅靠 `lease.lost` 中止，删除后也仍能写回展示数据。

影响：DELETE 已返回成功且 tombstone 已存在，但存储面并未保持删除态；已删除会话可能出现新消息、checkpoint 和待审批单，审批批准后还可能执行危险操作。管理员 history 的全局视图可直接看到这些“删除后复活”的消息。新请求复用被 tombstone 拒绝，不能替代对在途写入的终止保证。

整改建议：

- 将删除建模为会话状态机/代际切换，而非六次独立清理。所有消息、审批、checkpoint 写入都必须绑定创建时的代际，并在写提交时再次验证“活跃且代际未变”；旧代际写入 fail-closed。
- 删除应注册取消信号并等待/确认在途执行已停止，或采用可证明旧代际写入永远不会提交的事务协议。`lease.lost` 只能是协作提示，不能作为唯一安全边界。
- `approval.create_approval`、危险工具实际执行点及 assistant 持久化点均需检查取消/代际；仅拒绝新 chat 不足。
- 至少补三个确定性并发测试：删除发生在模型流中途、删除发生在 pending 审批后、删除与批准/工具执行竞争。断言 DELETE 返回后 messages/checkpoint 不再增加、无新 pending、危险工具不执行。

现有 `tests/test_session_lifecycle.py:127-160` 只验证“预先存在的审批”和“事后人为放入的租约”，没有驱动真实在途 chat，因此无法覆盖上述竞态。

### P1：存量混合归属会话的回填规则可能永久扩大访问权限

`server/sessions.py:233-258` 将无 meta 的存量会话归属固定为“最早一条 user 消息的 user_id”，而 `server/main.py:632-636`、`:684-690` 对该 owner 以及 `anonymous` 直接宽恕，没有验证消息集合是否与单一 owner 相容。

典型反例：历史匿名会话的模型上下文曾被用户 Alice 接续，之后 Alice 删除该会话，最早 user 消息仍为 anonymous。升级后 Bob 的首次访问即可回填 anonymous 并继续同一 `thread_id` 的 checkpoint；或者 Alice/Bob 的混合消息被永久归给首个用户，绕过旧实现 `owners <= {本人, anonymous}` 的拒绝规则。

这不是普通单 owner 存量会话的问题，而是“由消息推断不可信历史所有权”的边界。建议：

- 回填时检查全部相关消息身份，而不是取首条；混合且无法证明单一 owner 的会话进入 `legacy_quarantined`/只读管理员治理状态，禁止普通用户续写。
- 对 anonymous 存量会话，只有在不存在已认证用户消息、且模型上下文能证明同属匿名域时才允许认领；否则新开会话，不复用旧 checkpoint。
- 增加 anonymous→Alice→删除→Bob 升级访问，以及 Alice/Bob 混合消息的迁移测试。

### P1：SSO 请求身份与 Agent/工具执行身份仍不一致

`server/auth.py:393-404` 仍通过 `usage.current_user` 回查本地用户表，`server/agent.py:140-141` 和 `server/custom_tools.py:462` 继续采用该结果。SSO 部门头虽然会进入 HTTP `request.state.user`，但未传递到 Agent/工具执行层。

上一轮报告的撤权即时性和最小权限问题未修复。应将不可变的请求级 Identity（username/role/department/auth_source）显式传入执行链，禁止执行层用用户名重建身份，并补并发及 SSO/本地部门冲突测试。

### P1：共享技能发布与审批、职责分离仍未统一

`server/tools_admin.py:44-50` 直接调用 `server/skills.py:266-309`；approver/admin 写共享技能时不经过 `approval.require_approval()`。`server/approval.py:160-179` 也未禁止 approver 批准本人创建的高风险审批单。

共享技能会进入其他用户后续会话的提示/能力面，仍应纳入统一 Command/Policy 入口，并记录实际执行结果；高风险操作需落实发起人与批准人分离。

### P2：Cookie 的生产安全与交付验证仍有缺口

- `server/config.py:228-231` 默认 `AUTH_COOKIE_SECURE=false`。本地 HTTP 可理解，但生产部署应使用安全默认或启动时校验：认证开启且非明确开发模式时，缺少 Secure/HTTPS 应拒绝启动或显著阻断上线。
- `server/main.py:197` 仍在登录 JSON 响应体返回 token。浏览器代码已不保存它，但响应对同源脚本和浏览器开发工具可见，不能表述为“XSS 后凭据完全不可读”。建议浏览器与程序化登录分端点/分响应模式，浏览器响应不返回 token。
- `tests/test_kb_source_xss.py` 主要检查字符串与 sanitizer 单元行为，尚无浏览器 DOM/脚本执行断言。本轮明确的 AC11 人工 E2E 仍须执行并留证。
- `server/html_sanitize.py` 自研解析器应增加畸形标签、嵌套未知/主动内容、命名及数字实体 URL、SVG data URI、注释/声明等对抗用例；生产前优先引入维护中的成熟 sanitizer，避免仅依赖自编白名单实现。

## 3. 已确认闭环或明显改善

- 新会话 ID 改为 `secrets.token_hex(8)`；活跃新会话通过 `session_meta` 原子注册，tombstone 可跨连接拒绝新请求复用。
- 静态删除路径已覆盖 messages、checkpointer 接口、compact cache、预存 pending 审批和租约；但受 Finding P0 限制，不能视为完整生命周期闭环。
- admin 接入已有 meta 的会话不再通过消息集合漂移 owner。
- docx 标题、逻辑路径、fallback 正文和锚点已转义；Mammoth 输出经服务端白名单处理；原文页设置 nonce CSP 与 X-Frame-Options。
- pat- 浏览器登录改用 HttpOnly SameSite=Lax Cookie，非 GET/HEAD/OPTIONS 请求具备 X-Requested-With 校验；Bearer 路径保留。

## 4. 测试结果与边界

- 定向回归：`90 passed in 41.49s`，覆盖新增 lifecycle/cookie/XSS 及既有 session ACL、approval、auth 测试。
- 全量回归：`648 passed, 18 skipped, 1 warning in 109.14s`。
- 唯一 warning 仍为 `create_react_agent` 弃用迁移。
- 未实测真实 PostgreSQL checkpointer、真实模型、Docker/多副本及浏览器恶意文档攻击链。
- 新增测试证明的是顺序执行和预置状态，不证明删除与在途执行的并发安全；全量通过不能消除 P0。
