# Spec — 6.6 run 健康度（时长与状态）

## 1. 背景与目标

出处：docs/PLAN.md「P6 运营与架构补齐」6.6 行（优先级 6，规模 S，来源 ④）。

现状：usage_records 只记每次模型调用的 token/金额（6.5），回答不了「这次 run
跑了多久、有没有调用失败」。目标：明细行补单次调用时长与成败状态，
by_run 视图输出单次 run 的总时长/调用次数/失败次数；老库自动补列不丢数据；
计量失败不阻塞主链路红线保持。

## 2. 需求分析与约束条件澄清

**功能边界**

- 做：
  - usage_records 增 `duration_ms`（INTEGER，单次模型调用耗时毫秒）与
    `status`（TEXT，'ok'/'error'）两列，启动时 ALTER 自动迁移老库（幂等，
    历史行按 0/'ok' 计入）
  - UsageCallback 补 `on_llm_start` 计时（按 LangChain 回调 run_id 配对，
    monotonic 时钟）、`on_llm_end` 计算时长落账、`on_llm_error` 记失败行
  - by_run 视图（summary）与 run_usage 输出 `duration_ms`（各次调用之和）与
    `failed_calls`（status='error' 计数）
- 不做：
  - session_usage / summary 其他视图加时长（会话是多次 run 累计，时长求和
    无运营意义；需要时 6.7 归因后按实例算）
  - run 墙钟总时长（含工具执行/编排间隙）——计时挂在 LLM 回调上，天然只覆盖
    模型调用段（PLAN 原文即「回调补 on_llm_start 计时」）
  - 失败重试统计、超时分类、告警推送

**约束（沿用既有约定）**

- 计量红线：回调内任何异常吞掉不阻塞主链路（现状 on_llm_end 即如此，
  on_llm_start/on_llm_error 同样处理）；错误不回显原始异常
- 客户端中断的调用不落账（回调不触发，与现状一致，健康度不虚构数据）
- 失败行模型名取当前配置模型（on_llm_error 拿不到响应元数据，近似归属）
- 空 usage 的正常调用仍跳过不落账（现状 tt<=0 跳过仅对 status='ok' 生效；
  error 行必须落库，否则失败无法计数）
- 迁移幂等：ALTER 前查表结构，列已存在跳过（对齐 6.5 增列迁移模式）

**待澄清问题（已答复）**

1. by_run「总时长」口径：**各次模型调用时长之和**（用户 2026-10-17 确认；
   不含工具执行与编排间隙，PLAN 原文「回调补 on_llm_start 计时」即此口径）。
   run 墙钟时长（口径 B）单列为 PLAN 6.8（优先级 23，依赖 6.6），本任务不实现。

## 3. 关键技术与选型决策

| 决策点 | 候选方案 | 选定 | 取舍理由 |
|---|---|---|---|
| 计时配对 | contextvar 存开始时间 / 回调 run_id 字典配对 | run_id → monotonic 起始时刻字典（_lock 保护） | 多 Agent worker 并行时同一进程内有并发模型调用，contextvar 单值会互相覆盖；LangChain 每次调用的 start/end/error 共享同一 run_id，天然配对键；end/error 后弹出条目，无泄漏 |
| 时钟 | time.time() / time.monotonic() | monotonic（时长）+ 现有 time.time()（ts 落账不变） | 时长只关心差值，monotonic 不受系统跳变影响 |
| 失败行落账 | 只在内存计数 / 落 status='error' 明细行 | 落明细行（token 0、金额 0） | 失败次数可从明细聚合；与「计量即明细」的既有模型一致；6.7 归因后可按实例算失败成本 |
| duration 语义 | 每行单调用耗时 / 查询时算 | 每行单调用耗时，视图 SUM | 明细自含，聚合零成本；对齐 PLAN「usage_records 增 duration_ms 列」 |
| run_usage 是否带健康度 | 仅 by_run 加 / run_usage 同步加 | 两者都加（同列） | run_usage 本就是「单次 run 合计」，缺时长/失败数反而不完整；session_usage 不加（见边界） |

沿用：usage._ensure_schema 迁移模式；record() 签名向后兼容（新参带默认值，
6.5 既有调用与用例不受影响）；tests/conftest.py 离线隔离体系。

## 4. 验收标准

| # | 标准（Given/When/Then） | 验证方式 |
|---|---|---|
| AC1 | Given record 以 status='error' 落账（token 空），Then 明细行落库且 token/金额为 0、status 为 error；Given 默认参数调用（既有代码路径），Then status='ok'、duration_ms=0，空 usage 仍跳过（向后兼容） | 单测 |
| AC2 | Given 回调 on_llm_start(run_id=x) 后 on_llm_end(run_id=x)，Then 该次落账 duration_ms>0、status='ok'；Given 只有 on_llm_end 无配对 start，Then duration_ms=0 且不报错 | 单测（配对与容错路径） |
| AC3 | Given 回调 on_llm_error(run_id=y)（此前有 start），Then 落 status='error' 行（token/金额 0，duration 为已计时长），run_usage 的 failed_calls=1；并行 worker 的 run_id 互不串扰 | 单测（失败路径） |
| AC4 | Given 混合 ok/error 明细，When 查询 by_run 与 run_usage，Then duration_ms = 各行之和、failed_calls = error 行数，token/金额聚合不受影响 | 单测 |
| AC5 | Given 无健康度列的老库已有历史记录，When 启动迁移（重复执行），Then 列补齐、历史行 duration_ms=0/status='ok'、token/金额不丢、幂等不报错 | 单测（迁移） |
| AC6 | Given 回调 handler 内抛异常（response 非法等），Then 异常被吞、不外泄、不阻塞调用方 | 单测（红线） |

安全/拒绝路径：AC3（失败可观测）、AC6（异常吞掉不回显原始错误）。
