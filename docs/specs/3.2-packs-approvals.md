# Spec — 3.2 包与审批面板

## 1. 背景与目标

PLAN 3.2（序号 13，批次三收官项，依赖 3.1 已交付）：管理控制台补齐「包与审批」运营面板——包列表/启停、审批单列表/页面决议，把现有能力收口到 Web 页面，交非技术人员运营。出处：docs/PLAN.md P3 管理控制台行「包列表/启停、审批单列表/决议（收口现有端点）；审批操作记审计」。

现状盘点（调查结论）：
- 审批能力已完整：`GET /api/approvals`（main.py L1083，user 只查自己发起的、approver/admin 查全部）+ `POST /api/approve`（L1135，仅 admin/approver 可决 pending，6.3 已落审计）；审批是全局池（任何 approver/admin 可决任何 pending 单，decided_by 记决策人）
- 包管理函数层已有、HTTP 层缺失：`list_packs()`（packs.py L353，全量管理视图含 status/enabled/platform/tools/skills/RBAC 字段）、`disable_pack(name)`（L374）/`enable_pack(name)`（L389）——**内存态**（`_disabled` 集合，重启恢复；持久禁用走 ENABLED_PACKS 环境白名单）；平台包不可禁用；status≠ok 不可启用；无 CLI 无端点
- console 现状：`me.role !== 'admin'` 即拒绝视图（console.html L440），user/approver 全部不可用；已有页签机制（.ctab onclick 切换 active，L514）与双视图（用户与 Key 管理/审计日志）

## 2. 需求分析与约束条件澄清

### 功能边界

做：
- **审批面板**（console 新页签）：审批单列表（工具名/参数摘要/状态/发起人/发起时间/决策人/决策时间）；pending 单提供「批准/拒绝」操作；全部状态历史同面板可查（Q4 双通道：另在审计页签查决议日志）
- **包管理面板**（console 新页签）：包全量列表（name/version/description/status/enabled/platform/工具数/技能数/trust）；领域包提供「启用/停用」操作；平台包标注不可停用
- **启停持久化（Q2 已决策）**：禁用名单落 STATE_DB（新表 `disabled_packs`），重启不丢；ENABLED_PACKS 白名单保持部署层语义（两者都通过才启用：`is_enabled = _env_enabled and not in _disabled`，优先级不变）
- console 准入改造（Q1 已决策）：按角色渲染页签——admin 全部四页签；approver 仅「审批」页签；user 仍拒绝视图
- 新增 HTTP 端点：包列表 + 包启停（admin 专属）；审批决议与列表端点**已存在，不新增**（前端直接调 /api/approvals、/api/approve）
- 审批决议已在 6.3 落审计（审批通过/审批驳回），无需新接触点；包启停为新管理动作，接 `_audit`（沿用 3.1 七端点同款 print+audit.log 模式）

不做：
- 包的创建/编辑/删除（仅启停，Q3 已决策；导入已有独立端点不在本面板范围）
- 审批流的配置（谁能审批、审批超时时长等不变）
- 聊天页既有审批卡片/记录面板不动（用户发起侧视角保留）
- 多进程/多副本的禁用名单实时同步（单进程 POC；跨机是 6.4 范围）

### 约束

- 宪法 §1 fail-closed：包启停端点复用 `_admin_guard`（未登录 401/开放模式 400/非 admin 403，与 3.1 七端点同构）；前端隐藏入口只是体验层
- 宪法 §2：approve 请求与审批记录不含明文 Key；args（工具参数）可能含敏感内容——列表渲染时前端截断展示，服务端原样返回（审批本身需要看参数才能决策）
- 宪法 §4：审批列表可见性沿用现有口径（user=仅自己发起，approver/admin=全部），不在本项改动
- 宪法 §6 POC 取舍：启停改为 STATE_DB 持久化（Q2 决策），但单进程口径——不做多副本实时同步（6.4 范围）
- 宪法 §7：README 版本记录只写功能；push 由用户操作

### 待澄清问题（Q1-Q4，已全部决策回写）

- **Q1 审批面板角色入口** → 已决策：**按角色渲染页签**——admin 全部四页签（用户/审计/包管理/审批），approver 仅「审批」页签，user 仍拒绝视图
- **Q2 包启停持久化** → 已决策：**STATE_DB 持久化**（新表 `disabled_packs`，重启不丢；ENABLED_PACKS 白名单保持部署层语义不变）
- **Q3 包面板操作范围** → 已决策：**仅启停**（PLAN 原文口径；列表展示全字段满足查看需求）
- **Q4 审批历史口径** → 已决策：**双通道展示**（审批面板展示全部状态历史 + 审计页签决议日志，不新增导出）

## 3. 关键技术与选型决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 包列表/启停端点 | `GET /api/admin/packs`、`POST /api/admin/packs/{name}/(enable\|disable)` | 沿用 3.1 的 /api/admin/* 命名与 _admin_guard；enable/disable 对称两个子路径（对齐 packs.enable_pack/disable_pack 函数语义），不用单端点+布尔体（操作意图在 URL 上更可审计） |
| 启停实现 | packs 持久化改造（Q2）：`_disabled` 集合改为**启动时从 STATE_DB 加载**，`disable_pack`/`enable_pack` 保持签名与全部校验、内部改为写库（新表 `disabled_packs(name PRIMARY KEY)`，参考 audit.py 的 `_connect` 独立连接模式防循环依赖）；返回文案去掉「重启后恢复」改为「已持久化，重启不丢」 | 用户决策优先于我的内存态推荐；函数校验逻辑（存在性/平台包/白名单/status）原样保留，端点零业务逻辑 |
| 页签接入 | console.html 新增 view-packs、view-approvals 两个 view + .ctab 按角色显隐 | 复用现有 .ctab/.view 机制（6.3 页签先例）；角色显隐在 L440 守卫处改逻辑 |
| approver 准入 | 守卫改为：admin 全页签 / approver 仅审批页签 / user 拒绝视图 | Q1 建议；服务端防线不变（/api/admin/* 仍 admin-only，/api/approve 已有角色校验），前端只是视图层分配 |
| 审批面板数据 | 直接调既有 GET /api/approvals + POST /api/approve | 「收口现有端点」原则；零新后端改动 |
| 启停后生效 | 沿用 packs 现有挂载链（_disabled 过滤 → 工具/技能/提示词即时移除） | 无需额外刷新机制 |
| 审计 | 包启停两动作走 `_audit(operator, "停用包"/"启用包", name, role)` | 3.1 同款；审批决议已接审计不动 |

## 4. 验收标准

- **AC1**：admin 在 console 可见四页签；打开「包管理」页签看到全量包列表（含平台包与领域包，字段完整：版本/描述/状态/启用位/工具与技能计数/allowed_roles）
- **AC2**：admin 停用一个已启用领域包 → 列表即时变「已停用」；该包工具从后续会话工具清单消失（挂载链生效）；再启用恢复；**停用后重启进程（或单测模拟重新加载）仍为停用**（STATE_DB 持久化，Q2）
- **AC3**：平台包不提供停用操作（按钮禁用或隐藏，文案说明不可停用）；status≠ok 的包不提供启用操作
- **AC4**：包启停写审计——「停用包/启用包」可在审计页签查到 who/when/what
- **AC5**：approver 登录 console 仅见「审批」页签；user 登录 console 仍见拒绝视图（口径与现状一致）
- **AC6**：审批面板展示全部审批单（工具名/参数摘要/状态/发起人/时间），pending 单可「批准/拒绝」；决议后状态即时更新
- **AC7**：approver 在页面完成一次决议（PLAN 主验收）——批准一个 pending 单后对应会话继续执行（沿用现有 resume 链路），审计与审批历史均可查（who/when/what）
- **AC8（拒绝路径）**：非 admin 调 `/api/admin/packs*` 三端点分别得到 401（未登录）/403（user/approver）/400（开放模式）；user 调 POST /api/approve 得 403（沿用现状）
- **AC9**：前端按角色渲染——approver 无法看到用户/审计/包管理页签；切换页签懒加载与现有 view-audit 一致

验证方式：AC1-AC3 手工实测（页面操作）；AC4-AC7 页面操作 + 审计页签/审批历史交叉核对；AC8-AC9 单测（client_factory 体系，test_acN_* 命名）+ 手工抽查。
