# Spec — 5.1 通用多角色编排引擎

状态：**已确认（八项裁决已落定，进入实现；实现完成后随代码一并入库）**
目标版本：v0.17.44（基线 v0.17.43）
出处：docs/PLAN.md 执行序号 14（批次四首项，规模 L，无前置依赖）。

PLAN 原文验收口径：「①用自定义角色搭建一个调研编排，结果与现
`orchestrate_subtasks` 等效；②再搭一个非调研类流程（如「审核-修订-复核」
三角色）跑通，证明角色不限领域。」

## 一、背景与目标

### 1.1 现状核实：`orchestrate_subtasks` 的实际能力边界

基线 v0.17.43，逐行核实（行号为当前仓库状态）：

- **入口**：`server/tools_admin.py:327-341` 的 `orchestrate_subtasks(task)`，
  作为内置工具注册（`tools_admin.py:417-418`），所有角色可用，**无审批门**。
- **编排结构**：`server/multi_agent.py:139-148` 固定三节点
  `plan → worker×N → aggregate`；`plan` 用一次 LLM 把任务拆成 2~4 条**纯文本
  子任务**（`:50-60`、`:76-90`），`_route_workers` 用 LangGraph `Send`
  并行扇出（`:103-108`），`aggregate` 再用一次 LLM 汇总（`:129-136`）。
- **角色模型**：**没有**。所有 worker 共用同一份 `_WORKER_PROMPT`
  （`:62-66`），只有"拆解者/执行者/汇总者"三个硬编码身份；角色名称、
  职责提示词、工具子集、串并行方式、上下文传递规则均不可配置。
- **工具边界**：worker 工具集来自 `tools_admin.py:298-324` 的
  `_worker_tools()`——`read_text_file` / `list_uploaded_docs` /
  `save_output_file` + **全量** `STATE.pack_tools` + `get_city_weather`。
  排除删文件、建工具、跑沙箱等危险能力，靠"架构层只给安全工具"隔离，
  不靠 prompt 约束（`multi_agent.py:13-15` 注释）。
- **执行形态**：只有"并行扇出 + 单次汇总"，没有串行步骤、没有阶段组合、
  没有上游输出选择性传递；worker 上限 4、单 worker 最多 4 轮工具调用
  （`:18`、`:32-33`）。
- **身份传递**：实际是**隐式**的——`stream_reply` 在
  `server/agent.py:549-556` 设置 `usage.current_user/current_session/
  current_run/current_identity`，嵌套 worker 复用同一 asyncio 上下文，
  工具守卫 `custom_tools.pack_scope_denied`（`server/custom_tools.py:446-473`）
  调用 `auth.current_role()/current_department()` 时读到的是**发起者**身份。
  这条链路目前正确，但没有任何断言锁定；一旦编排被挪到线程池/后台任务，
  ContextVar 丢失后会静默回落到"查表/空部门"（fail-closed 但不再是
  同一份身份快照）。
- **权限过滤层次**：只有**执行层**。`STATE.pack_tools` 是全量包工具，
  `_worker_tools()` 不做角色/部门过滤——低权限发起者的 worker 提示里
  能看到 approver 专属工具的名称与描述，调用时才被拒绝。这与 1.2
  （包级 RBAC 提示层 + 执行层双层）的既定口径不一致。
- **知识库范围**：检索工具的可用性由**所在包的** `allowed_roles/
  allowed_departments` 决定（`pack_scope_denied`）；出处定位端点另由
  `server/kb_access.py:23-43` 的 `kb_allowed` 判定。两者共用同一份包级
  白名单，但目前没有任何"编排定义声明的检索能力"与"发起者 KB 权限"
  的交集逻辑（因为还没有定义模型）。
- **失败语义**：worker 抛异常直接冒泡到工具层，被
  `tools_admin.py:338-341` 转成一条"编排执行失败（异常类名）"文案，
  整次编排失败，没有部分成功、没有重试。
- **计量归因**：依赖 ContextVar，理论上全部计入发起者的
  `user/session/run`；没有 `source` 区分，无法把编排产生的调用与主对话
  区分开。
- **其他边界**：Mock 模式不可用（`STATE.llm is None` 直接返回提示，
  `tools_admin.py:333-334`）；整个编排在 chat 请求生命周期内执行，受
  会话租约串行化；`ma_worker` 标签只用于过滤 worker 中间 token
  （`multi_agent.py:16`、`:35`）。

### 1.2 与目标设计的差距

| 能力 | 现状 | 5.1 目标 |
|---|---|---|
| 角色定义 | 三个硬编码身份，提示词固定 | 任意角色：名称、职责提示词、工具子集、串并行、上下文传递规则可配置 |
| 编排模式 | 仅 orchestrator-worker 并行 | 并行/串行/阶段组合；orchestrator-worker 降为预置示例 |
| 定义来源 | 无 | 配置文件 + 对话式创建（范围见 §八.D7） |
| 定义校验 | 无 | fail-closed：未知工具、危险工具、重名角色、环、并发超限 |
| 权限传递 | 隐式 ContextVar，仅执行层过滤 | 显式不可变快照 + 装配层/执行层双层，检索范围按发起者收窄 |
| 审批旁路 | 工具子集硬编码安全，暂无风险 | 显式白名单 + 校验拒绝 + 执行兜底，禁止审批类工具进入子 agent |
| 沙箱边界 | 复用包工具构建器，正确但无编排路径断言 | 复用同一构建器 + 编排路径专项断言，sandbox-down fail-closed |
| 生命周期 | 嵌套调用不校验会话代际 | 每步模型调用前复用 `fence_ok`，删除后中止 |
| 计量 | 归发起者，无来源区分 | 归发起者 + `source=orchestration` |
| 可对比性 | 只能与自身比 | 保留原实现作基准，自定义定义与之做集合等价断言 |

### 1.3 目标

交付一个**声明式**多角色编排引擎：角色与步骤由定义描述，引擎负责按
串行/并行方式调度、按显式规则传递上下文、在执行全程把"发起者的身份
与权限"作为唯一执行身份，并保证审批、沙箱、会话生命周期三条既有边界
不被新执行路径绕过。本轮同时交付两个可运行示例：调研编排（与现状
等效）与「审核-修订-复核」串行流程（证明角色不限领域）。

## 二、需求分析与约束条件澄清

### 2.1 定义模型（最小可用字段）

一份编排定义至少包含：

- `name` / `version` / `description`：定义标识与版本；
- `roles[]`：每项含 `id`、`name`（展示名）、`prompt`（职责提示词）、
  `tools[]`（工具名子集，只能从引擎的安全工具清单里选）；
- `steps[]`：每项含 `id`、`role`、`mode`（`single` / `parallel`）、
  可选 `fanout`（并行扇出的子任务来源与上限）、`inputs[]`（显式声明的
  上游输出引用，空 = 只拿总任务）；
- `aggregate`（可选）：最终汇总角色与输入步骤；
- `max_parallel`（可选，见 §八.D3）、`on_error`（可选，见 §八.D4）。

语义约束（校验期 fail-closed，任一不满足则定义 `status=error`、不可执行）：

1. `roles` 非空、`id` 唯一、`prompt` 非空且长度上限；
2. `tools` 必须是引擎安全工具清单的子集（见 3.3）；
3. `steps` 引用的 `role` 必须存在；`inputs` 只能引用前序步骤；
4. 步骤图无环（串行流水线的硬性前提）；
5. `max_parallel` 不超过全局上限；
6. 定义文本不得包含绝对路径/服务账号标识（落盘前校验，错误信息不回显
   原始异常，沿用 `{e}` 三通道口径）。

定义本身是**数据不是代码**：引擎不 exec/eval 定义内容，不做模板求值。

### 2.2 执行模型

- **阶段内并行**：`mode=parallel` 的步骤按上游输出扇出 N 个子执行单元，
  并发受 `max_parallel`（默认 4，与现状 `MAX_WORKERS` 一致）与全局硬上限
  双重约束。
- **阶段间串行**：`steps` 按声明顺序推进，后一步只能看到 `inputs` 显式
  引用的前序输出；未声明的一律不可见（默认最小信息）。
- **组合**：调研编排 = `plan(single) → research(parallel) →
  aggregate(single)`；非调研流程 = 三个 `single` 步骤串联。二者共用同一
  执行器，不写两套调度。
- **上下文传递**：只传"总任务 + 显式声明的上游输出"，不共享主对话历史；
  每个子执行单元是独立 ReAct 循环，无独立 checkpointer、无长期记忆。
- **空产出标记（v0.17.50 / 5.2 补丁）**：`inputs` 引用的上游步骤产出为空
  或缺失时，下游提示写入「上游步骤 X 输出为空」；`fanout.from` 来源为空
  而退回总任务时同样标注。不失败、不改变 `ok`/`failed_step` 判定。
- **事件与展示**：沿用 `ma_worker` 标签过滤子执行单元中间 token；本轮
  不做步骤级进度事件（属 4.1 范围，见 §七）。

### 2.3 工具装配与权限交集（双层）

- **装配层**：按当前发起者身份过滤角色声明的工具子集——包工具过
  `pack_scope_denied`、知识库相关能力过 `kb_allowed`、个人专属技能/工具
  只保留发起者本人域与通用层。过滤发生在**绑定给模型之前**，低权限
  发起者的子 agent 看不到无权工具的描述。
- **执行层**：即使装配层被绕过（直接构造工具对象/提示注入），工具入口
  的 `_guard_pack_tool` 与各工具自带的工作区/专属域守卫仍然拦截。两层
  必须同时存在，缺一不可（与 1.2 包级 RBAC 的既定口径一致）。
- **复用而非重写**：权限判定只调用 `custom_tools.pack_scope_denied`、
  `kb_access.kb_allowed`、`skills.current_scope`、`custom_tools.current_scope`
  现有实现，不新增第二套判定（避免口径漂移）。

### 2.4 归属、创建与审批

- 定义资产沿用技能/自定义工具的归属模型：`user` 角色的定义落个人域
  （`orchestrations_personal/<域>/`），仅本人可见；approver/admin/开放模式
  创建的**全局定义**全员可见，须走 `approval.require_approval` 审批门。
- 定义创建是资产写入，不是执行；审批门在工具入口层（与 create_skill/
  create_custom_tool 分层一致），存储层保持纯落盘。
- 审批职责分离沿用 v0.17.41：发起者不得批准自己发起的定义创建。
- 具体创建入口形态（仅配置文件 / 加对话式工具 / 加 Web 编辑器）见 §八.D7。

### 2.5 生命周期与资源上限

- 编排在 chat 请求生命周期内执行，受会话租约串行化；不引入后台队列。
- 每个子执行单元在**每次模型调用前**复用 `sessions.fence_ok` 校验会话
  代际（与 `stream_reply` 三栅栏同口径）；会话被删即中止，不产生新的
  产出文件或审批记录。
- 资源上限：子执行单元上限、单单元工具轮数上限、单次编排总模型调用
  次数上限（防止"定义声明 10 步、每步 4 worker"式的成本放大）。超限
  以错误事件中止，不做静默截断。

### 2.6 约束（沿用项目既有约定）

- 离线可测：全部单测用 FakeLLM/假 ReAct 工厂，不依赖真实模型与网络。
- 不新增数据库表（若 §八.D1 选 DB 方案再调整）；不引入新第三方依赖。
- 错误信息三通道口径：用户/模型/审计不回显原始异常（含绝对路径），
  本机日志可保留。
- Mock 模式维持现状：编排不可用，返回明确提示，不伪造执行。
- 定义文件热加载沿用"mtime_ns + 内容摘要"签名思路（与技能/包一致），
  避免秒级 mtime 漏更新。

## 三、身份与权限在编排链路中的传递模型

这一节是硬约束，实现时逐条对照，评审时逐条核对。

### 3.0 传递链路（唯一允许的形态）

```
HTTP 中间件 resolve_identity
      ↓ 构造一次
usage.Identity(username, role, department, auth_source)  ← 不可变快照
      ↓ chat 端点传入
agent.stream_reply(identity=...) → usage.current_identity.set(快照)
      ↓ 引擎入口读取快照（一次）
orchestration.run(definition, task, identity=快照)
      ↓ 每个子执行单元启动前显式重设
usage.current_identity.set(发起者快照)  （并复位 current_user/session/run）
      ↓ 子 agent 内
auth.current_role()/current_department() 只读快照
自定义/包工具守卫、文件域守卫、技能域守卫、沙箱调用
```

要点：身份**从入口一次读取、显式参数下传、每个执行边界重设**，不依赖
"调用栈恰好共享 ContextVar"。`Identity` 是 frozen dataclass
（`server/usage.py:43-56`），引擎不得构造第二份或修改字段。

### R1 执行身份 = 发起者的不可变快照

**规则**：子任务/子 agent 的身份只能是发起者 `Identity` 的四字段原样传递；
不得置换为服务账号、编排定义作者、`anonymous`，也不得按用户名重查本地
用户表重建（v0.17.39 已禁止执行层查表）。开放模式（`auth_source=open`）
沿用既有契约：`role=admin`、`department=""`、`username` 与自报 `user_id`
对齐。

**违反后果**：低权限发起者的子任务以高权限检索/写盘；调岗或撤权在同一
请求内不生效；审计与计量归属错人。

**检测方式**：
1. 子执行单元内记录 `usage.current_identity.get()` 与
   `auth.current_role()/current_department()`，断言四字段与发起者快照
   **逐字段相等**（含空部门、SSO 来源）。
2. **边界丢失测试**：在子执行单元启动前手动清空
   `current_identity/current_user`（模拟线程池/后台调度），引擎仍须用
   显式快照重设；若实现依赖隐式 ContextVar，此用例红。
3. **提权回归**：以 `role=user` 发起、定义作者为 `approver`，断言全链路
   任何位置不出现 `role=admin`（`auth.current_role` 返回值逐步骤断言）。
4. 静态检查：编排模块不得出现 `user_by_name(...)` 按名重建身份；
   身份只能来自入口参数（评审清单 + 单测用 `user_by_name` 爆炸替身固化，
   沿用 v0.17.39 AC6 做法）。

### R2 定义者权限不得放大执行者的检索范围

**规则**：定义里声明的工具/知识库能力必须与**发起者**的 entitlement
取交集，而不是与定义作者的交集：
- 包工具：`pack_scope_denied(包, allowed_roles, allowed_departments,
  role=发起者.role, department=发起者.department)` 通过才装配；
- 知识库：任何库/出处判定走 `kb_access.kb_allowed(kb, 发起者.role,
  发起者.department)`，不另写判定；
- 个人资产：技能与自定义工具只允许发起者本人域 + 通用层，定义不得
  借用作者个人域资产；
- 提示层：子 agent 的职责提示词来自定义文本，但领域包片段仍按发起者
  身份注入（`packs.prompt_fragments` 现有口径），定义作者的高权限不会
  把受限片段带给低权限发起者。

**违反后果**：定义作者（高权限）搭一个"调研编排"，任何低权限用户触发
都能借道检索到本无权访问的部门库/专属资产——这是比单次越权调用更隐蔽
的横向提权。

**检测方式**：
1. **必测用例（用户点名）**：定义作者 hr/approver 声明 `hr` 库检索工具
   与 `allowed_departments=[hr]` 的包工具；发起者 `user/finance` 执行
   → 装配层工具集不含该工具（模型消息中无其 description），**且**强行
   直调返回与 `pack_scope_denied` 完全一致的拒绝文案；同一 FakeKB 下
   检索结果为空/拒绝。发起者 `user/hr` 则可用并命中。
2. 同一份定义先后以两种身份执行，断言结果互不影响（无跨请求工具集
   缓存污染）。
3. 个人域断言：定义声明他人专属技能/工具 → 发起者装配层不可见、直调
   被拒；作者本人发起时可见（证明是发起者而非作者决定）。
4. 口径一致断言：对同一 (包, 角色, 部门) 组合，编排装配层判定与直接
   调用包工具的判定结果一致（参数化用例，防两套实现漂移）。

### R3 编排引擎不得成为绕过审批的旁路

**规则**：
- 子 agent 的工具只能来自**引擎安全工具清单**：`read_text_file`、
  `list_uploaded_docs`、`save_output_file`、只读类包工具、显式白名单的
  MCP 工具。清单是代码常量，只能"选子集"，定义不能扩展。
- 审批类/管理类/危险类工具**永久排除**：`delete_workspace_file`、
  `create_skill`、`create_custom_tool`、`delete_custom_tool`、
  `run_custom_tool`、`enable_pack`、`disable_pack`、`create_pack`、
  `delete_pack`、`sign_pack`、`run_python_code`、`orchestrate_subtasks`
  （后者防递归放大）。
- 定义声明上述任一工具 → **校验期** `status=error`，定义不可执行；执行
  层再兜一层（强注入时返回拒绝且无副作用）。
- 理由：`approval.require_approval` 依赖 LangGraph `interrupt` 与
  checkpointer（`server/approval.py:306-329`），嵌套子 agent 没有独立
  checkpointer，危险工具进去只会以"审批流不可用"fail-closed 失败；不能
  把安全性寄托在这条隐式失败上，必须显式排除。

**违反后果**：删文件、建工具、启停包等全局影响操作在子 agent 里被执行，
审批门被绕过；或审批 interrupt 冒泡污染主图状态。

**检测方式**：
1. 参数化用例：逐个危险工具名声明进定义 → `load_definition` 返回 error，
   错误文案点名工具，定义不可执行。
2. 绕过校验直接构造执行计划 → 工具调用返回拒绝文案，目标文件/资产
   未发生变化（副作用断言）。
3. 一次含危险工具声明的编排尝试后，`approvals` 表 pending 数不增加
   （证明没有走到审批，也没有偷偷执行）。
4. 定义创建本身走审批门（全局层）：graph 上下文 approve 才落盘；
   reject/无图上下文 → 不落盘（`create_skill` 同口径）。

### R4 编排产生的执行路径不得绕过沙箱令牌与环境隔离

**规则**：
- 子 agent 的包工具对象必须复用 `packs.load_pack_tools()` /
  `custom_tools.build_tool()` 产出的同一批对象：沙箱模式经
  `POST /run_tool` 带 `X-Sandbox-Token`（`sandbox/server.py:41-54`），
  不得自建执行器、不得直连本地模块、不得新增网络出口。
- 引擎自身不执行任何代码：定义是数据，不做 eval/模板求值/动态 import。
- `sandbox-down`（沙箱不可达）时编排启动即 fail-closed 拒绝，与
  `custom_tools.build_tool` 同口径，不降级为本地执行。
- 子进程环境继续剔除 `SANDBOX_AUTH_TOKEN`/`SANDBOX_OPEN_MODE`
  （`sandbox/server.py:97-106`），编排路径不得以"透传环境"为名绕过。

**违反后果**：不可信工具在宿主机执行、外联或拿到沙箱令牌；沙箱故障时
静默降级为本地执行。

**检测方式**：
1. 沙箱模式下用 HTTP 替身截获 `/run_tool` 请求，断言
   `X-Sandbox-Token` 存在且等于配置值；错误/缺失令牌 → 401 且工具无
   结果产出。
2. `sandbox-down` 替身 → 编排在启动阶段返回失败，包工具未执行。
3. 复用 `sandbox/server.py` 既有环境隔离用例，新增"编排路径触发工具"
   的变体，断言子进程环境不含两个变量。
4. 静态扫描：编排模块不得出现 `subprocess`、`exec`、`eval`、
   `importlib.import_module`（白名单除外）、直连 `httpx/requests` 的
   写调用；纳入代码评审清单。

### R5 生命周期与资源边界（相邻但必须写死）

**规则**：每个子执行单元在每次模型调用前校验会话代际
（`sessions.fence_ok`），删除即中止；单次编排的步骤数、并发数、总模型
调用次数受硬上限约束，超限以错误事件中止。

**违反后果**：会话删除后在途编排继续写 checkpoint/产出（违反 v0.17.38
代际 fencing 的终局语义）；一份定义被用来放大成本（1 次请求 → 数十次
模型调用）。

**检测方式**：代际替身在中途翻转为旧代际 → 断言下一步不调用模型、
不写产出；并发计数替身断言峰值 ≤ 上限；超步数定义在校验期拒绝，运行期
超调用数中止并返回错误事件。

## 四、关键技术与选型决策

| 决策点 | 候选 | 选定 | 理由 |
|---|---|---|---|
| 执行器 | ① LangGraph `StateGraph` + `Send` ② 纯 asyncio 编排 | **①** | 复用 `multi_agent` 已验证的扇出/标签/事件过滤，未来 4.1 进度也可复用；纯 asyncio 需重造事件与取消语义 |
| 定义形态 | ① 声明式 YAML ② Python DSL/代码 ③ 自由文本由模型解释 | **①** | 可校验、可快照、可审计；代码形态等于开放执行面，自由文本无法 fail-closed |
| 权限过滤位置 | ① 仅执行层 ② 装配层 + 执行层 | **②** | 与 1.2 既定双层口径一致；仅执行层会让低权限模型看到无权工具描述（现状通病） |
| 工具清单 | ① 静态安全清单 + 定义选子集 ② 反射全部内置工具后排除危险项 | **①** | 白名单比黑名单可靠；新增工具默认不进编排，需显式评审加入 |
| 定义快照 | ① 执行前按内容 hash 快照 ② 实时读取文件 | **①** | 执行中改定义不应改变本次语义；同时给审计留版本证据 |
| 子单元状态 | ① 无 checkpointer、独立 ReAct ② 共用主图 checkpointer | **①** | 共用会让审批 interrupt 冒泡污染主图，且子单元无需断点续跑 |
| 测试落点 | ① 新增 `tests/test_orchestration_*.py` ② 塞进 test_multi_agent.py | **①** | 主题独立、体量较大；保留 `test_multi_agent.py` 作基准回归 |

## 五、验收标准（AC）

每条都写成可执行断言或可核对文件，不写"体验良好"类软标准。

- **AC1 定义模型可用且校验 fail-closed**：能载入含 ≥3 角色、串行+并行
  混合的定义；未知工具、危险工具、重名角色、空提示词、步骤引用不存在、
  步骤成环、并发超上限、定义文本含绝对路径——逐项返回 `status=error`
  且不可执行，错误文案点名定义与原因、不含绝对路径。
  *判定：`load_definition` 单测参数化。*
- **AC2 调研编排与现有实现等效**：同一任务文本 + 同一 FakeLLM 回放 +
  同一假 ReAct 工厂，自定义三角色调研定义 vs `run_orchestration`：
  子任务集合相等、worker 数相等、汇总器收到的 findings 集合相等、产出
  含摘要与子任务清单。不要求自然语言逐字相同（LLM 输出不可复现）。
  *判定：集合相等断言（顺序无关）。*
- **AC3 非调研三角色串行流程跑通**：「审核→修订→复核」定义按序执行；
  第二步输入含第一步输出、第三步输入含第二步输出；三步各调用一次；
  终态产出非空；`save_output_file` 落在 `outputs/<发起者域>/`。
  *判定：FakeLLM 调用记录 + 输入消息内容 + 文件路径断言。*
- **AC4 身份四字段透传**：子步骤内 `current_identity` 与
  `current_role/current_department` 与发起者快照逐字段相等（含空部门、
  SSO 来源）。*判定：记录器逐字段断言。*
- **AC5 调度边界不丢身份**：子步骤启动前清空
  `current_identity/current_user`，引擎仍以显式快照重设，身份与 AC4
  一致；漏传即红。*判定：清空后断言。*
- **AC6 无提权/不降级为服务账号**：`user` 发起、定义作者 `approver` →
  全链路角色恒 `user`；开放模式 `anonymous` 发起 → `role=admin`、
  `department=""`（既有契约）；全链路不出现服务账号标识。
  *判定：逐步骤角色断言 + 静态检查。*
- **AC7 检索范围按发起者收窄（双层）**：`hr` 域定义 + `finance` 发起者
  → 装配层无该工具、直调被拒且文案与 `pack_scope_denied` 一致、检索
  无结果；`hr` 发起者 → 有工具且命中。定义作者身份不改变结果。
  *判定：工具集/直调/检索结果三重断言。*
- **AC8 定义作者权限不放大（跨资产）**：approver-only 包工具、他人
  专属技能/自定义工具，`user` 发起者不可见且直调被拒；approver 发起者
  在权限内可用。*判定：装配层 + 执行层 + 专属域断言。*
- **AC9 审批旁路拒绝**：定义含 `delete_workspace_file`/`create_skill`/
  `create_custom_tool`/`enable_pack`/`run_python_code`/
  `orchestrate_subtasks` 之一 → 校验 error 不可执行；强注入执行层拒绝
  且无副作用；`approvals` 表 pending 数不增。
  *判定：参数化 + 副作用 + DB 计数断言。*
- **AC10 沙箱边界**：沙箱模式子步骤调用包工具时 `/run_tool` 收到正确
  `X-Sandbox-Token`；错/缺令牌 401 且无结果；`sandbox-down` 编排启动即
  拒。*判定：HTTP 替身 + `exec_mode` 替身。*
- **AC11 环境隔离**：编排路径的工具子进程环境不含
  `SANDBOX_AUTH_TOKEN`/`SANDBOX_OPEN_MODE`。*判定：复用 sandbox 既有
  环境用例并新增编排变体。*
- **AC12 并发与资源上限**：定义并发 5 而全局上限 4 → 校验拒绝；并发 4
  → 峰值并发 ≤4；总模型调用次数超上限 → 中止并返回错误事件。
  *判定：计数替身 + 超限定义。*
- **AC13 计量归因**：编排全程 usage 记录的 `user/session` 为发起者、
  `run` 为父 run、`source=orchestration`；无空用户/`anonymous` 记录
  （开放模式除外）；记录数与模型调用数一致。
  *判定：monkeypatch `usage.record` 捕获三元组。*
- **AC14 失败语义**：按 §八.D4 裁决落地。选 fail-fast 时：子步骤抛异常
  → 整次编排返回失败、不泄露原始异常文本、已完成部分标注"不完整"；
  选部分成功时：失败步骤有标记且汇总继续。两种路径都要有对应用例。
  *判定：注入抛异常的假 worker。*
- **AC15 会话生命周期**：编排中途代际变旧 → 下一步不调用模型、不写
  产出、不产生审批。*判定：`fence_ok` 替身 + 产出/审批计数。*
- **AC16 覆盖率与回归**：新模块单文件覆盖率 ≥90%；全量回归
  「基线 + 新增用例」全绿、0 failed、18 skipped 语义不变；拒绝路径
  映射表新增"编排工具级权限点"小节，每个判定点 ≥1 条拒绝用例。
  *判定：`pytest --cov` + 映射表核对。*

### D1 角色定义如何存储与版本化

- **A. 文件 YAML**：`orchestrations/`（全局）+ `orchestrations_personal/<域>/`
  （个人），`version` 字段 + 内容摘要；执行前按 hash 快照。
- **B. STATE_DB 表存 JSON**：版本行 + 执行记录，跨进程共享，但编辑只能
  走 API/工具，没有文件 diff，且 6.4 Postgres 化时需同步。
- **C. 混合**：文件为源，DB 只存版本指针与执行记录。
- **建议 A**：与 packs/skills 资产模型一致，归属、审批、热加载都能复用
  既有直觉，零新表；缺点是定义编辑需要仓库/文件权限（但本项目技能与包

- **影响**：选 B 会增加一次 6.4 的迁移面；选 C 会同时维护两套一致性问题。

### D2 工具子集如何授权

- **A. 静态安全清单，定义只能选子集**（清单是代码常量）。
- **B. A + 按发起者实时 entitlement 交集**（装配层 + 执行层）。
- **C. 任意内置工具可声明，靠执行层守卫兜底**。
- **建议 B**：A 是防止审批旁路的底线，B 解决"定义作者高权限、发起者
  低权限"的横向提权。C 会把越权推迟到调用时点，且提示层先暴露工具描述。
- **影响**：B 需要按 (定义 hash, 身份四元组) 缓存已过滤工具集，否则每次
  执行都重建；缓存键漏身份字段会造成跨身份污染（AC7 专门测）。

### D3 并发与串并行上限

- **A. 固定 4**（沿用 `MAX_WORKERS`）。
- **B. 定义可配 `max_parallel`，全局硬上限默认 4**，定义不得超上限。
- **C. 不限制**。
- **建议 B**：默认行为与现状一致，低配环境/成本敏感场景可按定义调小；
  全局上限防定义滥用。校验期 fail-closed。
- **影响**：C 会让一份定义打满模型配额，不建议；A 无法按流程调优。

### D4 失败、重试与部分失败语义

- **A. fail-fast**：任一子步骤异常 → 整次编排失败，如实返回已完成部分
  与失败步骤（不自动重试）。
- **B. 部分成功**：`on_error=continue`，失败步骤标记，继续汇总。
- **C. 自动重试 N 次**（模型/工具异常）。
- **建议 A 为本轮默认**：与本项目"审批/权限 fail-closed"口径一致，避免
  "部分成功被当成完整结论"；不自动重试，避免把故障掩盖成成功、放大成本。
- **影响**：B 需要产物里明确标记哪一步失败，否则误导决策；C 对非幂等
  工具（写文件/外部副作用）有重复执行风险，且会成倍放大 token。

### D5 子 agent 与主 agent 的上下文隔离/共享

- **A. 完全隔离**：只给总任务 + 本步显式输入。
- **B. 全共享主对话历史**。
- **C. 显式数据流声明**：每步 `inputs[]` 引用上游输出，默认只传总任务。
- **建议 C**：信息最小化、可复现、可控成本；B 会把主会话里的敏感内容
  带给所有角色，且 token 爆炸；A 无法支撑串行流程（后一步需要前一步结果）。
- **影响**：C 的"显式"由定义作者决定传什么，但内容仍属于同一发起者
  请求，不构成越权；需在定义校验里拒绝引用不存在的上游。

### D6 计量如何归因到发起者

- **A. 全部计入父 run**（user/session/run 同发起者），`source=orchestration`。
- **B. 每步独立 `run_id`（`<parent>:<step>`）**，按前缀聚合。
- **C. 单独计入定义作者/系统账号**。
- **建议 A 为本轮基线**：现成字段即可落地，风险最低；B 可作为后续增强，

## 九、风险与回归影响

- **成本放大**：一次编排最多 1 次规划 + N×轮数 + 1 次汇总，现状上限约
  18 次模型调用；定义可声明更多步骤时必须靠 §2.5 的硬上限兜底，并在
  审计里可见。
- **请求时长**：编排在 chat SSE 内执行，拉长单轮等待；性能门禁（每端点
  P95 ≤500ms）不覆盖 chat 长连接，但需在文档中说明编排属"用户主动发起
  的长任务"，不纳入该阈值。
- **ContextVar 边界**：任何把子执行单元挪到线程池/后台的改动都会丢身份；
  R1 的显式快照与 AC5 是唯一的防线，后续改动不得绕过。
- **定义热加载**：文件方案需接入签名（mtime_ns + hash），否则执行中改
  定义会造成"读到的和校验过的不是同一份"；快照 + hash 写入审计。
- **提示注入**：定义文本由有权限的创建者编写，但工具边界不能靠文本
  约束；装配层与执行层双层是硬要求。
- **错误信息**：编排错误经工具结果进入模型上下文，必须遵守 `{e}`
  三通道口径（不回显原始异常/绝对路径）。
- **回归门槛**：基线 v0.17.43（本 spec 编写时实测见 §十），新增用例不得
  改变 18 skipped 的语义；覆盖率单文件 ≥90%、整体 ≥90%。
- **文档同步**：README 版本记录只写功能不写技术细节；PLAN #14 状态回写；
  若 D7 选 B，SECURITY.md 需补"编排创建审批与职责分离"说明。
