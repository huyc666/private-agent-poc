# Spec — 2.4 一库多包共享（跨领域通用知识库）

出处：docs/PLAN.md 执行序号 10（规模 S，依赖 2.3 ✅ v0.17.26）。

## 1. 背景与目标

PLAN 2.3 交付了部门专属库隔离，但 `kb_allowed`（定位端点权限判定，
server/main.py）对同一库被**多个领域包声明**的场景取「声明顺序首包生效」：
若公司制度库 `kb/policy` 同时挂人事包与财务包（各自出检索工具与提示片段，
这是「跨领域通用知识库」的目标形态），财务账号会被首包（人事包）的部门
白名单误拒在出处定位端点之外——检索工具能用，点击出处却 404，体验割裂。

目标：库可见性判定改为**多包 OR 合并**——任一声明包对当前身份放行即放行；
检索层与提示层按包过滤天然兼容、无需改动。做完后「一库多包」形态全链路
（检索、出处定位）贯通。

## 2. 需求分析与约束条件澄清

### 功能边界

- **改 1**：`kb_allowed` 由「遍历中首个声明该库的包单独定生死」改为
  「遍历全部声明包，任一包 `pack_scope_denied` 通过即放行」。
- **改 2**：包校验层新增跨包规则——多包声明**同一库**且存在**同名检索工具**
  时，相关包整包 `status=error`（fail-closed，所有角色不可用），错误信息点名
  对方包、共享库与冲突工具名；不共享库的同名工具维持既有「后加载跳过 +
  WARNING」不变。
- **不改**：
  - 提示层（`packs.prompt_fragments`）：按包逐个过滤，天然兼容——身份经
    A 包放行则只见 A 的片段，B 包片段照常隐藏；
  - 执行层（`custom_tools._guard_pack_tool`）：按工具所属包判定，天然兼容；
  - `_declared_kb_packs` 扫描逻辑、`/api/kb/source` 端点结构与 404 语义。
- 明确不做：pack.yaml 不新增「共享库」声明语法——多包各自在
  `knowledge_bases` 列出同一库名即表达共享，零新字段。

### 约束（沿用既有约定）

- fail-closed：库未被任何启用包声明 → False；被声明但全部声明包拒绝 → False；
  开放模式（role=None）在首个声明包处放行（现状语义保持）。
- 纯函数语义：`department=None` 归一为 `""`，不回落上下文（2.3 评审修复既有约定）。
- 三处同口径：库判定仍复用 `pack_scope_denied`，不新写第二份实现。
- 404 不区分「不存在」与「无权」，不暴露库清单（2.2 既有语义）。

### 使用约束（澄清 1 答复：B 校验层强约束）

跨包**工具同名**在共享库场景下由校验层 fail-closed 拒绝（见功能边界改 2）；
非共享库场景维持既有「跳过 + 告警」。共享库的多个包必须使用不同的检索
工具名（现有示例已如此：`search_hr_knowledge` / `search_finance_knowledge`）。

### 待澄清问题（已获用户答复，2026-10-21）

1. **共享库检索工具重名** → **B：校验层强约束**。多包声明同一库且同名工具
   → 整包 error（fail-closed），不依赖告警自觉。
2. **OR 合并推论** → **接受**：任一不限部门的包声明某库 ⇒ 该库对所有部门
   可见；要限部门须所有声明包都配白名单。
3. **版本号** → **v0.17.27**。

## 3. 关键技术与选型决策

| 决策点 | 候选 | 选定 | 理由 |
|---|---|---|---|
| 多包合并语义 | ① OR（任一包放行即放行）② AND（全部声明包都放行才放行） | **① OR**（PLAN 行已定） | 共享库各包视角独立：人事包授权人事、财务包授权财务，任一授权链成立即应可用；AND 会让两包白名单交集生效，与「各包自治授权」直觉相悖 |
| 判定实现 | ① 循环内逐包调 `pack_scope_denied` ② 收集声明包后单独写合并器 | **① 沿用 pack_scope_denied 逐包判定** | 三处同口径（2.3 评审修复约定），零新实现；循环 + 早退即可，S 规模不引入抽象 |
| 共享表达 | ① 多包各自声明同一库名 ② 新增共享库清单文件/pack.yaml 字段 | **① 零新语法** | 声明即共享，与既有 `_declared_kb_packs` 扫描零改动兼容 |
| 重名工具处理 | ① 文档约定不改代码 ② 校验层强约束（共享库+同名→整包 error） | **② 校验层强约束**（用户答复） | fail-closed 与本项目配置错误处理一致（2.3 AC6 先例）；同名工具静默消失正是共享库最危险的歧义源，靠告警自觉不可靠 |
| 测试落点 | ① 扩展 test_kb_citation.py（kb_allowed 单测）+ test_kb_permissions.py（端点夹具）② 新建文件 | **① 扩展现有两文件** | 复用其 packs_list 注入与 kb_client 替身夹具，S 规模不起新文件 |

## 4. 验收标准

- **AC1 多包 OR 放行**：库 `policy` 被包 A（depts=[hr]）与包 B（depts=[finance]）
  同时声明 → hr 身份与 finance 身份的 `kb_allowed` 均为 True。
  （单测：packs_list 注入）
- **AC2 单包拒绝回归**：库仅被包 A 声明（depts=[hr]）→ finance 身份 False、
  未分配部门身份 False（与 2.3 行为一致，无回归）。
- **AC3 混合授权**：包 A（roles=[approver]+depts=[hr]）、包 B 不限 → user/hr
  身份经 B 放行；approver/hr 经 A 或 B 均放行；user/finance 经 B 放行。
- **AC4 全拒绝 fail-closed**：库被 A（depts=[hr]）、B（depts=[finance]）声明，
  身份为未分配部门（""）→ False；admin 身份 → True（admin 全局视图经任一
  声明包放行）。
- **AC5 未声明库**：库未被任何包声明 → False（回归）。
- **AC6 开放模式**：多包声明同一库、role=None → True（回归）。
- **AC7 提示层/执行层按包隔离不受影响**：两包共享库 `policy` 时，hr 身份只见
  A 包提示片段、调 B 包检索工具被拒；finance 反之（单测：_mk_pack 构造两包 +
  prompt_fragments / pack_scope_denied 断言）。
- **AC8 端点 e2e**：`/api/kb/source` 以 `_declared_kb_packs` 替身注入两包同声明
  库 → hr/finance 身份均 200，未分配部门 404（集成测：kb_client 夹具模式）。
- **AC9 文档同步**：多包共享语义与「共享库须用不同工具名（校验层强约束，
  fail-closed）」写入 docs/PACK_GUIDE.md 与 docs/DEPLOYMENT.md（文档核对）。
- **AC10 校验层强约束**：两包声明同一库且存在同名工具 → 两包 `status=error`
  （错误信息点名对方包、共享库、冲突工具名，所有角色不可用）；两包无共享库
  但同名工具 → 维持既有「后加载跳过 + 告警」；冲突消除（改名）后两包恢复
  正常加载（单测：_mk_pack 构造三组场景）。

验证方式：AC1~AC8 单测/集成测（离线），AC9 文档核对；全量回归无既有用例破坏。
