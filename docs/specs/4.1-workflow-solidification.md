### 1.2 与 4.1 目标的差距

| 能力 | 现状（5.1） | 4.1 目标 |
|---|---|---|
| 参数 | 无参数模型，只有自由文本 `task` | 定义声明 `params[]`（类型/必填/默认值），触发时传参并校验 |

| 示例流程 | research-demo / review-demo（5.1 验收用） | 新增「周报汇总」参数化示例，固化且可重复触发 |
| 下游解锁 | — | 实例实体 = 4.2（调度/历史）与 6.7（task_id 归因）的前置 |

### 1.3 目标

在 5.1 引擎之上交付「流程固化」层：**参数化定义 + 可发现触发 + 实例留存 +
进度可视**，并以「周报汇总」示例证明同一流程可带不同参数重复触发。
不新增执行路径、不放宽任何 5.1 安全边界；身份/权限/审批/沙箱/栅栏全部沿用。

## 二、需求分析与约束条件澄清

### 2.1 定义模型扩展（向后兼容）

在 5.1 定义 schema 上新增两个**可选**顶层字段（`_TOP_KEYS` 相应扩充）：

- `params[]`：每项 `{name, type, description, required, default}`。
  - `name`：slug（`^[a-z0-9][a-z0-9_]{0,29}$`），同一定义内唯一；
  - `type` ∈ `string|int|float|bool`（白名单，其余拒绝）；
  - `required` 缺省 false；`default` 必须与 `type` 匹配（校验期检查）；
  - 单个参数值运行期长度上限 2000 字符（防成本放大，超限拒绝）。
- `task_template`：可选字符串，可引用 `{{参数名}}`；引用了未声明参数 →
  定义校验错误（加载期 fail-closed）。

**渲染机制（硬约束）**：纯正则字面替换（`\{\{\s*([a-z0-9_]+)\s*\}\}`），
单遍、不递归、不 eval、不引入模板引擎——5.1「定义是数据、不做模板求值」
的边界不变，参数替换是唯一且显式声明的例外。参数值即使包含 `{{其他}}`
或表达式文本也按字面量处理（AC2 专门测）。

无 `params`/`task_template` 的既有定义（research-demo、review-demo）
校验与执行行为逐字节不变（回归断言）。

### 2.2 触发入口

- **`run_orchestration(name, task="", params=None)`**（扩展现有工具签名）：
  1. 解析定义（沿用 `resolve_definition`）→ 加载校验（沿用 + 参数扩展）；
  2. 参数校验：缺必填 / 未知参数 / 类型不符 / 超长 → 拒绝，**不创建实例行**，
     错误文案点名参数、不回显绝对路径（三通道口径）；
  3. 任务确定：`task` 非空 → 用 `task`（显式优先）；否则渲染 `task_template`；
     两者皆无 → 拒绝；
  4. 创建实例行（status=running）→ 执行 → 回写终态（见 2.3）；
  5. 返回文案沿用现状格式，追加实例 ID。
  旧调用形态 `run_orchestration(name, task)` 完全兼容。
- **`list_orchestrations()`**（新增只读工具）：按当前身份列举可见定义
  （名称/版本/描述/参数声明/归属 personal|global）。可见性：
  `user` = 本人个人定义 + 全局；`approver/admin` = 全局 + 全部个人（全局视图，
  与 `list_custom_tools` 同口径）；开放模式 = 仅全局。
- 两个工具均注册进 `BUILTIN_TOOLS`；触发与列举不需要审批门
  （执行本身受 5.1 双层权限约束，列举只读）。

### 2.3 流程实例与历史留存

- **新表 `workflow_instances`，落 STATE_DB**（与 sessions/approval/auth/audit
  同库，`CREATE TABLE IF NOT EXISTS` + WAL + busy_timeout，沿用 `usage.py:131-173`
  模式）。字段：
  `instance_id`（TEXT 主键，`wfi-<12位hex>`）、`definition_name`、
  `definition_version`、`definition_hash`（执行前快照，沿用 5.1 口径）、
  `initiator`、`department`、`session_id`、`run_id`、`params_json`、
  `status`（`running/completed/failed/aborted`）、`failed_step`、`error`、
  `started_at`、`finished_at`、`outputs_json`、`summary`。
- **截断口径**：`outputs_json` 每个产出 ≤2000 字符、`summary` ≤2000 字符、
  `error` ≤500 字符（与工具结果截断同口径，防 DB 膨胀）。
- **状态机**：`running` → `completed`（ok=True）/ `failed`（执行异常、预算
  超限）/ `aborted`（代际栅栏中止）。终态回写 `finished_at` 与产出。
- **写入不阻塞主链路**：实例落库失败仅记日志、执行继续（与「计量失败绝不
  阻塞主链路」同原则）；实例是记录，不是执行前提。
- **`list_workflow_instances(definition_name="", limit=20)`**（新增只读工具）：
  按身份查历史（`user` 仅本人；`approver/admin` 全部；开放模式全部），
  按 `started_at` 倒序，`limit` 上限 100。4.2「历史可查」的底座提前就位。
- **归属与可见性判定只读身份快照**（`_identity_from_context` 现有入口），
  不按用户名查表重建（v0.17.39 口径）。

### 2.4 进度可视

- **引擎侧**：`execute()` 增加可选 `on_progress` 回调；每个步骤（含并行步骤
  整体与 aggregate）在 start/end/fail 三个时点调用。工具入口
  `run_orchestration` 传入的回调经 `adispatch_custom_event` 发
  `wf_progress` 事件：`{instance_id, definition, step, step_index, total_steps,
  status, detail}`。**尽力而为**：dispatch 抛错（如脱离 runnable 上下文的
  直接调用/测试路径）吞掉，绝不影响执行结果。
- **SSE 侧**：`agent.stream_reply` 增加 `on_custom_event` 分支——**仅**
  透传名称为 `wf_progress` 的事件为 `{"type":"progress", ...}`，
  其余 custom event 一律忽略（防任意事件注入）；payload 只保留白名单字段。
- **前端**：`web/index.html` 事件分派处新增一个 `else if (ev.type==='progress')`
  分支，把步骤进度渲染为当前气泡内的状态行（如「⚙ 步骤 1/3 · 审核 开始」
  「✓ 步骤 1/3 · 审核 完成」）。属既有页面的小幅增量修改（见 §八 D2）。
- `ma_worker` token 过滤与子工具事件透出现状不变。

### 2.5 示例流程：周报汇总（验收载体）

新增 `orchestrations/weekly-report.yaml`（全局内置，随仓库分发）：

- `params`：`week`（string，必填，如 `2026-W45`）、`highlights`（string，
  可选，默认空）；`task_template` 引用两参数。
- 角色与步骤（全部取自 5.1 安全清单且默认加载可用）：
  `collector`（工具：`list_uploaded_docs`、`read_text_file`、
  `get_current_time`）→ `writer`（工具：`read_text_file`、
  `save_output_file`）两个串行步骤，无 aggregate（末步输出即摘要）。
- 不声明 `search_common_knowledge` 等依赖可选包的工具，保证任何部署下
  定义校验都通过（避免「已登记但未加载」使内置示例不可用）。
- 验收语义：带不同 `week` 触发两次 → 两个实例、均 completed、产出留存、
  归属发起者——即「固化为可重复触发」。

### 2.6 权限与审批口径（沿用，无新执行面）

- 定义创建：个人自助 / 全局审批门 + 职责分离（5.1 既有，不改）。
- 执行：装配层+执行层交集按发起者身份（5.1 既有，不改）；参数值不改变
  身份链路——参数是发起者自己的输入，等价于其亲手写在 task 里，无提权面。
- 新工具 `list_orchestrations`/`list_workflow_instances` 只读、无审批门；
  **不进入**子代理安全清单（`SAFE_*` 不扩充）——定义声明它们会被校验以
  「不在编排安全清单内」拒绝（`_is_known_tool_name` 命中已知内置工具分支）。
- 实例表不引入新审批类型；流程执行不进 `audit_log`（6.3 审计范围为登录/
  文件读写/管理动作/审批操作；执行的 who/when 已由实例表 + usage 覆盖）。
- Mock 模式现状不变：编排不可用、返回明确提示、**不产生幻影实例行**。

### 2.7 约束（沿用项目既有约定）

- 离线可测：全部单测 FakeLLM/假回调，不依赖真实模型、网络或沙箱。
- 不新增第三方依赖；不新增数据库文件（新表进既有 STATE_DB）。
- 错误信息三通道口径；定义校验错误不回显绝对路径。
- SSE 序列化对事件 dict 通用透传（`routes/chat.py:168` 逐事件
  `json.dumps`），`progress` 事件无需改路由层；`agent.py` 仅增一个事件分支。
- 执行形态不变：流程仍在 chat 请求生命周期内同步执行、受会话租约串行化；
  后台执行/调度/取消属 4.2（实例表 `status=running` 为其预留）。

## 三、身份与权限传递（沿用 5.1，逐条对照）

5.1 spec §三 R1–R5 全部继续有效，本轮**不新增执行路径**：

- 实例写入/历史查询是纯数据层操作，身份只读快照（不重建、不查表）；
- 进度事件 payload 不含身份字段之外的敏感内容（白名单字段）；
- 参数渲染发生在身份校验与定义校验之后、模型调用之前，不接触工具装配；
- 新增拒绝面仅两处（参数校验、模板引用未声明参数），均 fail-closed。

## 四、关键技术与选型决策

| 决策点 | 候选 | 选定 | 理由 |
|---|---|---|---|
| 进度事件机制 | ① `adispatch_custom_event` + `on_custom_event` ② 伪造 tool 事件 ③ 轮询端点 | **①** | 官方通道、零新端点、与 astream_events v2 原生衔接；② 污染工具语义与前端芯片渲染；③ 需前端轮询，更适配 4.2 后台执行场景 |
| 实例存储 | ① STATE_DB 新表 ② 独立 workflow.db ③ 文件 JSON | **①** | 与 sessions/approval 同库同域，6.4 Postgres 化一次迁移；② 多一个迁移面与连接管理；③ 难查询难聚合 |
| 参数替换 | ① 纯字面替换 `{{name}}` ② Jinja2 模板 ③ 参数仅注入首步输入 | **①** | 零依赖、可 fail-closed、不开模板求值面（守住 5.1 原则）；② 引入求值面；③ 表达力不足 |
| 参数引用范围 | ① 仅 `task_template` ② +角色 prompt ③ +step inputs | **①** | 最小面，周报类场景足够；②③ 扩大提示注入面且校验复杂（见 §八 D1） |
| 代码落点 | ① 扩展 `server/orchestration.py` ② 新建 `server/workflows.py` | **①** | 定义/触发/实例同域内聚；文件约增至 ~1100 行可接受（见 §八 D4） |
| 产出留存 | ① 每产出截断 ≤2000 字符 ② 全量 ③ 不存 | **①** | 与工具结果截断同口径；② DB 膨胀；③ 4.2/6.7 失去证据 |

## 五、验收标准（AC）

每条写成可执行断言，不写软标准。

- **AC1 参数声明校验**：合法 `params` + `task_template` 定义可加载；
  参数名重复/非 slug、类型不在白名单、default 与 type 不符、`task_template`
  引用未声明参数——逐项 `status=error` 不可执行；无参数的既有定义
  （research-demo/review-demo）校验结果不变。*判定：参数化单测。*
- **AC2 触发参数校验与渲染**：缺必填/未知参数/类型不符/参数值超 2000 字符
  → 拒绝且**无实例行产生**；模板渲染为单遍字面替换——参数值含 `{{other}}`
  与 Python 表达式文本时按字面保留、无二次替换、无 eval；`task` 非空优先于
  模板；`task` 与模板皆空 → 拒绝。*判定：单测 + DB 行计数。*
- **AC3 示例流程可重复触发**：`weekly-report` 定义校验通过；带不同 `week`
  触发两次 → 两个不同 `instance_id`、均 `completed`、`outputs_json`/`summary`
  留存（截断口径内）、`initiator` 归属正确；产出文件落 `outputs/<发起者域>/`。
  *判定：FakeLLM 双触发 + 实例行断言。*
- **AC4 实例实体与可见性**：实例行字段完整（id/定义三要素/身份/会话/run/
  参数/状态/时间）；`user` 查不到他人实例，`approver/admin` 可查全部；
  `list_workflow_instances` 倒序、`limit` 生效（>100 截到 100）。
  *判定：多身份用例。*
- **AC5 进度事件**：FakeLLM 下捕获 `wf_progress` 序列——步骤 start/end
  顺序与定义 `steps`（含 aggregate）一致，同一 `instance_id` 贯穿；
  `stream_reply` 仅透传 `wf_progress`，其他 custom event 名称不透传；
  dispatch 替身抛异常时执行结果不受影响（尽力而为）。*判定：事件序列断言。*
- **AC6 新工具边界**：`list_orchestrations`/`list_workflow_instances`
  只读无审批门；定义声明二者 → 校验以「不在编排安全清单内」拒绝；
  二者不出现在 `SAFE_*` 清单。*判定：校验用例 + 常量断言。*
- **AC7 失败与终局**：执行异常 → 实例 `failed` + `failed_step` + `error`
  （无绝对路径）；代际栅栏中止 → `aborted`、无新产出；预算超限 → `failed`
  且点名步骤；Mock 模式触发 → 提示文案且无实例行。*判定：替身用例。*
- **AC8 列举可见性**：`user` 个人定义他人不可见、全局全员可见、参数声明
  随列举输出；开放模式仅见全局。*判定：多身份用例。*
- **AC9 计量无回退**：编排调用仍归发起者父 run、`source=orchestration`
  （5.1 AC13 用例全量重跑通过，实例表不改变计量链路）。*判定：回归。*
- **AC10 覆盖率与回归**：基线 891 passed / 18 skipped + 新增用例全绿、
  0 failed、18 skipped 语义不变；新增代码单文件覆盖率 ≥90%。
  *判定：`pytest --cov`。*

## 九、风险与回归影响

- **进度事件依赖链**：`adispatch_custom_event` 需在 runnable 上下文内；
  并行子任务经 `asyncio.create_task` 复制上下文，理论可达，但实现必须以
  try/except 兜底（尽力而为），且测试覆盖「脱离上下文直接调用」路径。
- **前端回归面**：`web/index.html` 改动限于事件分派新增分支，不触碰既有
  七类事件处理；人工验证覆盖登录态对话流一轮（沿用 E2E 清单做法留记录）。
- **实例写入在事件循环内**：同步 SQLite 写入每实例 2 次（创建+终态），
  低频，与 `usage.record` 同口径（同步+锁），可接受；不做 to_thread。
- **参数注入**：参数值入提示词等价于发起者自输，无提权；单遍字面替换防
  递归展开；长度上限防成本放大。
- **向后兼容**：`run_orchestration` 签名扩展保持旧调用形态；既有定义与
  5.1 全部用例不改一字节即须全绿（AC1/AC9 锁定）。
- **示例定义脆弱性**：`weekly-report` 只声明默认加载的安全工具，规避
  「已登记未加载」校验失败（2.5 已述）。
