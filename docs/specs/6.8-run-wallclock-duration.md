## 1. 背景与目标

PLAN 原文：「stream_reply 首尾挂秒表记录单次 run 端到端耗时（含工具执行与
编排开销，即用户等待时间），run 级视图输出；与 6.6 的模型调用时长（口径 A）
互补，区分「模型耗时」与「等待耗时」」。

### 1.1 现状：run 记录里到底存了什么时间

逐行核对基线 `886cd01`（4.3 已合入）：

| 数据 | 位置 | 实际语义 |
|---|---|---|
| `usage_records.ts` | schema `usage.py:144`，落账 `usage.py:186`、`192-195` | 每次模型调用**落账那一刻**的时刻，不是 run 开始或结束 |
| `usage_records.duration_ms` | schema `usage.py:156`；计算 `usage.py:243`（回调 `:224-253`） | 单次模型调用从 `on_llm_start` 到 `on_llm_end` 的耗时（6.6 口径 A） |
| `usage_records.status` | schema `usage.py:157` | 单次模型调用成败，不是 run 终态 |
| `workflow_instances.started_at/finished_at` | schema `orchestration.py:1108-1109`；写入 `:1168`、`:1199` | 仅编排实例；普通对话 run 没有实例行，且它不覆盖非编排 run |
| `run_id` | 生成 `routes/chat.py:73`；注入 `agent.py:558-566` | 一次 `/api/chat` 请求的标识；只有标识，没有起止时间戳 |

`stream_reply`（`agent.py:538-709`）全程没有任何「run 开始/结束」落点：入口只
设置 ContextVar（`:558-566`），出口的 done 事件读取聚合结果
（`:706-708` → `usage.run_usage` `usage.py:297-311`），聚合里只有调用级字段。
因此 run 级视图能回答「模型忙了多久」，回答不了「用户等了多久」。

### 1.2 为什么端到端等待取不到

主因是**根本没记录 run 级起止**，不是数据被缓存或重试「算短了」：

1. **不能从 `MIN(ts)`/`MAX(ts)` 推导。** 首个模型调用之前还有自定义工具热
   加载（`agent.py:591`）、上下文压缩准备（`:600`）、历史写入与模型首 token
   等待；末次调用之后还有工具结果落库、编排汇总与收尾。`ts` 两端都覆盖不到，
   工具执行、编排间隙、审批等待（`:695` 的 `wait_decision`）、最多 5 轮审批
   resume（`:605`）全在 `duration_ms` 之外。
2. **不是缓存造成的假象。** 项目没有模型响应缓存；`agent.py:492-495` 是摘要
   缓存、`orchestration.py:677-689` 是工具集缓存，二者都不减少用户等待。
3. **不是自动重试造成的假象。** 没有自动模型重试；`agent.py:605` 是审批
   轮次循环，它会让同一个 run 跨多轮模型调用，但这些空闲间隔没有任何字段承接。
4. **排队不在 run 内。** 同会话请求在 `stream_reply` 之前排队等锁与租约
   （`chat.py:114-153`），而 `run_id` 在 `:73` 就已生成——「run 已存在但尚未
   开始」这段既不属于任何 `ts`，也没有起点可减。
5. **客户端中断只会更少。** 中断时 `on_llm_start` 配不上 `on_llm_end`
   （`usage.py:85-87` 的滞留条目注释、6.6 spec §2），用现有行反推只会低估。

结论：要回答「用户等待时间」，必须新增一个 run 级的起止与墙钟记录，不能靠
现有字段拼接或事后推断。

### 1.3 目标

每次真实模型 run 结束时落一行 run 级墙钟记录（run_id、起止、wall_ms、终态），
`run_usage`、`by_run` 与前端 run 视图把墙钟与 6.6 的模型调用时长**并列**输出；
写入失败不阻塞主链路；历史 run 保持「未观测」（不写 0 冒充瞬时完成）；不新增
HTTP 端点。v0.17.52 只落账并透出数据，v0.17.53 补齐既有视图的展示（§2.2）。

## 2. 需求分析与约束条件澄清

### 2.1 口径定义与终态

- **起点**：`stream_reply` 越过 Mock 分支之后、任何真实模型工作之前
  （`agent.py:574-586` 返回之后），立即取一次起始时刻并进入 `try/finally`，
  覆盖热加载、压缩与后续全部路径（见 §2.4 的包裹范围）。
- **终点**：三种终态各取一次结束时刻——正常 `done`、任一 `error` 事件、生成器
  被显式 `aclose()`。同一终态只取一次，并把同一 `finished_mono` 同时用于
  `wall_ms` 与落账，保证 done 事件与数据行同源。
- **wall_ms** = 起点与终点之间的 monotonic 差值（毫秒取整），复用
  `usage._mono`（`usage.py:83`）便于测试替换；`started_at`/`finished_at` 用
  `time.time()`，与 `usage_records.ts` 同口径。
- **落账时机**：`ok` 与 `error` 必须在 **yield 该终态事件之前** 完成
  INSERT（`await asyncio.to_thread(usage.record_run, ...)`）；`finally` 只
  兜底取消（`GeneratorExit` → `cancelled`）与未走终态捕获点的异常退出
  （→ `error`）。内存 `recorded` 标志保证一个 run 只尝试写一次。
- **审批等待计入**：`wait_decision`（`agent.py:695`）的等待计入 `wall_ms`；
  本轮不拆分 `wait_ms`，后续若要区分「模型慢」与「人在审批」另立扩展。
- **一个 run 一行**：同一 run 内的多轮模型调用、多次工具调用、审批 resume
  循环（`agent.py:605`）全部计入同一条记录，不按轮次拆分、不重复落行。
- **跨子任务**：编排子 agent 共享父 run 的 `run_id`（5.1 spec D6；
  `orchestration.py:826-829`、`:1294-1299`），父 run 墙钟天然覆盖全部子任务；
  并行时是墙钟而非各子任务相加，不为子任务另建墙钟行。
- **取消链路**：`chat.py` 的 `async for` 必须用 `contextlib.aclosing`（或等价
  的 `finally: await agen.aclose()`）显式关闭内层 `stream_reply`。现有
  `break`（`chat.py:161`）和客户端断连只结束外层 `event_stream`，不保证内层
  生成器立即进入 `finally`；不显式关闭就无法稳定落 `cancelled`。
- **不覆盖**：Mock 分支（`agent.py:574-586`）；`stream_reply` 之前的排队、
  租约超时与归属校验拒绝（`chat.py:114-153`）；自动触发的 `run_triggered`
  （`orchestration.py:1330-1378` 不经过 `stream_reply`，Q3 裁决本轮不覆盖）。

### 2.2 数据与视图

- 新增 **run 级表 `run_records`**，落 `usage.db`（与 `usage_records` 同库，
  Q4 已裁决）：`run_id`（TEXT 主键）、`user_id`、`session_id`、
  `started_at`（REAL）、`finished_at`（REAL）、`wall_ms`（INTEGER）、
  `status`（`ok`/`error`/`cancelled`）、`created_at`（REAL，可选）。建表用
  `CREATE TABLE IF NOT EXISTS`，幂等。
- **不给 `usage_records` 加列**：明细行的语义是「一次模型调用」，run 级时长
  不是调用属性；零模型调用的 run 在明细表没有行，加列必须靠 UPDATE 回填，
  聚合口径与 `failed_calls`/`calls` 会混在一起。
- `run_usage(run_id)` 增加 `wall_ms`/`started_at`/`finished_at`/`status`：
  **键固定存在，无记录时值为 `None`**（不省略键、不用 0 冒充），与 AC5/AC6
  的断言一致。**取数形态（R6）**：墙钟字段来自**独立第二次 `_query`** 直查
  `run_records`（`SELECT wall_ms, started_at, finished_at, status FROM
  run_records WHERE run_id = ?`），不得写成 `FROM usage_records LEFT JOIN
  run_records`——零模型调用的 run（`_StreamAgent`、首 token 前取消、首次调用
  前报错）在 `usage_records` 没有行，LEFT JOIN 会把 `wall_ms` 恒置为 `NULL`。
  两次 `_query` 串行调用：第一次取 `_lock`、查询、释放，第二次再取；不得把
  第二次查询嵌进同一个 `_lock` 临界区（非重入锁会自锁）。`usage_records`
  无行时聚合键仍按固定键返回（`calls=0` 等），墙钟照常来自 `run_records`。
- `summary().by_run`：在现有 `usage_records` 聚合上按 `run_id` **LEFT JOIN
  `run_records`**，新增 `wall_ms` 列。SQL 必须写死列限定，禁止沿用现有未加
  别名的写法（`usage.py:361-369` 的 `run_id`/`user_id`/`session_id`/`status`
  在 JOIN 后全部歧义，SQLite 会报 `ambiguous column name`）：

  ```sql
  SELECT u.run_id AS run_id, u.session_id AS session_id,
         u.user_id AS user_id, u.date AS date,
         COUNT(*) AS calls, SUM(u.total_tokens) AS total_tokens,
         SUM(CASE WHEN u.source='worker' THEN u.total_tokens ELSE 0 END)
             AS worker_tokens,
         SUM(u.duration_ms) AS duration_ms,
         SUM(CASE WHEN u.status='error' THEN 1 ELSE 0 END) AS failed_calls,
         COALESCE(SUM(u.prompt_cost),0) AS prompt_cost,
         COALESCE(SUM(u.completion_cost),0) AS completion_cost,
         MAX(r.wall_ms) AS wall_ms
  FROM usage_records AS u
  LEFT JOIN run_records AS r ON r.run_id = u.run_id
  WHERE u.user_id = ? AND u.session_id = ? AND u.ts >= ?
  GROUP BY u.run_id
  ORDER BY MAX(u.ts) DESC LIMIT 50
  ```

  `by_run` 的 WHERE 分支单独用 `u.` 前缀构造（total/by_user/by_session 保持
  原样）；`_COST_COLS` 在 by_run 处改为带 `u.` 的等价列。`wall_ms` 用
  `MAX(r.wall_ms)` 而非裸列，兼容后续 Postgres。
- `done` 事件里的 `usage.run` 由 `run_usage` 生成（`agent.py:743-750`），
  自动带上墙钟字段。**展示（v0.17.53 补齐）**：
  - 聊天结束的用量提示（`web/index.html` 的 `addUsageNote`）并列显示「模型耗时」
    与「端到端等待」；`wall_ms` 缺失时写「端到端等待未观测」，不写 0。
  - 「记录 → 用量」的按运行列表以 `summary().wall_runs`（`run_records` 最近
    50 条，含零模型调用的取消/失败 run）为主，合并 `by_run` 的 token 与模型
    耗时；逐条显示「完成 / 失败 / 已取消 / 状态未记录」，差集标注
    「等待时长未观测」。`by_run` 增列 `MAX(r.status) AS status`。
  - 前端零 CDN、无构建，展示文本一律 `textContent` 写入，不做 innerHTML 拼接。
- 不新增 HTTP 端点。
- **空 `run_id`**：`stream_reply` 默认空串（`agent.py:539`，测试/回放会触发）。
  `record_run` 遇到空 `run_id` 直接跳过写入，不报错、不落行（否则主键冲突后
  会被吞异常静默丢弃）。

**历史数据**：不回填。老 run 在 `by_run` 中 `wall_ms` 为 `NULL`，这是
「未观测」而不是 0（与 6.6 历史行 `duration_ms=0` 的取舍不同：0 表示「观测到
瞬时完成」，这里没有观测，不能混）。

### 2.3 与端点 P95 ≤500ms 的关系（勿混为一谈）

端点 P95 ≤500ms 是 U2 指标（`ENGINEERING-METRICS.md:68-72`），对象是 login/
health/sessions/uploads/usage 等 HTTP 端点的进程内响应时延，明确**不含模型
推理**；`/api/chat` 是 SSE 长连接，既有文档已声明不纳入该阈值
（5.1 spec:656-658）。6.8 的 `wall_ms` 是单次 run 的用户等待观测值，没有阈值、
不参与提交阻断：500ms 达标不代表用户等得短，`wall_ms` 高也不代表端点退化。
两者唯一的交集是本任务给 `/api/usage` 的 by_run SQL 加了一个按主键的
LEFT JOIN，需实测该端点 P95 仍 ≤500ms（基线 23.7ms；AC11 要求由性能脚本
内部 seed 数据后再测）。

### 2.4 约束

- **异步边界（must）**：在 async 上下文写 SQLite 必须
  `await asyncio.to_thread(...)`，不得直接同步写（`docs/CODING-STANDARDS.md:66`）。
  本轮 `record_run` 一律走线程池。
- **连接与并发**：`record_run` 沿用 `record()` 的形态（`usage.py:196-207`）：
  在 `_lock` 内 `_connect()` 新建连接、执行 INSERT、`commit`、`close`；**不
  复用跨线程连接**，所以 SQLite 默认 `check_same_thread=True` 成立，不存在
  同一连接被两个线程同时使用的问题。多次 run 同时收尾时由进程内 `_lock`
  串行；跨进程由 WAL + `busy_timeout`（`usage.py:130-136`）容忍。`record_run`
  内部不得再调用 `_query()`（它会重复获取非重入的 `_lock`，造成自锁）。
- **上下文**：`record_run(run_id, user_id, session_id, started_at,
  finished_at, wall_ms, status)` 全部走显式参数，不依赖 ContextVar——取消
  发生在请求任务收尾阶段时，旧实现依赖 `current_*` 的假设并不可靠。
- **旁路不阻塞**：`to_thread` 调用与 `record_run` 的任何异常只记类型名，
  不影响 done/error 事件与对话主链路；写失败后仍置 `recorded=True`，不在
  `finally` 重试。
- **try 包裹范围**：起点之后立即 `try:`，覆盖 `maybe_reload_custom_tools`
  （`agent.py:591`）、`prepare_compaction`（`:600`）、审批循环与 done。必须
  覆盖的终态点：循环顶栅栏失败（`:606-610`）、`SessionDeletedError`
  （`:654-659`）、通用异常（`:660-668`）、审批创建栅栏失败（`:686-690`）、
  决议后栅栏失败（`:698-700`）、正常 done（`:705-709`）。明确不覆盖：Mock
  分支与 `stream_reply` 之前的路由排队/租约拒绝。
- **三通道口径**：错误不回显原始异常；记录不含提示词、回复正文、绝对路径。
- **多用户隔离**：`run_records` 存 `user_id`/`session_id`，不新增对外查询面；
  `/api/usage` 的 user 角色强制本人过滤（`routes/usage.py:59-62`）对新增列
  继续生效。
- **兼容**：不改 6.6 的 `duration_ms`/`status` 语义与既有用例；旧库启动自动
  建表。
- **性能**：每次 run 一次 INSERT，且在线程池执行，不阻塞事件循环。

### 2.8 取消与审批等待的语义（Q1/Q2 落地）

- **取消**：客户端断连或租约被接管时，`chat.py` 显式 `aclose()` 内层
  `stream_reply`，生成器进入 `finally`，落一行 `status='cancelled'`、
  `wall_ms>0`；它不产生 `ok` 行，也不并入 `error`（失败率口径不变）。
  租约接管时路由会先给客户端一个 error 事件，但 run 的终态仍是
  `cancelled`——`status` 描述 run 怎么结束，不描述 SSE 消息类型。
  `by_run` 只展示原始 `wall_ms` 与 run 终态，不新增成功率/平均耗时聚合。
- **审批等待**：`wait_decision` 的等待计入 `wall_ms`，因此该值可以远大于
  `duration_ms` 之和，这是预期而非缺陷。本轮不做拆分；将来若运营需要区分
  「模型慢」与「人在审批」，另加 `wait_ms` 作为独立任务，本 spec 不预留该
  字段，避免当前实现为空。

### 2.10 口径边界（评审补充）

- **统计单位**：`by_run` 的一行 = 一个「有模型调用记录」的 run（源自
  `usage_records` 分组），不是「所有执行过的 run」。加 JOIN 不改变行集。
- **两集合互不包含（R4）**：`run_records` 的行集与 `by_run` 的行集不是包含
  关系，禁止用任何一方计数去推另一方。`run_records` 多出零模型调用的 run
  （首 token 前取消、首次调用前报错、会话删除中止等，`usage_records` 无行）；
  `by_run` 多出历史未观测的 run（老库无 `run_records`）、写失败的 run、以及
  本轮不覆盖的 `run_triggered` 自动触发 run。最小反例：1 个老 run、0 条
  `run_records` → `0 < 1`，所以任何固定方向的「≥/≤/==」都不成立。
- **`wall_ms` 为 NULL 的三种来源**：历史未观测（老 run 无记录）、写失败（吞
  异常后无行）、`run_triggered` 自动触发（有 usage 行但本轮不记 run 级墙钟）。
  三者不可区分，运维不得单凭 NULL 判断 6.8 是否生效。`wfr-` 前缀只是现行
  调用约定，不是协议保证：`run_triggered` 的 `run_id` 允许调用方下传任意值
  （`orchestration.py:1369`），当前唯一调用点 `server/schedulers.py:714` 固定
  生成 `wfr-`；后续新增调用方必须自行遵守该前缀，否则不能据此排除。
- **禁止跨表分母**：不得拿 `COUNT(run_records)` 当成功率分母，也不得直接对
  全表 `wall_ms` 求均值（会混入 `cancelled`/`error`/NULL）。本轮不提供任何
  成功率或平均墙钟聚合；将来若加，必须显式声明 `status='ok'` 与 NULL 处理。
- **零调用 run 的查询面**：本轮没有端点或 CLI 能列出它们，只能直查
  `usage.db`，或在代码/测试内调用 `run_usage(run_id)`（它已能按 `run_id`
  读取 `run_records`）。这是已知限制，不新增只读函数或端点。
- **空 `run_id`**：跳过写入，避免空串主键与重复写入冲突（§2.2、AC12）。

## 3. 关键技术与选型决策

| 决策点 | 候选方案 | 选定 | 取舍理由 |
|---|---|---|---|
| 数据落点 | A 新建 run 级表 `run_records`；B `usage_records` 加 `run_wall_ms` 列；C 从 `ts`/`duration_ms` 推导；D 只用 `workflow_instances` | **A** | 一行一 run、语义干净；B 会让「调用明细」混入 run 属性，零调用 run 无行、需 UPDATE 回填；C 覆盖不到工具/编排/审批（§1.2）；D 只有编排实例，普通 run 没有 |
| 计时实现层 | A `stream_reply` 内 try/finally + 统一落账；B LLM 回调层；C 路由层 | **A** | PLAN 原文；能覆盖工具执行、编排间隙与审批等待；B 只能测模型段（就是 6.6 口径 A）；C 会把同会话排队算进「run 耗时」 |
| 落账时机 | A 全部在 finally 写；B 终态 yield 前写，finally 兜底 | **B** | async generator 的 finally 在最后一个 yield 之后才执行；A 会让 done 里的 `run_usage` 读不到刚写的行，AC1 必然失败 |
| 结束时刻来源 | A 各终态各自取时钟；B 单次捕获并向下传递 | **B** | 保证 done/error 的 `wall_ms` 与数据行同源，验收可断言精确相等 |
| 视图接入 | A `run_usage` + by_run LEFT JOIN；B 新增 `/api/usage/run` 端点；C 只写 done 事件 | **A（并保留 C 的即时输出）** | 复用既有视图与权限过滤；B 新增对外接口，扩大评审与权限面，PLAN 未要求 |
| 缺失值表达 | A 0；B 键存在、值 `None` | **B** | 0 会被读成「瞬时完成」；历史与未观测必须可区分，客户端也不必处理「键时有时无」 |
| 终态枚举 | A `ok`/`error`；B 加 `cancelled` | **B（已裁决 Q1）** | 取消是独立事实，混入 error 会污染失败率，混入 ok 会虚构完成 |
| 审批等待口径 | A 计入 `wall_ms`；B 从墙钟中剔除 | **A（已裁决 Q2）** | PLAN 口径是用户等待；剔除需额外记录等待区间且会低估真实体验；未来 `wait_ms` 另立任务 |
| 写库方式 | A 事件循环内同步写；B `asyncio.to_thread` | **B（已裁决 D5）** | 编码规范 must；连接每次新建并由 `_lock` 串行，线程安全成立，见 §2.4 |
| 取消域内的终态落账 | A 直接 `await asyncio.to_thread(...)`；B `anyio.CancelScope(shield=True)` 包裹该 await | **B** | 客户端断连时 `stream_reply` 处于 anyio 取消域，`_deliver_cancellation` 每轮重投取消，取消域内任何 await 立即中止，`to_thread` 的写因此丢失（AC8a 首版实测 0 行）；shield 只保护落账这一小段，随后取消照常上抛。`anyio` 本是 starlette 的硬依赖，但本代码**直接 import** 就必须在 `requirements.txt` 显式声明：`anyio>=4.0,<5`（与 starlette 1.7.0 的 `anyio<5,>=4.0.0` 一致，不锁小版本）。另起任务/独立线程直写等写法会绕开取消域或绕开 `to_thread` 选型，不采用 |

沿用：`usage._ensure_schema` 的建表/迁移模式（`usage.py:140-173`）、
`usage.record` 的锁与连接约定（`:196-207`）、`usage._mono` 测试替换点
（`:83`）、`tests/conftest.py` 离线隔离体系。

- 执行方式：两个任务必须在同一工作树**先后落地**，后落地者负责 rebase
  `_ensure_schema`、`record()`、视图 SQL 与相关用例；不得并行修改后互相覆盖。
- 归因口径：6.7 按实例/业务对象聚合成本时，若需要墙钟，应通过
  `workflow_instances.run_id ↔ usage_records.run_id ↔ run_records.run_id`
  关联取值，不要复制第二份墙钟字段；`task_id` 的落点需在 6.7 spec 里定死。

**与 6.4（Postgres 化）**：`_ensure_schema` 是 SQLite 方言（PRAGMA、
AUTOINCREMENT、WAL，`usage.py:140-173`），6.4 的 Postgres DDL 清单**必须
显式收录 `run_records`**（列、主键、与 `usage_records.run_id` 的对齐），不能
只在口头说「随计量表适配」，否则 6.4 落地时这张表会漏。

**其他依赖**：4.1 的 `workflow_instances.started_at/finished_at`
（`orchestration.py:1108-1109`）只覆盖编排实例，不能替代 run 级墙钟；4.2 的
`run_triggered`（`orchestration.py:1330-1378`）不经过 `stream_reply`，按 Q3
裁决本轮不覆盖，后续若需要，抽同一计时器另立任务。

## 9. 风险与回归影响

- **长尾被误读**：按 Q2 裁决，审批等待计入 `wall_ms`，该值可能达到分钟/小时
  级；视图只展示不设阈值。运营若要区分「模型慢」与「人在审批」，后续另立
  `wait_ms` 扩展（本 spec 不做）。
- **取消样本**：按 Q1 裁决，取消会留下 `cancelled` 行；`wall_ms` 仍写入该行，
  但本轮不做成功率/均值聚合，`by_run` 只展示原始值，避免污染成功样本。
- **写库线程化**：`asyncio.to_thread` 只解决事件循环阻塞，不提供跨线程连接
  复用；实现必须每次在 worker 线程内新建/关闭连接并由 `_lock` 串行。若有人
  改成模块级缓存连接，`check_same_thread` 会直接报错——这是有意的保护。
- **进程被强杀**：没有 finally 就没有记录，该 run 在视图中缺失墙钟——属诊断
  数据缺失，不影响 token/金额计量，接受。
- **视图 JOIN 成本**：`run_records` 以 `run_id` 为主键、by_run 最多 50 行，
  LEFT JOIN 成本可忽略；以 AC11 的实测兜底。
- **口径漂移**：`duration_ms`（模型之和）与 `wall_ms`（端到端）并列展示，
  字段名不同、文档注明；禁止后续用 `wall_ms` 覆盖或替代 `duration_ms`，也
  禁止把 `run_records` 条数当作成功率/均值分母（§2.10）。
