# Spec — 2.3 多知识库与权限

## 1. 背景与目标

出处：docs/PLAN.md「P2 知识库问答 RAG」2.3 行（依赖 2.1 ✅、6.1 ✅）。

现状：知识库按「kb 名 → 所属包（pack.yaml `knowledge_bases`）」归属，可见范围只由
包级 RBAC 的 `allowed_roles` 控制（v0.17.18 角色维度）；`kb/common` 为平台包全员可用，
`kb/hr` 为领域包（当前未限角色，全员可见）。账号的 `department`（v0.17.11 已入库并可
随 SSO 头透传）尚未参与任何知识库可见性判定——任何角色/部门身份都能检索到全部库。

目标：**通用库 + 部门专属库并存**，按账号「部门 + 角色」双维度控制每个库的可见范围：
人事部门账号能用人事库、财务部门账号能用财务库，且**互相检索不到对方库内容**；
知识库更新后重导入索引即生效，无需重启服务。

## 2. 需求分析与约束条件澄清

**功能边界**

- 做：
  1. pack.yaml 扩展 `allowed_departments` 部门白名单字段（与既有 `allowed_roles` 并列）；
  2. 提示层（包片段）与执行层（工具调用入口）按「角色 + 部门」双维度过滤/拦截；
  3. 定位端点 `kb_allowed` 纳入部门维度（与 2.2 的角色维度同口径合并）；
  4. 新增 `auth.current_department()`（与既有 `current_role()` 同构）；
  5. 演示样例：`kb/common`（通用库，全员）+ `kb/hr`（人事部门专属）+ 新增 `kb/finance`
     （财务部门专属）三库并存，互相隔离；
  6. 知识库「重导入即生效」验证与文档。
- 不做：库级（单库）独立声明文件；一个包按不同库分部门的细粒度授权；管理界面配置；
  操作审计（另立 6.3）；kb 目录文件变更自动监听热加载（只要求 `build_kb` 重导入后生效）。

**约束（沿用项目既有安全约定）**

- **fail-closed**：`allowed_departments` 配置为非法值（非列表、空列表、含空串/超长/控制字符）
  → 整包标记 `error`、所有身份不可用，防「部门名拼错 = 永不匹配 = 静默不可用」；
  未分配部门（`department` 为空）的身份**不能命中**任何部门白名单（最小权限）。
- **向后兼容**：未配置 `allowed_departments` 字段 → 不限制部门（存量包零改动）。
- **双层拦截**：提示层过滤包片段（防误触），执行层（工具入口 guard）才是权限边界
  （防提示词注入绕过）；与 1.2 包级 RBAC 同一套设计，不改动。
- **即时生效**：角色/部门每轮动态从用户表读取，不静态快照、不缓存；调岗后下一轮即生效。
- **不泄露**：定位端点对「未声明 / 越权 / 库名非法 / 文档非法」一律 404，不区分
  「不存在」与「无权」，不回显库清单与部门清单；错误信息不含服务器绝对路径。
- **包工具自包含**：执行层拦截由 server 侧 guard 完成，不改动包内检索工具，维持
  2.2 的「包工具不 import server」AST 断言。

**待澄清问题（已在 spec 确认环节向用户核实，2026-10-18）**

- 问：部门白名单声明位置——扩展 `pack.yaml`，还是引入库级 `kb/<库名>/kb.yaml`？
  答：**扩展 `pack.yaml`**（加 `allowed_departments`）。沿用 1.2 的双层拦截与
  fail-closed 解析链路，改动最小、存量包零迁移；「一库一包」时部门边界 = 包边界。
  库级清单（一包多库按库分部门）留作后续演进项，不纳入本任务。
- 问：角色与部门同时配置时的组合语义？答：**AND**——两者都需满足才放行，
  不放宽既有角色约束。
- 问：部门值匹配口径？答：**两侧归一化**（`strip` + casefold）后比较，
  防空格/大小写差异造成静默不匹配。
- 问：admin / 开放模式（认证关闭）是否跨部门放行？答：**放行**（全局视图），
  与 1.2 中 admin 对 `allowed_roles` 的行为一致；开放模式无部门概念，等同不限制。
- 问：演示部门库命名与范围？答：**复用 `kb/hr` 作人事部门专属库（部门标识 `hr`）
  + 新增 `kb/finance` 财务部门专属库（部门标识 `finance`）**，形成 A/B 隔离对照。

**部门来源口径**：HTTP 端点（定位端点）用请求身份、**SSO 部门头优先**（与 6.1 请求级
ACL 同口径）；工具执行层用**本地用户表**（与 `current_role()`、6.2 部门报表同口径）。
两处各自与既有实现保持一致，不引入新的部门透传机制。

## 3. 关键技术与选型决策

| 决策点 | 候选方案 | 选定 | 取舍理由 |
|---|---|---|---|
| 部门白名单声明位置 | pack.yaml 扩展 / 库级 kb.yaml | pack.yaml 扩展（已确认） | 复用 1.2 双层拦截与 fail-closed 解析，改动最小、零迁移；与「库→包」归属模型一致 |
| 组合语义 | AND / OR | AND（已确认） | 部门+角色双约束不应互相放宽，安全优先 |
| 拦截层次 | 仅提示层 / 仅执行层 / 双层 | 双层（沿用 1.2） | 提示层防误触、执行层是边界，缺一不可 |
| 部门读取 | 静态快照 / 每轮实时查表 | 每轮实时（新增 `auth.current_department()`） | 调岗即时生效，无需重登/重建图 |
| 部门值匹配 | 精确 / 归一化 | 归一化（strip + casefold，已确认） | 防静默不匹配（1.2 已确立「配置错误要显式暴露」的原则） |
| admin / 开放模式 | 跨部门放行 / 同样受限 | 跨部门放行（已确认） | 与 1.2 中 admin 对 allowed_roles 的行为一致，全局视图语义统一 |
| 定位端点权限 | 新增独立判定 / 复用 role 判定并叠加部门 | 在 `kb_allowed` 内叠加部门维度 | 与 2.2 实现同函数、同 fail-closed 口径，避免两套授权逻辑漂移 |
| 与包 RBAC 关系 | 合并为一个 `pack_scope_denied` / 各自独立 | 合并为一个 scope 判定函数 | 一处判定、提示层与执行层共用，防口径漂移 |

沿用：packs.py 加载/过滤链路、custom_tools 的 `_guard_pack_tool` 包装点、auth 的
`current_role()` 上下文契约、tests/conftest.py 离线隔离体系；不引入新框架、不新增 Python 依赖。

**实现备注（定稿后补充）**：`kb_allowed(kb, role, department, packs_list)` 在
`role` 之后插入 `department`，`packs_list` 退为第 4 位关键字参数——既有调用侧
（含 2.2 用例）一律改为关键字传参，避免位置参数错位导致的静默误判。

## 4. 验收标准

| # | 标准（Given/When/Then） | 验证方式 |
|---|---|---|
| AC1 | Given 包未配置 `allowed_departments`，When 任意部门（含未分配部门）身份会话，Then 包片段与工具可用 | 单测 |
| AC2 | Given 包配置 `allowed_departments: [X]`，When X 部门身份会话，Then 包片段可见、工具可调用 | 单测 |
| AC3 | Given 同 AC2，When Y 部门身份**绕过提示层直接调用**该包工具，Then 返回权限拒绝（执行层拦截） | 单测（拒绝路径） |
| AC4 | Given 同 AC2，When Y 部门身份组装提示词，Then 该包片段不出现在提示中（提示层过滤） | 单测（拒绝路径） |
| AC5 | Given 同 AC2，When 身份 `department` 为空（未分配），Then 该包不可用（fail-closed） | 单测（拒绝路径） |
| AC6 | Given `allowed_departments` 为 `[]` / 非列表 / 含空串 / 超长 / 控制字符，When 加载包，Then 整包 `status=error`，所有身份不可用 | 单测（fail-closed） |
| AC7 | Given 包同时配置 `allowed_roles` 与 `allowed_departments`，When 身份只满足其一，Then 拒绝；两者都满足才放行（AND） | 单测 |
| AC8 | Given 运行中会话的人事部门账号改用财务部门（调岗），When 进入下一轮，Then 财务库由不可用转为可用、人事库相反，无需重启/重登 | 单测 |
| AC9 | Given 财务部门账号，When 请求人事库原文定位 `GET /api/kb/source?kb=hr...`，Then 404（不暴露库清单）；请求本部门库则正常返回 | 单测（拒绝路径） |
| AC10 | Given 服务运行中，When 通过 `tools/build_kb.py` 重导入某库索引，Then 同一会话下一次检索即命中新内容，无需重启 | 单测（工具按调用打开索引） |
| AC11 | Given admin 角色或开放模式（认证关闭），When 任意部门身份，Then 跨部门放行（全局视图） | 单测 |
| AC12 | Given 三库并存（common 全员 / hr 仅人事 / finance 仅财务），When 各身份检索，Then 通用库人人可用、部门库仅本部门可用且互不可见；包工具自包含 AST 断言（2.2 既有用例）持续通过 | 单测 + 回归 |

安全/拒绝路径：AC3/AC4/AC5/AC6/AC7/AC9 成对覆盖提示层与执行层、未分配部门、
非法配置与定位端点枚举旁路的拒绝侧，不留放行-only 盲区。

测试对应：`tests/test_kb_permissions.py`，用例名与 AC 编号对应
（`test_ac1_unset_departments_all_allowed`、`test_ac3_other_dept_call_denied` …），
spec 确认后先写用例跑红，再实现转绿。
