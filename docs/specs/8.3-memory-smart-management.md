状态：**草稿待确认**

依赖：8.1 已交付（v0.20.0，user_memories 表 + save_memory 工具 + 记忆管理页签）

## 1. 背景与目标

8.1 交付的「显式指令 + 全量注入」基线存在三个问题：

1. **重复记忆**：用户可能多次说「记住我喜欢中文」，产生语义相同但表述略异的冗余记录。
2. **过期记忆残留**：`expires_at` 字段已定义但无自动清理机制，过期记忆仍占用数据库空间。
3. **注入量粗粒度**：当前按 token 截断（`MEMORY_MAX_TOKENS=2000`），可能切断关键记忆或注入无关条目。

本项补「**记忆智能管理**」：相似记忆合并去重、过期记忆自动清理、注入策略优化（分类加权 + 相关性筛选）。

目标版本：v0.21.0（新增去重/清理逻辑 + 注入策略优化）

## 2. 需求分析与约束条件澄清

### 2.0 业界方案对照（2026-11-22）

| 方案 | 去重机制 | 过期清理 | 注入策略 | 对本项启发 |
|---|---|---|---|---|
| **Mem0** | 向量相似度 + LLM 判重 | TTL 字段 + 后台任务 | 向量检索 + top-K | 向量检索过重（内网部署难）；LLM 判重成本高；降级为规则去重 |
| **Letta** | Agent 自主合并（工具调用） | 手动归档 | 分层注入（core/archival） | Agent 自主合并本轮不做；分层注入可借鉴（按分类加权） |
| **Zep** | 时序图节点 supersede | 边带有效期，自动失效 | 图遍历取相关子图 | supersede 语义清晰（新记忆覆盖旧）；图数据库过重，降级为标记替换 |
| **ChatGPT** | 用户手动编辑 | 不支持自动过期 | 全量注入 saved memories | 初版简单，后期 dreaming 才做自动合并；本轮做轻量规则去重 |
| **Claude** | 用户手动编辑 | 不支持自动过期 | 项目级隔离 + 全量注入 | 项目级隔离过重；手动编辑是兜底，自动清理是增强 |

**共识**：
- **去重是增强而非必须**：ChatGPT/Claude 初版均不做，依赖用户手动编辑；Mem0 自动合并是差异化能力但复杂度高
- **过期清理必要**：Zep 时序图、8.1 spec 已定义 expires_at 字段；自动清理避免脏数据积累
- **注入策略需平衡**：全量注入简单但可能挤占窗口；向量检索精准但部署成本高；分类加权 + 关键词匹配是轻量折中

### 2.1 功能边界

- **相似记忆合并**：写入新记忆时，检测同用户同分类下语义相似的记忆（基于关键词重叠度），提示用户选择「合并替换旧记忆」或「保留为新条目」。
- **过期记忆自动清理**：每日定时任务（或启动时）扫描 `expires_at < now` 的记录，物理删除（硬删除，同 8.1 手动删除口径）。
- **注入策略优化**：按分类加权（preference > project > fact > context），同分类内按 `updated` 倒序；超过 token 上限时优先保留高权重分类。
- **明确不做**：
  - 不做向量相似度检索（需 embedding 模型，内网部署成本高，与 2.1 RAG 职责重叠）
  - 不做 LLM 判重（每轮调用 LLM 成本高，降级为规则去重）
  - 不做记忆版本历史（合并时直接替换，不保留旧版本）
  - 不做记忆自动提取（8.1 已明确显式指令是基线，自动提取留待后续）

### 2.2 约束

- **去重规则简单可解释**：基于关键词重叠度（如「中文」和「中文回复」视为相似），不用黑盒语义模型。
- **用户可控制**：合并提示由用户确认（不自动合并）；过期清理在控制台可见（显示「已清理 N 条过期记忆」）。
- **性能**：去重检测在写入时同步执行（同用户同分类记忆数通常 <100，遍历成本可忽略）；过期清理任务异步执行，不阻塞主链路。
- **数据库兼容**：不新增字段；复用 8.1 的 `expires_at` 字段；清理任务兼容 SQLite/Postgres。
- **审计**：合并操作记审计日志（action=memory_merge，target=新记忆 ID，detail=被合并的旧记忆 ID 列表）；过期清理记系统审计（actor=system）。

### 2.3 待澄清问题

**Q1 相似度判定规则**（已确认 2026-11-22）：
- 方案 A：关键词完全匹配（如「中文」≠「中文回复」，误判少但漏判多）
- 方案 B：关键词包含关系（「中文」包含于「中文回复」，轻量但可能误合并「我喜欢中文」和「我讨厌中文」）
- 方案 C：编辑距离 ≤2（如「中文」vs「中问」，成本高且对中文不友好）

**结论：B**（包含关系 + 同分类约束，轻量可解释；误合并风险由用户确认环节兜底）。缩写/同义词场景（PostgreSQL vs PG）明确漏判，靠人工在控制台手动管理；LLM 判重列入 PLAN 后续迭代（8.5）。

**Q2 过期清理触发时机**（已确认 2026-11-22）：
- 方案 A：启动时清理（服务重启时执行一次，简单但依赖重启频率）
- 方案 B：每日定时任务（APScheduler 或 asyncio.create_task，需引入调度依赖）
- 方案 C：惰性清理（查询时过滤，不物理删除；但脏数据积累影响性能）

**结论：A**（8.1 已惰性过滤过期记忆，本轮补启动时物理清理；B 作为后续增强）。

**Q3 合并交互方式**（已确认 2026-11-22，结合用户画像修正）：
- 方案 A：写入时同步提示（save_memory 工具返回「检测到相似记忆 ID=123，是否合并？」，用户回复确认）
- 方案 B：控制台页面提供「合并建议」列表（管理员/用户手动选择合并）
- 方案 C：后台自动合并（高风险，违反「用户可控」原则）

**结论：A + B 双通道**（用户画像：最终用户是 FDE/业务用户，非技术人员）：
- **FDE/业务用户**：对话流内提示合并建议（save_memory 返回相似记忆提示，用户回复「合并」或「保留」），一键确认，零学习成本
- **技术人员**：控制台「合并建议」列表，供排查/批量管理用（面向研发人员，不影响最终用户）

### 4.1 相似度检测（server/memories.py）

```python
def find_similar(user_id: str, content: str, category: str) -> list[dict]:
    """查找同用户同分类下关键词重叠的记忆（轻量规则，非向量检索）。"""
    keywords = _extract_keywords(content)  # 提取名词/动词（简单分词或 jieba）
    all_memories = list_all(user_id, category=category)
    similar = []
    for mem in all_memories:
        mem_keywords = _extract_keywords(mem["content"])
        overlap = keywords & mem_keywords
        if len(overlap) >= 2 or any(k in mem["content"] for k in keywords):
            similar.append(mem)
    return similar
```

### 4.2 过期清理（server/memories.py）

```python
def cleanup_expired() -> int:
    """删除已过期记忆（expires_at < now）。返回删除条数。"""
    now = time.time()
    conn = db.connect("state")
    cur = conn.execute(
        "DELETE FROM user_memories WHERE expires_at IS NOT NULL AND expires_at < ?",
        (now,))
    conn.commit()
    deleted = cur.rowcount
    if deleted > 0:
        audit.log("system", "", "memory_expire", detail=f"deleted={deleted}")
    return deleted
```
