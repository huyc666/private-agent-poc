# Spec — 6.7 run ↔ 业务对象归因（task_id）

状态：**已交付（v0.19.0）**
流程档位：PLAN 功能（M）；裁剪：无（纯后端/API 响应扩展，不触发页面关卡）
spec 独立评审：**触发**（新增数据列/索引/兼容迁移，并扩展 `/api/usage` 响应结构）
出处：`docs/PLAN.md:70`（优先级 18，M，验收「一次流程执行的多次 run 带同一
task_id，按实例聚合出总成本」）
依赖：4.1 已交付 `workflow_instances` 实体；6.4 已交付 SQLite/Postgres 统一适配

## 1. 背景与目标

当前计量只有 `user_id / session_id / run_id`。一次流程执行虽然有稳定的
`workflow_instances.instance_id`，但模型调用用量没有持久化这个业务对象 ID；
跨多次 run、或后续执行拆分为多个 run 时，无法直接回答「这件事花了多少」。

6.7 在 `usage_records` 增加 `task_id`，并把 `task_id` 固定为
`workflow_instances.instance_id`；编排执行期间通过请求上下文向下传递，使同一
流程实例的全部模型调用落在同一业务对象下，并在用量聚合中按实例输出总成本。

目标版本：v0.19.0（新增对外 API 响应结构与数据列）

## 2. 需求分析与约束条件澄清

### 2.1 功能边界

- **实体口径**：`task_id = workflow_instances.instance_id`。不新建任务表、
  不生成第二套任务 ID、不把审批单作为本轮归因对象。
- **数据列**：`usage_records` 增加 `task_id TEXT NOT NULL DEFAULT ''`；
  普通对话与历史行保持空字符串，不改变既有口径。
- **写入路径**：`run_orchestration()` 创建实例后，在执行期间设置
  `usage.current_task`；`run_triggered()` 使用同一机制。`record()` 读取该
  ContextVar 并写入 `task_id`。
- **上下文边界**：`run_orchestration()` / `run_triggered()` 在创建实例后执行
  `token = usage.current_task.set(instance_id or "")`，并把 `execute()` 包入
  `try/finally token.reset()`；即使模型调用失败、流程取消或实例写入失败，也必须
  恢复进入编排前的原值。
- **聚合输出**：`usage.summary()` 新增 `by_task`，仅聚合 `task_id <> ''` 的
  行，输出 `task_id / calls / runs / token / cost / total_cost`；沿用现有
  `/api/usage` 权限与过滤逻辑，不新增独立端点。
- **兼容迁移**：SQLite 老库启动时惰性补列；Postgres schema 幂等补列；
  `tools/migrate_db.py` 继续动态按源列复制，老源库缺列时目标默认空字符串。
- **明确不做**：不改 `run_records` 表；不改流程实例表；不做任务管理页面；
  不为审批单、单次聊天或手工工具调用虚构 `task_id`。

### 2.2 约束

- **旁路不阻塞**：实例行创建失败时现有行为是记录异常并继续执行；此时
  `task_id` 为空，模型调用与主流程不得因归因失败被阻塞。
- **多用户隔离**：`by_task` 继承 `/api/usage` 现有 ACL。user 角色仍被强制
  只看本人数据；admin/approver 与开放模式沿用现口径。`task_id` 本身不包含
  路径、提示词或敏感值。
- **上下文隔离**：`task_id` 在编排执行结束后恢复原值，避免同一请求后续工具
  调用误挂到上一个流程实例；同一执行内的多次模型调用/多个 run 共享同一值。
- **数据库兼容**：新增 SQL 需同时兼容 SQLite 与 PostgreSQL；`GROUP BY`
  不引入裸列问题；`by_task` 需要索引支撑。
- **迁移安全**：老数据 `task_id=''`；不得因补列失败丢账；Postgres 旧 schema
  必须可幂等升级。`db.ensure_postgres_schema()` 不能只重放建表 DDL；对已存在的
  `usage_records` 必须执行
  `ALTER TABLE usage_records ADD COLUMN IF NOT EXISTS task_id TEXT NOT NULL DEFAULT ''`
  并创建 `idx_usage_task`。
- **依赖**：不新增 Python 依赖，`requirements.txt` 不变，无需 pip-audit 增量。

### 2.3 待澄清问题

无。用户已接受「`task_id` 直接绑定流程实例 ID，不新建任务实体」的口径；
其余行为由 PLAN 验收标准与现有架构约束决定。

### AC 明细

**AC1 schema**：Given 老 SQLite 用量库，When 初始化 usage schema，Then
`usage_records` 幂等补 `task_id TEXT NOT NULL DEFAULT ''` 与
`idx_usage_task`，老行值为空且不丢数据；Postgres DDL 同样包含列与索引。
契约测试必须覆盖「已存在 6.4 旧表 → `ensure_postgres_schema()` → 列/索引存在」。

**AC2 计量写入**：Given `usage.current_task` 设置为 `task-A`，When
`record()` 落一条模型调用，Then `usage_records.task_id='task-A'`；未设置时为
空字符串。

**AC3 手动编排**：Given `run_orchestration()` 成功创建实例
`instance-1`，When 执行内发生多次模型调用（可用不同 `run_id` 模拟），
Then 所有 `usage_records.task_id='instance-1'`，且执行结束后上下文恢复原值。

**AC4 自动编排**：Given scheduler 调用 `run_triggered()`，When 执行成功，
Then 实例行、模型调用行与同一 `instance_id` 对齐；取消/失败路径同样保留已发生
调用的归因。

**AC5 实例成本**：Given 同一 `task_id` 下两个 `run_id` 各落一条用量，When
查询 `usage.summary()["by_task"]`，Then 输出 `runs=2`、调用数/token/金额合计
正确，并包含 `total_cost`；只统计非空 `task_id`。

实现必须固定为以下投影语义（方言只差占位符；所有过滤条件均用 `u.` 前缀）：

```sql
SELECT u.task_id AS task_id,
       MAX(u.user_id) AS user_id,
       MAX(u.session_id) AS session_id,
       COUNT(DISTINCT u.run_id) AS runs,
       COUNT(*) AS calls,
       SUM(u.total_tokens) AS total_tokens,
       SUM(u.prompt_tokens) AS prompt_tokens,
       SUM(u.completion_tokens) AS completion_tokens,
       SUM(u.duration_ms) AS duration_ms,
       SUM(CASE WHEN u.status='error' THEN 1 ELSE 0 END) AS failed_calls,
       COALESCE(SUM(u.prompt_cost),0) AS prompt_cost,
       COALESCE(SUM(u.completion_cost),0) AS completion_cost
FROM usage_records AS u
WHERE u.task_id <> ''
  [AND u.user_id = ?]
  [AND u.session_id = ?]
  [AND u.ts >= ?]
GROUP BY u.task_id
ORDER BY MAX(u.ts) DESC
LIMIT 50
```

`total_cost` 由 `prompt_cost + completion_cost` 在返回前按现有口径补齐。

**AC6 兼容与权限**：Given 普通对话或历史行 `task_id=''`，When 查询
`/api/usage`，Then 不出现在 `by_task`，既有 `total/by_user/by_session/by_run`
不变；user 角色仍只能看到本人 `by_task` 数据。

**AC7 旁路失败**：Given `workflow_instances` 写入失败返回 `None`，When 编排
继续执行并落模型调用，Then `task_id=''`、主流程不抛异常、不虚构实例 ID。

**AC8 Postgres**：Given 6.4 的 PG schema，When 执行幂等升级，Then
`usage_records.task_id` 与索引存在；`by_task` SQL 在 PostgreSQL 下合法，不出现
`GROUP BY` 裸列问题；测试必须证明已存在的旧表也会被补列，而不是仅验证新建
表 DDL。

**AC9 回归**：全量默认测试通过，且不低于当前基线（6.4 后约 1208 passed /
26 skipped，真实 PG 门控另行按 `RUN_PG_TESTS=1` 执行）。
