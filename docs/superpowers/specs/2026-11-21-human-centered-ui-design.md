# Human-Centered UI 工作流设计

日期：2026-11-21

## 1. 目标

建立一个个人 Codex Skill，以统一入口串联「方向、品味、审计、自检」，同时允许四阶段独立执行。它帮助设计者减少软件界面的模板感和 AI 味，提高任务适配、审美与完成度，不把审美简化为禁用渐变、圆角或某种配色的机械规则。

PAP（本仓库）作为首个检验项目：实际改造聊天首页和管理控制台，保留现有业务、权限、接口与离线零 CDN 约束，以真实浏览器截图和交互检查形成前后对比。

## 2. 范围与原则

- 新 Skill 位于 `C:\Users\Lenovo\.codex\skills\human-centered-ui`，允许自动发现。
- 统一入口支持完整流程与 `direction`、`taste`、`audit`、`self-check` 四种单阶段模式。
- 阶段交接采用可复用设计简报、证据与检查结果，不依赖临时聊天记忆。
- 设计判断与可自动验证的事实分开。没有真实运行或截图证据时，明确标为未检查。
- 复用现有能力，不复制第三方 Skill 全文。专家模块可插拔，缺失不阻塞核心流程。
- PAP 只改 UI/UX 与必要的前端无障碍语义，不顺手重构后端或重做整个产品。

## 3. 架构

```text
用户请求
   │
   ▼
human-centered-ui/SKILL.md（目标、路由、共享约束）
   │
   ├── direction ── 用户任务、页面职责、优先级、约束、验收条件
   ├── taste ────── 有依据的视觉语言、文案、密度、动效与关键决策
   ├── audit ────── 真实流程、截图、问题证据、严重度、修改建议
   └── self-check ─ 任务、响应式、键盘、状态、视觉对比、未验证边界
          │
          ▼
references/experts.md（现有 Skill 与 Playwright 的可选适配约定）
```

`SKILL.md` 只保存路由与共享原则。各阶段的操作细则放入独立参考文件，只在对应阶段读取。PAP 的实施和测试文件仍留在 PAP 项目中，个人 Skill 不耦合某个项目路径。

## 4. 四阶段契约

### 4.1 方向

先查看现有页面和真实用户任务。输出：

- 目标用户、使用环境和关键任务。
- 每个页面唯一的首要职责，以及主要、次要、辅助信息。
- 必须保留的产品约束、明确不做的内容。
- 可由人观察的验收条件。

缺少信息但不妨碍推进时，采用并记录合理假设；只有不同答案会显著改变产品结构时才询问。

### 4.2 品味

将方向落实为紧凑的设计决策，而不是先选流行模板：

- 从业务内容、用户心智和使用环境中推导视觉语言。
- 明确字体层级、颜色用途、间距与密度、布局、状态、文案和动效。
- 对关键选择写出「为何适合此产品」，删除无功能的装饰。
- 不把奶油底配衬线字、黑底荧光色、报刊风、蓝紫渐变等当成通用默认，也不绝对禁止。

`frontend-design` 用于强化独特且有依据的审美决策；`Taste Skill` 用作质量判断的可选参考。两者不可用时，核心阶段仍按上述契约执行。

### 4.3 审计

先审计再改造。审计对象必须是真实运行页面、代码和关键流程：

- 为每一步保存截图，并实际查看截图，拒绝空白、加载中或错误状态。
- 发现必须关联页面、流程步骤、截图或代码位置。
- 分别标记 UX、视觉、无障碍和完成度问题，按影响与频率排序。
- 给出高影响优先修改项，同时列出值得保留的设计。
- 截图不能证明完整无障碍合规；键盘、读屏等需要独立检查。

`impeccable` 用于可选的完成度审计；`web-design-guidelines` 用于 Web 规范复核。外部规则与产品意图冲突时，解释取舍，不盲目照单全收。

### 4.4 自检

优先使用 Playwright；工具不可用时降级为实际可用的浏览器证据，并披露限制。检查：

- 关键任务能完成，操作反馈、空态、加载、错误和危险操作清楚。
- 桌面与窄屏没有非预期溢出、遮挡或不可达控件。
- 键盘焦点可见、顺序合理，表单有可访问名称，弹窗能退出。
- 控制台错误、请求失败和视觉回归有记录。
- 前后截图使用相同页面、视口和可比状态。

最终报告区分通过、失败、未检查，不把自动评分器当作审美裁决。

## 6. PAP 检验与实施边界

### 6.1 基线审计

- 启动本地服务，使用测试凭据或项目既有 mock 能力进入真实页面。
- 检查聊天首页的空会话、消息/输入区和历史面板；控制台的用户列表、筛选/管理操作和审计日志。
- 保存 1440×900 桌面截图和必要的窄屏截图。
- 将发现关联到 `web/index.html`、`web/console.html`、`web/tokens.css`。

### 6.2 改造

- 建立更明确的产品身份和内容层级，让聊天与管理任务优先于装饰。
- 评估并减少无意的蓝紫渐变、过量徽章、重复卡片和过圆容器；根据证据而非禁令决定保留或替换。
- 优化欢迎区、输入区、状态反馈、表格信息密度、筛选区和危险操作的视觉权重。
- 使用用户可理解的动作和结果文案，保持同一操作全程命名一致。
- 保留所有既有 DOM 功能挂钩、后端接口、权限与业务流程。
- 沿用原生 HTML/CSS/JavaScript，保持离线运行，不引入框架或 CDN。

### 6.3 验证

- Playwright 驱动相同流程，保存前后对比截图。
- 检查桌面与 390px 窄屏、键盘导航、主要空态/错误态、弹窗关闭和控制台错误。
- 运行受影响的前端/服务端测试，再运行项目全量离线回归。
- 输出报告，包含：基线发现、设计决策、实际改动、截图、通过/失败/未检查项、残余风险。

## 8. 验收标准

1. Skill 可由统一描述自动发现，四阶段均可独立运行，且各阶段引用可发现。
2. Skill 不强制依赖任何可选专家，不宣称截图等于完整审计或无障碍合规。
3. PAP 两页有真实基线截图和修改后截图，视觉变化有用户任务依据。
4. 现有业务与权限行为不回归；页面仍无 CDN 依赖。
5. 桌面、窄屏、键盘与关键状态有实际验证证据，未验证项目明确列出。
6. Skill 结构校验、相关测试和全量离线回归通过；若存在既有失败，单独记录，不顺手修复无关问题。
