# Spec First + TDD

本仓库的研发流程约定：PLAN.md（docs/PLAN.md）任务与安全加固等工程变更按「任务档位与裁剪」确定档位；需要 spec 的档位，编码前必须先有 spec，spec 确认后按测试驱动开发（TDD）——先写测试、后写实现。spec 是开发契约，测试是验收标准的可执行形式。

**带页面的功能**（Web 控制台、前端页面、交互界面等）在标准流程上叠加两道人工关卡：spec 确认后先出**页面原型**（调用原型设计 skill，如 trae-design:solo-design）经人工审核再开发；实现完成后做**页面功能展示与人工测试**，通过后才进入代码评审（页面实现可调用 frontend-design skill 保证质量）。

流程骨架对齐 GitHub spec-kit 的 SDD（specify → clarify → plan → tasks → implement → converge），按本项目规模做了轻量化裁剪：宪法内嵌于本 skill、plan 并入 spec 第三部分、tasks 由 TDD 用例承担，另吸收其质量闸门——spec 自检与一致性分析合并为「契约关」，收敛判定改为「兑现关」，两关共用一张 AC 账本。

## 项目宪法

以下原则一次成文、长期有效，spec 的技术选型、测试设计、代码评审与兑现关都以此为对照基准；与宪法冲突的决定须在 spec 中显式声明并说明理由，否则视为无效：

1. **fail-closed 安全**：认证/权限/沙箱默认拒绝；前端隐藏入口只是体验层，服务端判定才是防线
2. **敏感值红线**：明文密码/Key 绝不进日志、审计、错误响应或复存；文件名等审计目标只存域内相对路径
3. **旁路不阻塞**：审计、遥测等旁路写入失败只自吞异常打印类型名，不得阻塞登录、对话等主链路
4. **多用户隔离**：文件分域、会话/数据默认仅本人可见（admin 例外须明写）；身份采用不可变快照模型——HTTP 层解析一次产出 `usage.Identity` 快照并向下显式传递，执行层禁止按用户名重查本地表，禁止依赖隐式 ContextVar 共享
5. **测试即验收**：用例命名与验收标准编号对应（`test_acN_*`）；拒绝路径（401/403/400/路径穿越/越权）必须成对覆盖；测试须造数据覆盖非空路径（空表循环体不执行曾漏掉真机 500）
6. **POC 取舍基线**：单机低频场景；为可读性/一致性接受已测量的低危开销（如审计写入全表 COUNT 对齐 login_fails 先例），性能优化以实测数据为准不凭感觉
7. **文档口径**：README 版本记录只写功能不写技术细节；push 恒由用户操作；提交按「成对提交」——功能 commit 在前（spec + 测试 + 实现 + README），评审/复核报告单独 `docs` commit 在后并在 message 中引用被评审 commit 的短 hash，两个 commit 同批推送、不跨版本积压；编码前的 spec 评审报告例外，独立成 `docs` commit 先行。理由：功能 commit 须可独立回滚与 bisect，报告混入会连带回滚审计记录、污染代码路径 log；报告须引用被评审 hash，且必然晚于功能 commit 产生，合并只能靠 amend 或预判结论。本条优先于其他文档中的旧表述

## 流程

1. **定位任务**：读 docs/PLAN.md，找到用户指定的任务编号，完整读取该行任务的内容要点、依赖、规模、验收标准与来源。
2. **必要的背景调查**：spec 涉及现有代码的，先读相关模块再写 spec；不基于猜测写现状描述。
3. **写 spec**：新建 `docs/specs/<任务号>-<短名>.md`（如 `6.2-usage-report.md`），固定四部分结构：

   ```markdown
   # Spec — <任务号 任务名>

   ## 1. 背景与目标
   简要（5 行内）：为什么做、做完是什么样子。引用 PLAN 行作为出处。

   ## 2. 需求分析与约束条件澄清
   - 功能边界：做什么、明确不做什么
   - 约束：安全约定（fail-closed/恒时比较/不回显原始异常等）、多用户隔离、
     性能、兼容性——凡受本项目宪法与既有约定影响的都列明
   - 待澄清问题：有歧义处逐条列出，先向用户提问，禁止擅自假设；无歧义写「无」

   ## 3. 关键技术与选型决策
   每个决策点给候选方案、选定的一个、取舍理由；遵循既有架构时写明「沿用 X」
   及理由，不为了新而新。

   ## 4. 验收标准
   条目化、可检验（Given/When/Then 或等价表述）；覆盖功能、边界与拒绝路径；
   注明每条用什么方式验证（单测/集成测/手工实测）。完成后逐条对照汇报。
   ```

   填写粒度与实际效果参照示例：`references/example-spec.md`（以已交付的 1.2
   包级 RBAC 为实例），写 spec 时参照其粒度，不照抄内容。

   spec 在四部分之外必须带固定追加节（新建 spec 生效，历史 spec 不回改）：
   §4.1 AC 账本 + §5 红测试清单 + §6 红运行记录（命令、基线 passed/skipped、
   失败分类与预期对照）+ §7 收敛结论；评审/整改记录从 §8 起按轮次追加。账本格式：

   ```markdown
   ### 4.1 AC 账本
   | AC | 验证方式 | 用例/留证 | 红态 | 实现证据 | 收敛 |
   |---|---|---|---|---|---|
   | AC1 | 单测/集成测/手工实测 | `test_ac1_*` 或留证形式 | 红态结果 | `文件:行号` | ✅/❌ |
   ```

   **澄清回写纪律（吸收 spec-kit clarify）**：用户的澄清回答必须回写进 spec 对应条目（如 Q1-Q4 问答复核后落入正文），不得只留在对话记录里——后续阶段只认 spec 文本。歧义面大时可多轮澄清，每轮 ≤5 个聚焦问题，收敛后再进入下一步。
4. **契约关·第一动作：spec 自检（吸收 spec-kit checklist——「需求的单元测试」）**：呈现用户确认前，对 spec 本身做一轮质量检查，结论填入 §4.1 账本：
   - **名词核对**：spec 中出现的函数名/端点/表名/工具名逐一与代码现状核对（grep 确认存在，或确认是「待新建」）——6.3 曾因 spec 写 `do_write` 而实际函数是 `save_output_file`，导致实现漏接
   - **AC 可检验性**：每条验收标准都能给出验证方式，无「工作正常」式表述；同时填账本「验证方式」列，手工实测/回归须写明留证形式
   - **覆盖完备**：功能/边界/拒绝路径都有对应 AC；spec 承诺的每个触点（该记审计的、该校验的）都出现在 AC 中
   - 自检发现的缺口先补进 spec，再请求确认；「验证方式」列无空、全部可检验，契约关前半通过
4a. **编码前 spec 独立评审（按档位触发）**：命中「任务档位与裁剪」所列触发条件时，spec 自检后、请求确认前，由新会话独立代理只读评审 spec（不动文件、不做产品决策）：产出 `docs/reviews/YYYY-MM-DD-plan-<任务号>-spec-review.md`，含 P0/P1/P2 问题表（带行号证据）、「不成立/误报」区、结论（通过/有条件通过/退回）。P0/P1 必须修复或在 spec 写明拒绝理由后才能请求确认；需用户拍板的写成待裁决项并入确认包。未触发时在汇报声明「spec 独立评审：未触发（原因）」。
5. **请求确认**：把 spec 全文或要点呈现给用户，明确说「确认后先写测试再编码」；已触发独立评审的，一并呈现其结论与整改情况。用户修改意见先落回 spec 再确认。
6. **页面原型（仅带页面的功能）**：spec 确认后、写测试之前，调用原型设计 skill（如 trae-design:solo-design）依 spec 出页面原型（布局、字段、交互状态、各角色可见性），呈现给用户人工审核；审核意见先落回原型再定稿。原型未经用户审核通过，不得进入 TDD。纯后端/CLI/工具类任务跳过此步。
7. **契约关·第二动作：测试先行（红）+ 红态一致性（吸收 spec-kit analyze）**：原型通过（纯后端任务则 spec 通过）后、写任何功能代码之前，把验收标准逐条转为测试用例——
   - **功能测试**：主路径 + 边界值 + 异常输入，命名与验收标准编号对应（如 `test_ac3_xxx`）
   - **安全测试**：本仓库拒绝路径必须成对覆盖（越权访问、路径穿越、超限、fail-closed、未授权令牌等，参照 spec 第 2 部分列出的约束）
   - 离线可跑为主（沿用 tests/conftest.py 隔离体系）；需真实环境的走既有门控（RUN_LLM_TESTS / RUN_DOCKER_TESTS）
   - 跑一遍确认新用例按预期失败（红），失败原因与 spec 预期一致
   - **红态一致性（只读）**：确认「每条 AC ↔ 至少一个验证项」双向无孤儿——自动用例按 `test_acN_*` 对应；标注「手工实测」的 AC 须有可复核的留证（执行记录/清单勾选），不以「无单测」判为缺口；无验证项或验证项无对应 AC 的都要补齐或说明。测试引用的模块/函数/端点名与代码现状一致。把「用例/留证」「红态」填入 §4.1 账本，并写入 §5 红测试清单、§6 红运行记录（命令 + 基线 passed/skipped + 失败分类与预期对照）。前三列无空、无孤立测试，契约关通过；发现问题回到 spec 或测试修正源头，不做实现侧迁就
8. **开发实现（绿）**：以让测试通过为完成定义来编码；不为未出现的用例过度设计。带页面的功能按已定稿原型实现 UI（可调用 frontend-design skill），页面行为不偏离原型；实现若需偏离，先回到用户确认。全部新用例转绿后跑全量回归，确认无既有用例破坏。
9. **页面功能展示与人工测试（仅带页面的功能）**：全量回归通过后、代码评审之前，真实启动服务展示页面功能（按原型逐项演示主要交互与边界状态），交用户人工测试；用户确认通过才进入代码评审。纯后端/CLI/工具类任务跳过此步。
10. **兑现关（原收敛判定，吸收 spec-kit converge）**：代码评审之前、回归通过之后，对照 spec 逐条核对实现收敛，结论写入 §7：
    - 验收标准逐条在代码/测试中确认兑现（给出文件:行号证据，并填入 §4.1「实现证据/收敛」列）
    - spec 第 2 部分承诺的全部触点与行为逐项 grep 确认存在（如「文件写/删都记审计」须两个写路径都能找到 audit 调用）
    - 输出收敛结论：全部满足 → 进入代码评审；存在缺口 → 生成补救任务清单（只增不删），实现清零后重新兑现判定——**未兑现不进评审**（6.3 的「工具级写入漏审计」正是此步应提前抓住的缺口，当时拖到评审才暴露）
11. **代码评审（含触发式复审）**：全量回归、（如适用）页面人工测试、兑现关通过后、提交之前，对本次变更执行一次通用代码评审，产出结构化问题清单（正确性、安全边界与拒绝路径、可维护性、性能）。执行方式：调用 TRAE-code-review skill 对本次变更差异评审。满足以下任一条件时，修复后执行**复审**——首轮有 P0；≥2 项 P1；修复触及安全边界（认证/权限/沙箱/文件隔离等）；修复净改动超过 100 行或 3 个文件；改法与评审建议不一致。复审由新会话独立代理执行，产出 `docs/reviews/YYYY-MM-DD-v0.17.xx-<修复后短hash>-rereview.md`，只查「上轮问题是否关闭 + 本轮新改动有无新 P0/P1」，不重审未触碰代码。**复审最多 2 轮**：每轮 P0/P1 必须严格减少，出现新 P0 或数量不降即停止并交用户裁决（接受并记录 / 继续 / 缩减范围）；新增 P2 记入 PLAN 后续待办，不延长本轮。评审确认的问题修复后重跑全量回归，复审本身不改代码不重复跑；判定为误报或有意保留的，在汇报中写明理由。评审与复审结论（发现问题数、修复情况、触发或未触发）随本次提交一并汇报。
12. **收尾**：实现若偏离 spec（选型变化、砍范围），先更新 spec 并说明。提交按「成对提交」：功能 commit（spec + 测试 + 实现 + README）在前，评审/复核报告单独 `docs` commit 在后并引用被评审 commit 短 hash，同批推送、不跨版本积压（编码前的 spec 评审报告例外，先行独立 `docs` commit）。汇报首行写明「流程档位/裁剪」与「spec 独立评审、复审：触发或未触发」；按验收标准逐条对照；PLAN 行同步标注交付状态。

## 任务档位与裁剪

按任务形态选择关卡（「条件」由实际改动决定；「免」必须在 spec 头部、无 spec 时在交付汇报声明）：`流程档位：<类型>；裁剪：<关卡清单>（原因）`。声明与实际改动不符按代码评审 P1 处理；安全加固档不可裁剪。页面关卡按三分口径判定：①页面结构、交互流程、信息架构变化 → 全关卡（原型 + 人工测试）；②新增或调整用户可见的业务信息（信息本身变化，不只是改措辞）→ 同样走全关卡；③纯文案、颜色、间距、图标等不动语义的调整 → 免原型与人工测试。

| 关卡 | PLAN 功能 | 安全加固 | 复核整改 | 纯文档 | 重构 | 缺陷修复 |
|---|---|---|---|---|---|---|
| spec 文件 | 必（四部分） | 必（可沿用「一～七」骨架） | 不新开，原 spec 追加整改节 | 免 | 必（含行为等价声明） | 免 |
| AC 账本 | 必 | 必 | 必（本轮新增/改动 AC） | 免 | 必（AC=行为不变 + 特征测试清单） | 必（AC=复现用例） |
| 契约关 | 必 | 必 | 必 | 免 | 必（特征测试先行，无红态） | 必（复现用例红） |
| 用户确认 | 必 | 必 | 条件（改行为/范围） | 用户可见文档必 | 必 | 免（缺陷已由用户报出） |
| spec 独立评审 | 条件 | 必 | 免 | 免 | 条件（改公共接口） | 免 |
| 页面原型/人工测试 | 条件 | 条件 | 条件 | 免 | 免 | 条件 |
| 兑现关 | 必 | 必 | 必 | 免 | 必（行为等价证据） | 必 |
| 代码评审 | 必 | 必 | 免（由复审承担） | 免 | 必 | 必（小修可单代理） |
| 修复后复审 | 条件 | 条件 | 条件 | 免 | 条件 | 条件 |

**spec 独立评审触发条件**（任一命中）：L/XL；触及安全边界（认证/权限/沙箱/文件隔离/敏感值/审批链）；跨 ≥3 个顶层模块，或新增对外接口/数据表/迁移；历史上该区域出现过 P0/P1。S/M 且非安全边界不触发，汇报写明原因。

**重构的测试替代**：改实现前先写特征测试钉住当前对外行为（含已知怪癖），只测公共接口/端点/CLI，不测内部调用顺序，特征是绿的、替代红态；覆盖率不得低于重构前基线。重构同时改行为即不再是重构，退回 PLAN 功能档。

## 红线

- 没有用户确认的 spec（档位矩阵中免 spec 的档位除外），不开始写测试或编码；命中 spec 独立评审触发条件却未做、且无显式降级声明的，不得请求确认
- spec 自检未通过（名词未核对/AC 不可检验/账本「验证方式」列有空）的 spec 不得请求确认
- 带页面的功能：原型未经用户审核通过，不进入开发；页面功能未经用户人工测试确认，不进入代码评审
- spec 里的「待澄清问题」必须得到用户回答且**回写进 spec**，不得用假设替代
- 验收标准不得写成「工作正常」这类不可检验的表述
- 除纯文档档位外，功能代码不得先于测试用例（重构以特征测试先行替代红态）；无验证方式，或验证方式未执行且无留证的验收标准视为未完成
- 兑现关存在未清零缺口的，不得进入代码评审；复审触发命中却未执行的，不得提交
- 未经代码评审的变更不得提交（档位矩阵标「免」的除外）；评审确认的问题未修复又未在汇报中说明的，视为未完成；裁剪声明缺失或与实际不符的不得提交
- 项目宪法条款不得被任何一步绕过；冲突决定未在 spec 显式声明的视为无效
