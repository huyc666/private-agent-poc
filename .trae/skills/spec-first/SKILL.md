# Spec First + TDD

本仓库的研发流程约定：PLAN.md（docs/PLAN.md）中的每一项任务，编码前必须先有 spec；spec 确认后按测试驱动开发（TDD）——先写测试、后写实现。spec 是开发契约，测试是验收标准的可执行形式。

**带页面的功能**（Web 控制台、前端页面、交互界面等）在标准流程上叠加两道人工关卡：spec 确认后先出**页面原型**（调用原型设计 skill，如 trae-design:solo-design）经人工审核再开发；实现完成后做**页面功能展示与人工测试**，通过后才进入代码评审（页面实现可调用 frontend-design skill 保证质量）。

## 流程

1. **定位任务**：读 docs/PLAN.md，找到用户指定的任务编号，完整读取该行任务的内容要点、依赖、规模、验收标准与来源。
2. **必要的背景调查**：spec 涉及现有代码的，先读相关模块再写 spec；不基于猜测写现状描述。
3. **写 spec**：新建 `docs/specs/<任务号>-<短名>.md`（如 `6.2-usage-report.md`），固定四部分结构：

   ```markdown
   # Spec — <任务号 任务名>

   ## 1. 背景与目标
   简要（5 行内）：为什么做、做完是什么样子。引用 PLAN 行作为出处。

   ## 2. 需求分析与约束条件澄清
   - 功能边界：做什么、明确不做什么
   - 约束：安全约定（fail-closed/恒时比较/不回显原始异常等）、多用户隔离、
     性能、兼容性——凡受本项目既有约定影响的都列明
   - 待澄清问题：有歧义处逐条列出，先向用户提问，禁止擅自假设；无歧义写「无」

   ## 3. 关键技术与选型决策
   每个决策点给候选方案、选定的一个、取舍理由；遵循既有架构时写明「沿用 X」
   及理由，不为了新而新。

   ## 4. 验收标准
   条目化、可检验（Given/When/Then 或等价表述）；覆盖功能、边界与拒绝路径；
   注明每条用什么方式验证（单测/集成测/手工实测）。完成后逐条对照汇报。
   ```

   填写粒度与实际效果参照示例：`references/example-spec.md`（以已交付的 1.2
   包级 RBAC 为实例），写 spec 时参照其粒度，不照抄内容。

4. **请求确认**：把 spec 全文或要点呈现给用户，明确说「确认后先写测试再编码」。用户修改意见先落回 spec 再确认。
5. **页面原型（仅带页面的功能）**：spec 确认后、写测试之前，调用原型设计 skill（如 trae-design:solo-design）依 spec 出页面原型（布局、字段、交互状态、各角色可见性），呈现给用户人工审核；审核意见先落回原型再定稿。原型未经用户审核通过，不得进入 TDD。纯后端/CLI/工具类任务跳过此步。
6. **测试先行（红）**：原型通过（纯后端任务则 spec 通过）后、写任何功能代码之前，把验收标准逐条转为测试用例——
   - **功能测试**：主路径 + 边界值 + 异常输入，命名与验收标准编号对应（如 `test_ac3_xxx`）
   - **安全测试**：本仓库拒绝路径必须成对覆盖（越权访问、路径穿越、超限、fail-closed、未授权令牌等，参照 spec 第 2 部分列出的约束）
   - 离线可跑为主（沿用 tests/conftest.py 隔离体系）；需真实环境的走既有门控（RUN_LLM_TESTS / RUN_DOCKER_TESTS）
   - 跑一遍确认新用例按预期失败（红），失败原因与 spec 预期一致
7. **开发实现（绿）**：以让测试通过为完成定义来编码；不为未出现的用例过度设计。带页面的功能按已定稿原型实现 UI（可调用 frontend-design skill），页面行为不偏离原型；实现若需偏离，先回到用户确认。全部新用例转绿后跑全量回归，确认无既有用例破坏。
8. **页面功能展示与人工测试（仅带页面的功能）**：全量回归通过后、代码评审之前，真实启动服务展示页面功能（按原型逐项演示主要交互与边界状态），交用户人工测试；用户确认通过才进入代码评审。纯后端/CLI/工具类任务跳过此步。
9. **代码评审**：全量回归（及页面人工测试，如适用）通过后、提交之前，对本次变更执行一次通用代码评审，产出结构化问题清单（正确性、安全边界与拒绝路径、可维护性、性能）。执行方式：调用 TRAE-code-review skill 对本次变更差异评审；变更较大或触及安全边界（认证/权限/沙箱/文件隔离等）时，按 v0.17.13 既有做法再做一轮独立交叉验证。评审确认的问题修复后重跑全量回归；判定为误报或有意保留的，在汇报中写明理由。评审结论（发现问题数、修复情况）随本次提交一并汇报。
10. **收尾**：实现若偏离 spec（选型变化、砍范围），先更新 spec 并说明。提交时 spec、测试、实现同一 commit；汇报按验收标准逐条对照；PLAN 行同步标注交付状态。

## 红线

- 没有用户确认的 spec，不开始写测试或编码
- 带页面的功能：原型未经用户审核通过，不进入开发；页面功能未经用户人工测试确认，不进入代码评审
- spec 里的「待澄清问题」必须得到用户回答，不得用假设替代
- 验收标准不得写成「工作正常」这类不可检验的表述
- 功能代码不得先于测试用例；没有对应测试的验收标准视为未完成
- 未经代码评审的变更不得提交；评审确认的问题未修复又未在汇报中说明的，视为未完成
