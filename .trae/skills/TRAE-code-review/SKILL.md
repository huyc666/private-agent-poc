# TRAE Code Review

本仓库约定：任何变更提交前必须过一次通用代码评审（spec-first 红线「未经代码评审的变更不得提交」）。本 skill 定义该评审的固定流程——结论必须经双子代理独立交叉验证，不以单点判断定案。

## 流程

1. **范围判定**：默认范围为工作区未提交变更（`git status --short` + `git diff --stat` 确定文件清单与增删规模）；用户指定范围（commit 区间 / 文件 / PR）时以指定为准。范围内含 spec 文档的一并读入，作为「实现是否兑现承诺」的对照基准（spec-实现差距是常见问题类别）。
2. **上下文收集**：逐文件读 diff 与新文件全文；按需读关联模块（被调用的函数、前端调用点、既有测试）避免孤立判断；跑一遍相关测试套件确认当前基线是绿的。
3. **推断意图**：用 3-5 句话说明这次变更想做什么（对应 PLAN 任务 / bugfix）、核心链路是什么，并渲染一张 mermaid 图（flowchart 即可）作为汇报与讨论的共同参照。
4. **扫描候选问题**：主代理自查一轮，产出候选清单（宁可多报，交给下一步裁决），维度固定四类：
   - **正确性**：边界、空数据路径、异常路径、并发/锁
   - **安全边界与拒绝路径**：认证/权限/沙箱/文件隔离/敏感值入日志；前端隐藏入口只是体验层，服务端判定才是防线
   - **可维护性**：与既有约定一致性、命名、重复代码
   - **性能**：只标严重度，POC 单机场景下低危项不列
   同时对照已知盲区清单自查：空数据路径使循环体不执行（NameError 类漏网，测试须造数据覆盖非空路径）、agent/浏览器验证只看动作不看内容（下载触发 ≠ 内容正确）、bytes 字面量含中文、前端输出 esc() 转义是否含引号、延迟导入防循环依赖、端点名与 action 文案以实现为准。
5. **双子代理并行交叉验证**：在一条消息里并行派 2 个 general-purpose 子代理，各自独立验证**全部**候选（互不可见对方结论），要求：逐条给【确认】/【证伪】+ 理由 + 证据（文件:行号），允许跑 Python 实验验证语言语义（csv/splitlines/strip 等），**只验证不改代码**；提示语需自带项目背景与约定（审计不阻塞主链路、明文 Key/密码不入日志、target 域内相对路径等），不依赖子代理自行探索。
6. **裁决与汇报**：按票数裁决——**2/2 确认纳入；1/2 带疑纳入（标注分歧点与建议处置）；0/2 证伪排除**。汇报结构：
   - 意图理解 + mermaid 图
   - 问题表格：# ｜ 严重度 ｜ 位置（file:/// 链接带行号） ｜ 问题 ｜ 验证要点
   - 带疑项表格（建议处置）+ 排除项一句话理由
7. **修复选择**：用 AskUserQuestion 让用户选修复范围——推荐选项放首位并标注 (Recommended)；「有意保留」项必须写入选项文案供用户知情选择。
8. **修复与回归**：按用户选择修复，同步补测试（修复类改动必须带回归防线用例）；重跑相关测试 + 全量回归（`.venv\Scripts\python.exe -m pytest`）；README/PLAN 受影响时一并更新；提交信息需注明「评审修复 N 项 + 有意保留项」。
9. **收尾汇报**：逐项写明「已修复 / 误报排除（理由）/ 有意保留（理由）」；评审结论随提交汇报；push 恒由用户操作。

## 裁决与红线

- 子代理结论仅采信带证据（文件:行号或实验输出）的部分；无证据的泛泛判断不纳入
- 评审未完成、或确认问题未修复又未在汇报中说明理由的变更，不得提交
- 评审中不夹带与本次变更无关的重构；发现的相关问题记录为候选，由用户决定是否本次处理
- 「误报」「有意保留」必须在汇报中写明理由，不得静默丢弃
- 测试命名与验收标准编号对应（`test_acN_*`）；修复补的用例同样落测试文件随同一 commit 提交
